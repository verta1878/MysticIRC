_Delta against [Pattern Fill & Rasterization](../../1.54/techspecs/2.1-pattern-fill-rasterization.md) in the 1.54 techspecs. See the [tree README](../README.md) for standing and provenance._

Two rendering-quality items. Neither changes wire syntax: the same commands with the same arguments produce different-looking output.

## §A2G.4 - the built-in pattern table

RIPlib ships eleven built-in 8×8 patterns plus a user-defined slot, and describes providing them natively as a v3.1 improvement over implementations that carried eight and approximated the rest. `A2G.4`

| Slot | Name | 8×8 bytes (top row first, bit 7 = leftmost pixel) |
| --- | --- | --- |
| 0 | Solid | `FF FF FF FF FF FF FF FF` |
| 1 | 50% checker | `AA 55 AA 55 AA 55 AA 55` |
| 2 | Diagonal `\` | `88 44 22 11 88 44 22 11` |
| 3 | Diagonal `/` | `11 22 44 88 11 22 44 88` |
| 4 | Horizontal | `FF 00 FF 00 FF 00 FF 00` |
| 5 | Vertical | `AA AA AA AA AA AA AA AA` |
| 6 | Cross-hatch | `FF AA FF AA FF AA FF AA` |
| 7 | Light diagonal | `80 40 20 10 08 04 02 01` |
| 8 | Interleave | `CC 33 CC 33 CC 33 CC 33` |
| 9 | Wide dot | `80 00 08 00 80 00 08 00` |
| 10 | Close dot | `AA 00 AA 00 AA 00 AA 00` |
| 11 | User pattern | set by [RIP_FILL_PATTERN](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill_pattern) (`\|s`) |

`riplib (src/drawing.c:52-65)` - matches §A2G.4's table, which prints IDs 0-11 in the same order.

### These are slot numbers, not wire values

**Do not read the table above as a `|S` argument table.** The `pattern` argument of [RIP_FILL_STYLE](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill_style) keeps its documented meaning - `00` background, `01` solid, `02` line, `03` light slash … `0B` close dot, `0C` user - and RIPlib translates it to the slot table through an explicit mapping. `riplib (src/ripscrip.c:693-710)`

That mapping, the semantics of pattern `00`, and the fact that these bitmaps are an independently chosen set rather than the specification's own byte values are all **baseline** questions, not §A2G.4 ones - they are documented in [3.0-riplib → 2.0 Fill Pattern Mapping](../../3.0-riplib/techspecs/2.0-fill-pattern-mapping.md). The short version bearing on §A2G.4's claim to provide _"all 13 patterns natively"_: four of the thirteen wire values still resolve to approximations, and `05`/`06` collapse onto the same bitmap - the specific defect `§DEAD.6` sets out to fix, relocated rather than removed.

Pattern anchoring is the same in both: `pattern row = y & 7`, `pattern bit = 0x80 >> (x & 7)` on device coordinates, so adjacent shapes tile seamlessly. `spec (10 §A.7)`

## §A2G.5 - floating-point rendering

v3.1 moves four rasterization paths from fixed-point/integer approximations to single-precision floating point. `A2G.5` The stated target is a Cortex-M33 with a hardware FPU, which is why this is framed as a protocol revision rather than an internal change: it declares a hardware requirement.

| Path | Was | Now |
| --- | --- | --- |
| **Bezier curves** | Recursive integer De Casteljau subdivision, `>>1` shift rounding at each of 8 levels - error accumulates | Parametric cubic evaluation, `B(t) = (1-t)³P₀ + 3(1-t)²tP₁ + 3(1-t)t²P₂ + t³P₃`, adaptive step count (4-64) from control-polygon length |
| **Trigonometry** (arcs, pies, elliptical arcs) | 91-entry integer sine table with linear interpolation, ±1° accuracy | `sinf()`, `cosf()`, `atan2f()`, `sqrtf()` - under 0.01° |
| **Pie fill** | Flood fill seeded inside the arc + radii boundary; leaked through pixel gaps between the arc and the radial line endpoints | Per-pixel angle-and-distance test over the bounding box using `atan2f` - no leaks |
| **Coordinate scaling** | Integer `y * 8 / 7` | **Unchanged** - the integer result is exact for this ratio, so no FPU is used |

**The pie-fill change is the substantive one, and RIPlib is right about it.** Boundary-seeded flood fill escaping through a one-pixel gap is a real class of defect in the shipping TeleGrafix implementation, and replacing it with a scanline sector test removes it by construction rather than by tuning. This is the clearest case in either revision of RIPlib finding something this repository had not documented; the finding has been folded into the record on its own terms - see [2.0 fill defects](../../2.0/techspecs/2.1-fill-defects.md) and the [3.0 delta](../../3.0/techspecs/2.0-fill-defects-delta.md). RIPlib records the original behavior as `§BUG.6`. `spec (11 §11.3)`

Two related notes from the same segments, both affecting output without touching syntax:

- **Bezier `steps` is accepted and ignored.** The adaptive step count supersedes it, for both the single curve and the poly-bezier form. `spec (02 §2.20, 04 §4.7)` The [3.0 entry](../../3.0/ripscrip/2.2-curves.md) treats it as a real parameter; content that lowers it deliberately for a faceted look will not get one.
- **Patterned flood fill uses two passes** - a solid fill first, to establish the boundary correctly, then the pattern over it. `spec (02 §2.24)` This too is a correct fix to a real defect: `§DEAD.7` records that the DLL created the pattern brush but never applied it to the `ExtFloodFill` call, so patterned flood fills came out solid. Recorded in [2.0 fill defects](../../2.0/techspecs/2.1-fill-defects.md#dead7---the-patterned-flood-brush-was-never-applied).
