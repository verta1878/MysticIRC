# Connection Directory Model (delta)

[◀ Prev: UI Resources](3.5-ui-resources.md) · [Contents](README.md)

The storage model - a per-host [connection directory](../../glossary.md#client-storage) checked first, the shared [default icon directory](../../glossary.md#client-storage) as fallback, [file override](../../glossary.md#client-storage) semantics, auto-creation, case-insensitive lookup - is established for 1.54 in the [v1.54 connection directory model](../../1.54/techspecs/4.0-connection-directory-model.md) and does **not** change in 2.x. What changes is the **scope of what flows through it**: 2.x adds JPEG images, WAV audio, and host-deliverable `.RIP` scenes to the icon family, and adds a block-transfer mode whose extension table routes each received file automatically. Quotations below are from the RIPterm 2.30 manual (`~/src/rip-tools/artifacts/ripterm-2.30/extracted/RIPTERM.DOC`), the definitive 2.30 client documentation.

## One directory family for all host media

There was never a separate audio (or image, or scene) directory: the default directory - `ICONS\` historically - houses the entire host-deliverable media family. RIPTERM.DOC §2.1.4 ("Move Files To Their Correct Directories") tabulates it:

> There are other categories of files that must also be in the ICONS sub-directory for RIPterm to be able to use them:

| File Category            | File Extension       |
| ------------------------ | -------------------- |
| RIPscrip v1.x Icon Files | `.ICN` `.MSK` `.HOT` |
| RIPscrip v2.x Icon Files | `.BMP` `.BMM` `.BMH` |
| Image Files              | `.JPG`               |
| Sound Files              | `.WAV`               |
| RIPscrip Files           | `.RIP`               |

The same section's startup-housekeeping dialog groups them identically ("Icon Files (BMP, ICN, etc.) - Sound Files (WAV) - Image Files (JPG) - RIPscrip Files (RIP) … These files need to be moved into the ICONS directory"), and confirms the per-connection side applies to the whole family:

> NOTE: A host system can have its own ICONS directory containing any of the file type listed as valid for an ICONS directory. See Section 5.2 - The Dialing Directory for details on how to set this up.

**Fonts are the explicit exception** - they are global client resources, never per-connection:

> All font files must be in the FONTS directory. RIPterm does NOT scan the host system directories for font files, and ask to move them. _(RIPTERM.DOC §2.1.4)_

So a 2.x implementation applies the v1.54 lookup order (connection directory first, then default) to `.BMP`/`.BMM`/`.BMH`, legacy `.ICN`/`.MSK`/`.HOT`, `.JPG`, `.WAV`, and `.RIP` - and resolves fonts (`.CHR`, `.FF1`/`.RFF`, terminal fonts) only from the global font store. The shipped distribution itself models the layout: the 2.30 `ICONS\` directory carries 164 icons (142 `.BMP` + 22 `.BMH`), 7 JPEGs, and 36 RIP scripts side by side - 207 files in all ([asset inventory](../../2.0/assets/icons/README.md)), with `.WAV` listed as valid but none shipped ([audio](3.4-audio.md)).

## The per-connection directory catches the whole family

The dialing-directory entry's "System Dir" field (the RIPterm 2.30 name for the connection directory - the 1.54 manual's DIR field) is documented with the widened scope. RIPTERM.DOC §5.2.1, "System Dir":

> Each entry in the directory can have a sub-directory associated with it. This directory is used when RIPscrip graphics are being viewed on the host. Any icon, RIPscrip, sound, or image files that are sent by the host are automatically placed in the System Dir. This in effect, helps keep your icons separated from each other.

The lookup order and override rule restate the 1.54 model verbatim in behavior:

> If the System Dir field is not blank, RIPterm checks in that directory FIRST for any necessary files. If the files are not found in that sub-directory, RIPterm will check the ICONS\ sub-directory afterward to see if it is there. This facilitates the concept of "file override".

Auto-creation likewise: "You do not need to create the sub-directory yourself. RIPterm will create it for you automatically."

## Block-mode routing - the extension table

New in 2.x, [RIP_ENTER_BLOCK_MODE](../ripscrip/5.5-file-transfer-and-queries.md#rip_enter_block_mode) (`!|9<ESC>`, level 9) auto-initiates a file transfer whose `<file_type>` parameter tells the client what it is receiving - a `.RIP` sequence to play, generic files to store, icons, images to display - and, for the batch DYNAMIC modes, hands routing to a **per-extension table**: `RIP`, `BMP`, `BMH`, `BMM`, `JPG` (and `GIF`, v2.A4) are each placed "in proper directory", with ACTIVE DYNAMIC mode additionally playing/displaying `.RIP` and `.JPG` on arrival. The catch-all is explicit:

> If you receive file(s) with extensions other than the ones listed above, then no processing will be done on the files other than placing them in the appropriate Host Directory. _(spec v2.A0, [RIP_ENTER_BLOCK_MODE](../ripscrip/5.5-file-transfer-and-queries.md#rip_enter_block_mode))_

"Proper directory" resolves through the model above - the connection directory when one is set, else the default - and **not** through the user's ordinary download directory. The manual closes the loop (§5.2.1 NOTE):

> Any files received in this mode are automatically placed in the proper System Dir. If no System Dir is defined, then the ICONS\ sub-directory is used as the destination sub-directory. The Download Directory as set in the File Transfer Settings dialog box is not used in this situation as the destination directory.

Two implementation footnotes: `.WAV` is absent from the DYNAMIC extension tables (audio arrives via the generic file type and still lands in the media directory per §2.1.4), and the `GIF` rows are speculative spec surface - no shipped 2.x-generation client decodes GIF (see [JPEG images](3.1-jpeg-images.md)). The same delivery path serves [RIP_FILE_QUERY](../ripscrip/5.5-file-transfer-and-queries.md#rip_file_query) update checks and the v2.A4 RIP_FILE_DELETE cleanup of "unneeded JPEG or WAVE files".

## Manual Connect - a connection directory for unlisted hosts

The RIPterm 2.30 client extends the model to hosts that have no dialing-directory entry: the Manual Connect dialog (RIPTERM.DOC §3.3, "Manual Connect Alt-M") prompts for a phone number **and a System Directory** - i.e. an ad-hoc connection directory for the session:

> You are prompted you to enter the Phone Number to dial, and the name of the System Directory to use for icons and any other files the host needs while you're connected (if any).

> For the icon directory, enter the name of the directory that contains the icons this system may need, or a directory that you use for temporary files. If you never call this system again, you won't want to keep its icons hanging around on your hard disk taking up space.

The manual is emphatic that bypassing both mechanisms breaks the model - "if you dial a host by typ[ing] modem commands directly … the correct directory may not be used since RIPterm has no way of knowing which Dialing Directory entry you are calling … You can use the Manual Connect option to dial a host and set the correct System Dir" (§5.2.1). For a modern implementation the takeaway is that **every session has a connection-directory binding** - persistent for known hosts, ad-hoc (and user-discardable, per the temporary-directory advice) for unlisted ones - never an unscoped shared write.

## Implementer summary

- Resolution order, override semantics, auto-creation, and case-insensitivity: identical to [v1.54](../../1.54/techspecs/4.0-connection-directory-model.md).
- Apply them to the full 2.x media family - icons (both generations), `.JPG`, `.WAV`, `.RIP` - in **one** per-connection namespace plus **one** shared default; do not invent per-type directories.
- Fonts resolve globally only; host-delivered font files are not part of the model.
- Block-mode/UU-encoded deliveries route by extension into that namespace, bypassing any user download directory; unknown extensions are stored, not processed.
- Sessions to unlisted hosts still get a connection directory (the Manual Connect prompt is the historical UI for it); a temporary, discardable directory is an explicitly sanctioned choice.
