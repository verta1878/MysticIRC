# 2.0 Fill Pattern Mapping

[◀ Prev: 1.0 Stream Parsing & Escapes](1.0-stream-parsing-and-escapes.md) · [Contents](README.md)

_Delta against [Pattern Fill & Rasterization](../../1.54/techspecs/2.1-pattern-fill-rasterization.md). See the [tree README](../README.md) for how each side's evidence should be weighed._

Both projects implement the same twelve-value `pattern` field on [RIP_FILL_STYLE](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill_style) (`|S`) plus a user-defined pattern via [RIP_FILL_PATTERN](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill_pattern) (`|s`), and both anchor patterns to device coordinates (`row = y & 7`, `bit = 0x80 >> (x & 7)`) so adjacent shapes tile seamlessly. Three things differ underneath.

## Wire values map correctly, with four approximations

RIPlib keeps eleven built-in 8×8 patterns in slots 0-10 plus a user slot at 11, and translates the wire `pattern` value into that table through an explicit mapping. `riplib (src/ripscrip.c:693-710)` Out-of-range wire values fall back to no fill rather than wrapping. `riplib (src/ripscrip.c:2187-2198)`

**The wire semantics are right** - `01` is solid, `0B` is close-dot, `0C` is the user pattern, as documented. The mapping is not one-to-one, though, which qualifies §A2G.4's claim to provide _"all 13 patterns natively"_:

| Wire `pattern` | Documented meaning | RIPlib slot | Exact? |
| --- | --- | --- | --- |
| `00` | Fill with background color (color #0) | _(skipped - no fill)_ | see below |
| `01` | Solid | 0 solid | yes |
| `02` | Line (thick horizontal) | 4 horizontal | yes |
| `03` | Light slash | 7 light diagonal | approximate |
| `04` | Normal slash | 3 diagonal `/` | yes |
| `05` | Normal backslash | 2 diagonal `\` | yes |
| `06` | Light backslash | 2 diagonal `\` | **approximate** - no lighter variant exists, so `05` and `06` render identically |
| `07` | Light hatch | 6 cross-hatch | yes |
| `08` | Heavy cross hatch | 1 50% checker | **approximate** - "closest dense X feel" |
| `09` | Interleaving line | 8 interleave | yes |
| `0A` | Wide dot | 9 wide dot | yes |
| `0B` | Close dot | 10 close dot | yes |
| `0C` | User-defined | 11 user pattern | yes |

Four of the thirteen remain approximations, and `05`/`06` collapse onto one another - the specific defect §A2G.4 sets out to fix (`§DEAD.6`), relocated rather than removed. The source comments are candid about it ("no lighter variant"). **Disposition: compatible in structure, incomplete in coverage** - not a protocol conflict, just a gap against the stated claim.

## Pattern `00` - background fill versus no fill

⚠ The specification defines `00` as _"Fill with background color"_, an all-zero bit pattern that paints solid color 0; the 1.54 entry is explicit that _"Fill pattern 00 will set the entire fill area to the background color. (In this special case, the fill color doesn't matter.)"_ ([1.54 RIP_FILL_STYLE](../../1.54/ripscrip/2.3-shapes-and-fills.md#rip_fill_style))

Implementations already differ here. SyncTERM's scanline **polygon** filler skips filling entirely when style 0 is active, while bars and flood fills paint solid color 0 by the general rule ([1.54 fill styles](../../1.54/techspecs/2.1-pattern-fill-rasterization.md#fill-styles-and-patterns)); which of the two RIPterm 1.54 did for filled polygons is unverified. RIPlib skips the fill for **every** primitive.

**Disposition: open, leaning toward the documented reading for bars.** A scene using `!|S0000` followed by a bar to blank a region is a no-op on RIPlib. The specification's wording covers the bar case unambiguously; the polygon case is genuinely uncertain in every implementation. Worth aligning at least for bars and rectangles.

## The pattern bitmaps are an independent set

RIPscrip's own specification prints the eight byte values for each pattern in hex, decimal and MegaNum - and one of them is famously wrong in a way RIPterm faithfully implemented. The "Light Backslash" style's documented bytes are `A5 D2 69 B4 5A 2D 96 4B`, which do not form a backslash; the plausible intended bytes are `80 40 20 10 08 04 02 01`. SyncTERM ships the documented bytes, labeling the alternative "as expected" and the shipped one "as documented" ([1.54 fill styles](../../1.54/techspecs/2.1-pattern-fill-rasterization.md#fill-styles-and-patterns)).

RIPlib's eleven built-in bitmaps are an independently chosen set (`riplib (src/drawing.c:52-65)`; tabulated in [3.1-riplib techspecs 2.0](../../3.1-riplib/techspecs/2.0-fill-patterns-and-rendering.md)). Fills therefore render with the right _character_ but not the same pixels.

**Disposition: open, and a real decision rather than an error.** Byte-exact fidelity matters when a fill has to tile against era artwork or match a reference render; a cleaner modern set looks better in isolation. Either choice is defensible, but it should be a recorded choice - and if fidelity wins, the "as documented" Light Backslash bytes come with it, error included.
