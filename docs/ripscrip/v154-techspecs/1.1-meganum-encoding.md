# MegaNum Encoding

[◀ Prev: .RIP Stream & File Parsing](1.0-rip-stream-parsing.md) · [Contents](README.md) · [Next: Canvas, Clipping & Write Modes ▶](2.0-canvas-clipping-write-modes.md)

RIPscrip's numeric parameters are base-36 ("Hexa-Tri-Decimal", dubbed **MegaNums**), using digits `0`-`9` and `A`-`Z`, most significant digit first, in fixed-width fields with no delimiters (spec, [protocol structure](../ripscrip/1.1-protocol-and-command-hierarchy.md) item 10). The spec defines the digit set and per-command field widths but leaves signedness, case, invalid input, and overflow behavior unstated.

## Basics

- Digit values: `0`-`9` = 0-9, `A`-`Z` = 10-35. Value = Σ digit·36^position, MSD first: `2G` = 2·36 + 16 = 88.
- Fields are fixed-width and zero-padded; writers emit uppercase (all TeleGrafix-authored files observed use uppercase only, e.g. every scene in `~/src/rip-tools/artifacts/ripaint-1.52/RIPAINT.ZIP` and `RIPtermJS:rips/`).
- Ranges per width: 1 digit 0-35, 2 digits 0-1,295, 3 digits 0-46,655, 4 digits 0-1,679,615, 6 digits 0-2,176,782,335. Screen coordinates use width 2 (1,295 comfortably covers 0-639).
- If a command takes a text string, it is always the **last** parameter and is never meganum-encoded; a variable-width numeric parameter may also appear last (spec item 10) - in practice this is the coordinate list of the polygon/polyline commands (`P`, `p`, `l`), a repeated sequence of 2-digit pairs running to end of command.

## Field widths

Widths are defined per parameter in each command's spec entry (see the [command reference](../ripscrip/9.0-command-reference.md) and the per-chapter pages - e.g. RIP_TEXT_XY `@` is `x:2, y:2, text`, RIP_LINE_STYLE `=` is `style:2, user_pat:4, thick:2`, RIP_BUTTON_STYLE `1B` ends with a 6-digit `flags2`-era field). SyncTERM encodes the full width map as descriptor strings - `2#` = 2-digit field, `+2#` = variable-length list of 2-digit fields, `++` = trailing text - in its `rip_cmd_descs[]` table (`sbbs:src/syncterm/ripper.c`), which is a convenient machine-readable cross-check of every 1.5x command's layout. Notable widths beyond the ubiquitous `2#`:

| Command | Descriptor | Reading |
| --- | --- | --- |
| RIP_LINE_STYLE `=` | `2#4#2#` | style, 16-bit user pattern as 4 digits, thickness |
| RIP_FILL_PATTERN `s` | `2#` ×9 | eight 8-bit pattern rows + fill color, each 2 digits |
| RIP_WRITE_MODE `W` | `1#` | single digit 0/1 |
| RIP_FONT_STYLE `Y` | `2#2#2#1#1#` | font, direction, size, then the reserved word split 1+1 |
| RIP_POLYGON `P` / RIP_POLYLINE `l` | `2#2#2#+2#` | npoints, first x, first y, then 2-digit pairs to end |
| RIP_LOAD_ICON `1I` | `2#2#2#1#1#1#++` | x, y, mode, clipboard, res (2 digits), filename |
| RIP_BUTTON `1U` | `2#2#2#2#2#1#1#++` | coords, hotkey, flags, res, text |
| RIP_BUTTON_STYLE `1B` | `2#2#2#4#2#…2#6#` | incl. 4-digit flags and trailing 6-digit field |
| RIP_DEFINE `1D` | `3#2#++` | 3-digit variable number |
| RIP_ENTER_BLOCK_MODE `9␛` | manual | 1-, 2- and 4-digit fields mixed (the 4-digit field is the reserved `res`) |

(Descriptor strings quoted from `sbbs:src/syncterm/ripper.c` `rip_cmd_descs[]`; they match the 1.54 spec's argument lists command-for-command.)

## Edge cases as implemented

The subtleties below matter for byte-exact compatibility with RIPterm and with wild `.RIP` data. Primary source: SyncTERM's parser, whose comment declares it "BGI-exact" - i.e. matched to RIPterm's observed behavior (`sbbs:src/syncterm/ripper.c` `parse_mega()`); cross-checked against `icy_tools:crates/icy_parser_core/src/rip/builder.rs` (`BASE36_LUT`, `parse_base36_complete()`), `RIPtermJS:src/ripterm.js` (`parseRIPargs()`), and `pablodraw:Source/Pablo/Formats/Rip/RipExtensions.cs` (`ReadRipNumber()`/`ReadRipWord()`).

- **Case-insensitive digits.** `a`-`z` are accepted with the same values as `A`-`Z` (`parse_mega()`: explicit `'a'..'z'` branch; `BASE36_LUT` maps both ranges). Writers still emit uppercase; lowercase appears in the wild in filenames-adjacent contexts (e.g. `meowbody.ICN` follows lowercase-tolerant fields in `RIPAINT.ZIP:MEOW.RIP`). PabloDraw is the outlier: it accepts only `0-9A-Z` and silently reads any other byte as digit value 0 (`ReadRipNumber()` returns 0 on fall-through).
- **MegaNums are unsigned; `-` is not a sign.** No 1.54 parameter is negative. SyncTERM's BGI-exact parser accepts `-` **as a digit with value 0** (`ret = ret * 36`), so `-5` parses as 5 and `1-` as 36 - quirk compatibility, not signedness. No writer emits `-`.
- **Early termination.** A field may be cut short by `|` (next command) or end-of-input after at least one digit; the value is whatever was accumulated (`parse_mega()`: `break` on `'|'`/`'\0'` when `i > 0`). Wild files depend on this: `!|W0|…` (1 digit for the spec's 2-digit write mode) appears in the opening line of `RIPtermJS:rips/set1/11FV.RIP`.
- **Invalid characters reject the whole command.** Any other byte inside a numeric field makes the command fail: SyncTERM returns -1 and the command is dropped; RIPtermJS gets `NaN` from `parseInt(…, 36)` and skips the command (`noNaNs()` guard). For variable-length coordinate lists, SyncTERM additionally rejects the entire command if non-meganum bytes remain after the list (`parse_rip_args()` comment: "BGI rejects the entire command if any non-meganum characters remain after the varlen fields").
- **No overflow checking.** Accumulation is unchecked multiply-add; icy_term wraps at 16 bits (`wrapping_mul`/`wrapping_add` into `u16`), SyncTERM accumulates into a C `int`. Well-formed 1.54 traffic never exceeds 16-bit values except in the 6-digit button-style field.
- **Splitting across continuations.** Because line continuation is handled below the tokenizer, a fixed-width field can be split by `\` CRLF mid-number (observed in `RIPtermJS:rips/set1/11FV.RIP`; PabloDraw reads through continuations inside `ReadRipByte()` before digit conversion). See [.RIP Stream & File Parsing](1.0-rip-stream-parsing.md#the-80-column-convention-and--continuation).
- **Composition in decoders.** Multi-digit fields are just positional accumulation - PabloDraw expresses a 2-digit word as `ReadRipNumber() * 36 + ReadRipNumber()` and a 4-digit int as `word * 1296 + word` (`RipExtensions.cs`), a useful identity for writers: emit `value / 36^k % 36` per position.

## Worked examples

```text
"00"  = 0          "0F" = 15         "2G" = 2·36+16 = 88
"6Y"  = 6·36+34 = 250                "ZZ" = 35·36+35 = 1295
"1295" (4-digit) = 1·46656 + 2·1296 + 9·36 + 5 = 49,577
RIP_LINE_STYLE "=00000001": style 00, user pattern 0000, thickness 01
RIP_TEXT_XY  "@2233hello": x = 2·36+2 = 74, y = 3·36+3 = 111, text "hello"
```

(The `@2233` example follows the spec's own usage in [protocol structure](../ripscrip/1.1-protocol-and-command-hierarchy.md) item 13, which glosses it "at (22,33) [meganum]".)
