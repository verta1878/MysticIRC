# Bitmap Fonts (`RIPTERM.FNT`)

[◀ Prev: BGI Stroked Fonts](3.1-bgi-stroked-fonts.md) · [Contents](README.md) · [Next: Connection Directory Model ▶](4.0-connection-directory-model.md)

`RIPTERM.FNT` (18,596 bytes) is RIPterm's "system font data file" (RIPTERM.DOC distribution file list): a container of five bitmap character sets backing the text/ANSI window's five selectable System Fonts and, via its 8x8 charset, the graphics-window default font (RIP_FONT_STYLE font 0). It shipped alongside `RIPTERM.EXE` rather than in `FONTS\`, and is preserved byte-exact at [`version/1.54/assets/fonts/RIPTERM.FNT`](../../1.54/assets/fonts/README.md).

**Provenance:** no TeleGrafix documentation of this container is known; the layout below is original reverse engineering from the file's bytes, verified arithmetically and visually.

## Container layout

```text
offset 0x00:  24-byte signature:
              04 20 "RIPterm Font File" 20 04 0A 00 1A
              (0x04, space, 17-char title, space, 0x04, LF, NUL, DOS-EOF 0x1A -
               the trailing 0x1A makes DOS `TYPE RIPTERM.FNT` stop after the title)
offset 0x18:  uint16 charset_count            = 5
offset 0x1A:  charset_count directory entries, 42 bytes each
offset 0xEC:  glyph data, tightly packed in directory order
```

Each 42-byte directory entry:

```c
struct fnt_dir_entry {
    char     name[30];         /* NUL-padded: "8x8 Font", "7x8 Font", ...   */
    uint16_t width;            /* glyph cell width in pixels                */
    uint16_t height;           /* glyph cell height in pixels               */
    uint16_t bytes_per_glyph;  /* = height * ceil(width / 8)                */
    uint16_t reserved;         /* 0 in all entries                          */
    uint32_t data_offset;      /* absolute file offset of this charset      */
};
```

All integers little-endian. The five entries decode as:

| #   | Name         | Cell  | Bytes/glyph | Data offset | Charset size |
| --- | ------------ | ----- | ----------: | ----------: | -----------: |
| 0   | `8x8 Font`   | 8x8   |           8 |         236 |        2,040 |
| 1   | `7x8 Font`   | 7x8   |           8 |       2,276 |        2,040 |
| 2   | `8x14 Font`  | 8x14  |          14 |       4,316 |        3,570 |
| 3   | `7x14 Font`  | 7x14  |          14 |       7,886 |        3,570 |
| 4   | `16x14 Font` | 16x14 |          28 |      11,456 |        7,140 |

Consistency proof: each charset size equals **255 × bytes_per_glyph**, consecutive offsets differ by exactly that amount, and 11,456 + 7,140 = 18,596 - the file size to the byte. Header + directory = 26 + 5·42 = 236 = the first data offset, so the file is fully accounted for with no gaps.

## Glyph data

- Each charset stores **255 glyphs for character codes 1-255**; code 0 is not stored (glyph index = code - 1). Evidence: the first glyph at offset 236 is `7e 81 a5 81 bd 99 81 7e` - the classic IBM 8x8 smiley, CP437 code point 1 - and indexing `'A'` (0x41) at offset 236 + 0x40·8 yields `38 6c c6 c6 fe c6 c6 00`, the standard 8x8 capital A.
- Rows are stored top to bottom, one row per `ceil(width/8)` bytes, bit 7 = leftmost pixel; the 7-wide charsets still use one byte per row (low bit unused), and the 16-wide charset stores two bytes per row, left byte first.
- The glyph repertoire is CP437, the IBM PC code page used by DOS-based BBS terminals (box-drawing, block, and dingbat characters render correctly when decoded per the layout above).

## How RIPterm uses the five charsets

The System Font setting selects the text/ANSI-window font; it "does not have any effect on the graphics shown" (RIPTERM.DOC §2.4.2, "SYSTEM FONT"). The five documented text modes map onto the five charsets by dividing the 640x350 EGA screen:

| Text mode (RIPTERM.DOC) | Charset | Arithmetic                          |
| ----------------------- | ------- | ----------------------------------- |
| 80x43 (default)         | 8x8     | 640/8 = 80, 350/8 = 43.75 → 43 rows |
| 91x43                   | 7x8     | 640/7 = 91.4 → 91 cols              |
| 80x25 (normal DOS)      | 8x14    | 640/8 = 80, 350/14 = 25             |
| 91x25                   | 7x14    | 640/7 → 91 cols, 350/14 = 25        |
| 40x25 (low-res)         | 16x14   | 640/16 = 40, 350/14 = 25            |

(The mode list is from RIPTERM.DOC; the charset assignment follows from the cell sizes and is corroborated by RIPtermJS's identically-dimensioned `w0`-`w4` window fonts.)

## RIP_FONT_STYLE font 0 - the default 8x8 graphics font

Font `00` in [RIP_FONT_STYLE](../ripscrip/3.0-text-output-and-fonts.md#rip_font_style) is the only bit-mapped entry in the font table, and it is this file's 8x8 charset (same IBM-style glyphs; RIPtermJS ships its font 0 as a direct render of it, `RIPtermJS:fonts/8x8.png`). Behavior details, as specified and as implemented:

- **Magnification is pixel replication.** At size N each glyph pixel becomes an N×N block and the character cell advances 8·N pixels; the spec itself warns the result looks jagged above size 1 (spec note under RIP_FONT_STYLE; implementation: `sbbs:src/syncterm/ripper.c` `write_char()` replicates each set bit over `size × size` pixels, `RIPtermJS:src/BGI.js` `drawPNGChar()` scales the same way). Unlike the stroked fonts, size 1 really is 1:1 for font 0 - see the scaling-table discrepancy in [BGI Stroked Fonts](3.1-bgi-stroked-fonts.md#scaling-rip-size-vs-actual-magnification).
- **Both directions are supported.** Direction 01 (vertical) rotates each glyph 90° counter-clockwise and advances upward, matching stroked-font behavior (`sbbs:src/syncterm/ripper.c` `write_char()` vertical branch).
- **Text drawn with font 0 honors the current drawing color and write mode**, like all graphics text ([RIP_TEXT attributes list](../ripscrip/3.0-text-output-and-fonts.md#rip_text): "Draw Color, Write Mode, Font Sizes, Viewport").
- **Full 1-255 repertoire.** Because the charset covers codes 1-255, font 0 can draw CP437 line/block art in the graphics window (subject to the [protocol's escaping rules](1.0-rip-stream-parsing.md#escaping) for `!`, `|`, `\`).

The 2.x family replaced this container with a "MicroANSI" `RIPTERM.FNT` of a different internal format - see `version/2.0/techspecs/` (documented as a delta from this page).
