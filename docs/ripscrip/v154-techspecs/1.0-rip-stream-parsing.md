# `.RIP` Stream & File Parsing

[Contents](README.md) · [Next: MegaNum Encoding ▶](1.1-meganum-encoding.md)

A `.RIP` file is not a distinct binary format: it is a captured RIPscrip command stream - exactly the bytes a host would transmit - stored as a DOS text file, so everything in the [protocol structure chapter](../ripscrip/1.1-protocol-and-command-hierarchy.md) applies verbatim.

_On-disk conventions and spec deviations below are drawn from real 1.5x-era files: RIPaint 1.52's shipped scenes (`~/src/rip-tools/artifacts/ripaint-1.52/RIPAINT.ZIP`) and the RIPtermJS test corpus (`RIPtermJS:rips/`)._

## Storage: CRLF and CP437

- Line endings are CRLF (`0D 0A`), as in every DOS-era capture examined (e.g. `RIPtermJS:rips/set1/11FV.RIP`, hexdump shows `0d 0a` terminators). Line endings are **significant**: a bare CR terminates (dispatches) a command, and parsers treat CR/LF distinctly (see [Parsing model](#parsing-model-stream-not-lines)). This repository stores `.rip` files byte-exact for this reason (`.gitattributes` `-text` exemption; see [CONTRIBUTING.md](../../../CONTRIBUTING.md#checkout--repository-setup)).
- Text content (RIP_TEXT strings, button labels, embedded raw text) is CP437 - the code page of DOS-based BBS terminals and host software. There is no in-band encoding declaration.

## Line structure

Per the spec's syntax rules ([protocol structure](../ripscrip/1.1-protocol-and-command-hierarchy.md), items 1-13):

- A RIPscrip line begins with `!|` at the start of a line (column 0). Alternatively the `!` may be replaced by SOH (0x01) or STX (0x02), which are allowed mid-line - a host-only capability, since BBS users generally couldn't type control characters (spec item 12; `sbbs:src/syncterm/ripper.c` `cb_accept_introducer()` accepts `!` only at line start but SOH/STX anywhere).
- After the introducer, commands are separated by `|`. Each command is `[level digits][command char][fixed-width meganum args][optional text arg]` - e.g. `!|c0F|L00001010` is two commands (color, line). See [MegaNum Encoding](1.1-meganum-encoding.md) for the numeric fields.
- Anything on a line that does not begin with `!|` (or SOH/STX + `|`) is raw text routed to the text window, including ANSI sequences (spec items 6-7).

### The 80-column convention and `\` continuation

Spec item 5 allows any command or line to be split with a backslash immediately before the line break, "to conform to right margins and escape word wrapping". Observed practice:

- TeleGrafix-era tools wrap at 80 columns: every file in `RIPtermJS:rips/set1` and `set2` (RIPaint/RIPterm-era captures) has a maximum line length ≤ 80 including the `\`.
- The split may land **anywhere** - mid-parameter, mid-number, even mid-filename. `RIPtermJS:rips/set1/11FV.RIP` line 4 ends `…1A5W1F6A177\` CRLF and resumes with the remainder of the same polygon's coordinate list; another line splits the text `FOR YOUR     VIE\` CRLF `WING PLEASURE…` in the middle of a word.
- The 80-column limit is a writer convention, **not** a reader guarantee: later files in the wild run longer (files in `RIPtermJS:rips/set3` reach 129-130 columns) and terminals accept arbitrarily long lines. Parsers must not allocate fixed 80-byte line buffers.
- Continuation is resolved by counting trailing backslashes: an **odd** count means the last `\` is a continuation (strip it, splice the next line on); an **even** count means the backslashes are escaped literal data and the line ends normally (spec item 13's `\\\` example; implemented in `sbbs:src/syncterm/ripper.c` `cb_feed()` CR handling).

### Escaping

Inside text parameters (spec items 11 and 13):

- `\!` → literal `!`, `\|` → literal `|`, `\\` → literal `\`.
- Real-file example: `!|…@1O65FOR YOUR     VIEWING PLEASURE\!|…` in `RIPtermJS:rips/set1/11FV.RIP` - the `\!` keeps the exclamation mark out of introducer position; the following `|` still separates commands.
- SyncTERM generalizes: any `\X` other than `\|` collapses to `X` during pre-processing, and `\|` is protected through argument slicing so the pipe reaches the command handler as data (`sbbs:src/syncterm/ripper.c` `cb_unescape()`).

## Parsing model: stream, not lines

Terminals parse `.RIP` content as a byte stream, and files depend on it (`sbbs:src/syncterm/ripper.c` `cb_feed()`/`cb_dispatch()`, whose behavior was verified against RIPterm):

- `|` dispatches the accumulated command immediately and starts the next one - a terminal must not wait for end-of-line to execute.
- CR (not LF) terminates the final command of a line, after the trailing-backslash continuation check; LF is swallowed unconditionally while a command is being accumulated.
- If `!` is not followed by `|`, both characters are re-emitted as ordinary text (un-rip path) - so a lone `!` in column 0 of a text line is safe.
- Unrecognized trailing text after a complete command is ignored without invalidating the command (spec item 6).
- ESC sequences are intercepted by a separate sub-machine even mid-stream, which is how the auto-sense queries work (below).

## Embedded ANSI and plain text

Because non-`!|` lines pass through to the text window, `.RIP` files freely intermix RIPscrip with ANSI. The end of `RIPtermJS:rips/set1/11FV.RIP` is a real example - four lines of ANSI music with SGR color and cursor-up sequences sandwiched between RIP lines:

```text
!|c0B|Y0A000300|@685VRIP|S0103|F6X6Q0B|F776Z0B|F6F6C0B|e␍␊
␛[0;30m␛[MF T200 O2 L8 p2b64>c2<b64>c4.<b>cd2.p8cd4cdc4<ba#1␎  .␍␊
␛[A␛[MF T200 O3 L8 c#64d2c#64d4.c#de2.p8de4ded4c#c1␎     .␍␊
…
␛[A␛[0;37;40m␛[K␍␊
!|w0000000000|#|#|#␍␊
```

The ANSI goes to the text window on top of the graphics; `␛[A` (cursor up) keeps the music lines from scrolling the display. Auto-sensing sequences may also appear in captures: `ESC[!` / `ESC[0!` query the terminal version (answered `RIPSCRIP015410` by RIPterm 1.54), `ESC[1!` disables and `ESC[2!` re-enables RIPscrip parsing ([protocol structure - ANSI sequences](../ripscrip/1.1-protocol-and-command-hierarchy.md#ansi-sequences-auto-sensing); `sbbs:src/syncterm/ripper.c` `cb_esc_feed()` implements exactly these four).

## Scene prologue and epilogue conventions

TeleGrafix never specified how a `.RIP` file should begin or end, but the shipped scenes are consistent. Surveying first commands across the RIPaint distribution scenes and `RIPtermJS:rips/set1`-`set3`:

- **Prologue** - nearly every scene opens with some ordering of: `!|*` ([RIP_RESET_WINDOWS](../ripscrip/1.3-world-view-virtual-canvas.md#rip_reset_windows) - full reset + clear), `!|1K` ([RIP_KILL_MOUSE_FIELDS](../ripscrip/4.1-mouse-fields.md#rip_kill_mouse_fields) - the spec explicitly recommends it "at the beginning of each Scene"), and a [RIP_TEXT_WINDOW](../ripscrip/1.4-terminal-ansi-view.md#rip_text_window) definition (`!|w…`, often `w0000000000` to hide the text window or a full definition like `w0013271410`). Common observed openings: `!|*|1K|w0013271410|…`, `!|1K|*|w0010271610|…`, `!|1K` alone, `!|*` alone.
- Scenes that need a known graphics state continue with `W0` (write mode copy), `=00000001` (solid line, width 1), a palette (`Q…`/`a…`), and a color (`c0F`) before drawing - state is inherited from whatever ran before, so well-behaved scenes re-establish it (cf. [Canvas, Clipping & Write Modes - reset semantics](2.0-canvas-clipping-write-modes.md#reset-semantics)).
- **Epilogue** - files end with `|#|#|#` - three consecutive [RIP_NO_MORE](../ripscrip/5.5-queries-and-advanced-commands.md#rip_no_more) commands, following the spec's own advice that "the Host should transmit three or more RIP_NO_MORE commands consecutively" for noise immunity. Observed at end of file in `11FV.RIP`, `184.RIP`, `MAINMENU.RIP`, and most of the corpus, sometimes followed by one empty CRLF line.

## Known field-layout variance in the wild: RIP_LOAD_ICON `res`

The 1.54 spec defines [RIP_LOAD_ICON](../ripscrip/4.0-images-and-icons.md#rip_load_icon) as `!|1I <x:2> <y:2> <mode:2> <clipboard:1> <res:2> <filename>` and - uniquely among reserved fields - says `res` "should be set to `10`" (`RIPScrip-1.54.txt`, RIP_LOAD_ICON notes). Real 1.5x files disagree with each other:

```text
RIPAINT.ZIP:MEOW.RIP     !|1I4P2R00110meowbody.ICN     res "10" present (per 1.54 spec)
RIPAINT.ZIP:BOUNCY.RIP   !|1I000003110CHROME.MSK       res "10" present
RIPAINT.ZIP:RIPTANK.RIP  !|1I6Y1X010SHOTU.ICN          res ABSENT (pre-1.54 layout)
RIPAINT.ZIP:RIPTANK.RIP  !|1I002G0101TANK.ICN          res ABSENT (filename "1TANK.ICN")
```

A parser applying the 1.54 field widths to the `RIPTANK.RIP` lines consumes the first two filename characters as `res` (they are valid meganum digits) and then looks for a file that doesn't exist (`OTU.ICN`, `ANK.ICN`). Both styles shipped **in the same RIPaint 1.52 distribution**, so robust loaders of wild files need a heuristic (e.g. try the 1.54 layout, and on file-not-found retry without the `res` field). The spec's odd "set to 10" instruction makes 1.54-conformant streams self-consistent - but nothing enforces it in older material. This is the sharpest known example of why `.RIP` archives cannot be parsed by field widths alone without version context.

## Related: local playback

RIPterm can replay local `.RIP` files outside a connection: the `-R<file>` command-line switch, and the `$>FILENAME$` [local playback text variables](../ripscrip/5.3-local-playback.md) (e.g. `$>FILE1.RIP$$>FILE2.RIP$`), which search the current host's icon directory then `ICONS\` (RIPTERM.DOC, "-R" startup option and §on local RIP playback variables; the lookup order is part of the [connection directory model](4.0-connection-directory-model.md)). [RIP_PLAY_MACRO / scene playback](../ripscrip/5.5-queries-and-advanced-commands.md) likewise feeds a cached file back through the same stream parser (`sbbs:src/syncterm/ripper.c` `rip_play_scene()` re-enters `cb_feed()` with saved parser state, recursion capped at 8 levels).
