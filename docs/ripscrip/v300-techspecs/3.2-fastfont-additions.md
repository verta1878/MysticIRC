# FastFont Additions (.RFF / atf.cfg)

[◀ Prev: Fill Defects (delta)](2.0-fill-defects-delta.md) · [Contents](README.md) · [Next: MicroANSI Delta ▶](3.3-microansi-maf-delta.md)

The Atech FastFont outline-font format is fully documented in the 2.0 techspec [FastFont Outline Fonts (.FF1 / .RFF)](../../2.0/techspecs/3.2-fastfont-fonts.md); this page documents only what RIPtel 3.1 changes: three new font families and a regenerated catalog.

Files referenced live in `~/src/rip-tools/artifacts/RIPtel/FONTS/` and byte-exact in [`version/3.0/assets/fonts/`](../../3.0/assets/fonts/README.md); all integers little-endian.

## Carried-over families - byte-identical

RIPtel 3.1 ships the five RIPterm 2.30 families unchanged. Every one is **md5-identical** to its RIPterm 2.30 counterpart (verified `~/src/rip-tools/artifacts/RIPtel/FONTS/*.RFF` vs `~/src/rip-tools/artifacts/ripterm-2.30/extracted/FONTS/*.RFF`):

| Family      | md5 (both copies)                  |
| ----------- | ---------------------------------- |
| COBB.RFF    | `d19dadc63c43d826df2ce1320f1e1324` |
| DEFAULT.RFF | `a1ce1aac2b65a0f23e1c358ecb952b15` |
| DIXON.RFF   | `1edaf8f0df33fb47b524915697ffbbc4` |
| MARIN.RFF   | `f4701a707a28ac6cf053890646f4c0f7` |
| SYMBOL.RFF  | `db84594fc82f99ecbf4e420e1e698721` |

Nothing about the base format changed - the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#rff-header-54-bytes) applies verbatim to all eight RIPtel files, including the [decoded glyph-outline encoding](../../2.0/techspecs/3.2-fastfont-fonts.md#glyph-record) (moveto/lineto/cubic-curveto opcode stream): the three added families were part of the decode's verification corpus and every one of their 224 glyph records parses strictly and renders correctly (e.g. BRUSH's script `e`).

## The three added families

RIPtel adds **BRUSH**, **EUREKA**, and **OAKLAND** (file dates April 17, 1997 - the carried five are dated April 18-19, 1997, the same conversion batch as the RIPterm 2.30 `.RFF` reformat). All three conform exactly to the documented `.RFF` header: signature bytes `10 00 02 02 2E 00 36 00 02 04 98 44` at 0x10, `&T` sentinel at 0x34, 224 glyphs from character 32, 1000 units/em, 10 style records of 46 bytes at 0x36, glyph section at 0x202 opening `01 00` + u16 pointer to 0x212. Per-family header metrics (offsets per the [2.0 header table](../../2.0/techspecs/3.2-fastfont-fonts.md#rff-header-54-bytes)):

| Family | Size | Trailer offset (u32@0x00) | Width metric | Ascender | Descender | bbox xmin | Base handle | Kerning pairs |
| --- | --: | --- | --: | --: | --: | --: | --- | --: |
| BRUSH.RFF | 87,155 | 0x1544D | 305 | 1184 | -767 | -159 | 0x03B4 | 7 |
| EUREKA.RFF | 70,789 | 0x1145B | 358 | 1093 | -952 | -36 | 0x0024 | 8 |
| OAKLAND.RFF | 64,213 | 0xFA7F | 250 | 1249 | -894 | -127 | 0x0017 | 19 |

(Sample kerning pairs - BRUSH: `FL` -61, `GL` -76, `PL` -76, `ZA` -45, `gb` -91, `gd` -51, `gh` -96; EUREKA: `AV` -86, `Av` -96, `VA` -76, `yd` -86 …; OAKLAND: `VA` -137, `WA` -107, `AV` -102, `yd` -122 … - all in 1/1000 em, read at each file's trailer offset.)

BRUSH's trailer offset exceeds 16 bits (0x1544D) - direct confirmation of the 2.0 page's observation that widening the trailer offset from u16 to u32 was a motive for the `.FF1` → `.RFF` reformat: BRUSH could not have shipped as an `.FF1`.

### Style tables

Each added family carries the standard 10 records (base + Th/Cn/Wd/Ex at 85/75/125/150% + Hollow versions), same 46-byte record format, same engine-parameter block `XX 0F 05 F8 1E 14 00 00` with the hollow flag at XX. Decoded from BRUSH.RFF at 0x36 (EUREKA/OAKLAND identical in structure):

| #   | Handle | Flags | Scale % | Name       |
| --- | ------ | ----- | ------: | ---------- |
| 0   | 0x03B4 | 0x00  |     100 | `Brush`    |
| 1   | 0x03B3 | 0x01  |      85 | `Brush TH` |
| 2   | 0x03B2 | 0x02  |      75 | `Brush CN` |
| 3   | 0x03B1 | 0x04  |     125 | `Brush WD` |
| 4   | 0x03B0 | 0x08  |     150 | `Brush EX` |
| 5   | 0x03AF | 0x10  |     100 | `Brush HO` |
| 6   | 0x03AE | 0x11  |      85 | `Brush HT` |
| 7   | 0x03AD | 0x12  |      75 | `Brush HC` |
| 8   | 0x03AC | 0x14  |     125 | `Brush HW` |
| 9   | 0x03AB | 0x18  |     150 | `Brush HE` |

One telling difference: the added families spell the non-hollow style suffixes in **upper case** (`Brush TH`, `Eureka CN`, `Oakland WD`, `… EX`, `… HO`) where the carried five use title case (`Cobb Th`, `Marin Cn`, `… Wd`, `… Ex`, `… Ho`) - evidence of a different converter run, and proof that clients must match [RIP_EXTENDED_FONT_STYLE](../ripscrip/3.0-text-output-and-fonts.md#rip_extended_font_style) style names **case-insensitively** (the demo corpus already selects `marin`/`dixon`/`cobb` in lower case). EUREKA's and OAKLAND's handle sequences are ascending and non-contiguous (EUREKA 0x24, 0x25, 0x2D, 0x2E, 0x2F, 0x30, 0x31, 0x3B, 0x3D, 0x3E; OAKLAND 0x17, 0x87-0x8F) unlike the carried families' descending runs - the handles are engine-assigned and carry no cross-file meaning, exactly as the 2.0 page states.

### Trailer difference - no copyright section

The carried five end with `…[kerning record][separator B7 BC BA AB BE][COPR: + copyright text]` as documented (except SYMBOL, whose trailer offset is bogus and whose tail is truncated glyph data - a shipped Atech defect carried into RIPtel byte-identical, see the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#symbol-tail-corruption-shipped-defect)). The three added families end differently: the 5-byte separator comes **before** the kerning record (immediately preceding the trailer offset), the kerning record runs to exact end-of-file, and there is **no `COPR:` section at all** - no Atech copyright, no TeleGrafix copyright (verified: `COPR:` absent from all three files; BRUSH's kern record at 0x1544D is tag=1, totalLen=38 = 10 + 7×4, ending at 87,155 = EOF). The leaked PostScript tokens inside BRUSH ([research triage §1](../../3.0/research/riptel-binary-formats.md)) suggest these were converted from Type 1 sources by Atech's AllType converter in 1997, with the tool configured or versioned differently from the 1991-copyright batch.

## `atf.cfg` - the regenerated catalog

RIPtel's `FONTS/atf.cfg` (4,470 bytes) uses the same scheme as the RIPterm 2.30 `ATF.CFG` (684 bytes) documented on the [2.0 page](../../2.0/techspecs/3.2-fastfont-fonts.md#atfcfg---the-engines-font-catalog-cache), but where the RIPterm 2.30 file is the stale FF1-era cache carried forward, RIPtel's is **freshly generated against the eight shipped `.RFF` files**. Byte-verified layout (both generations):

```text
0x00  u16  differs per file: 0x218E (RIPterm 2.30), 0x2654 (RIPtel) - meaning unverified
           (not a constant magic; not a simple byte-sum checksum of the content)
0x02  u16  fileCount     (RIPterm 2.30: 5; RIPtel: 8)
0x04  u16  totalStyles   (RIPterm 2.30: 6; RIPtel: 80)
0x06  u32  0
0x0A  fileCount × 78-byte entries:
        char[14]  filename, NUL-padded ("BRUSH.RFF" … "SYMBOL.RFF", alphabetical)
        u16       index of this font's first record in the style list
                  (RIPtel: 0, 10, 20, … 70; RIPterm 2.30: 0, 1, 3, 4, 5)
        u32       0
        byte[54]  verbatim copy of the font file's 0x00-0x35 header
        byte[4]   zero padding
then, at fileSize - 48 × totalStyles  (= 0x0A + 78 × fileCount - 4; RIPtel 0x276, RIPterm 2.30 0x18C):
      totalStyles × { u16 fileIndex, 46-byte style record }
        fileIndex = 0-based index of the owning file entry
        style record = the 46-byte format from the .RFF files, carrying the true
        engine handle from the source file; name padding is uninitialized memory
      … ending exactly at end-of-file (no trailing bytes)
```

The style-pair area's start overlaps the last file entry's zero padding by two bytes - the first pair's `fileIndex` is 0, indistinguishable from padding, which is why earlier decodes framed the records at the wrong offset (the [2.0 page's layout block](../../2.0/techspecs/3.2-fastfont-fonts.md#atfcfg---the-engines-font-catalog-cache) was corrected to this framing alongside this page).

Verified against the RIPtel file: all 8 header copies are byte-identical to the shipped files' first 54 bytes; all 80 records carry the exact handles, flags, scales, and names from the eight `.RFF` style tables (including the upper-case suffixes of the three added families); the `fileIndex` words read 0×10, 1×10, … 7×10 in file order. The catalog also preserves the DEFAULT quirk documented on the 2.0 page: record 24 ("DEFAULT Ex") has scale 0x8C = **140%** where every other family's Ex is 150% - the FF1-conversion fingerprint, carried through RIPtel's regenerated cache.

Delta summary vs the RIPterm 2.30 file: `fileCount` 5 → 8, `totalStyles` 6 → 80 (the RIPterm 2.30 cache lists only the base faces its `.FF1` sources contained, plus "DEFAULT EX"; RIPtel's lists all 10 synthesized styles per family), filenames `*.FF1` → `*.RFF`, cached header copies FF1-format → RFF-format (with `&T` sentinel), and the u16 at 0x00 changes value. The file is machine-written by the client and safe to regenerate, as before.
