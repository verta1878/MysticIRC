## Introduction

As system operators of many bulletin board systems, we've often wished for some form of Graphical User Interface for our boards. Like most Sysops, we've come across many solutions. But they all seemed to fall short in one way or another: inadequate for THIS system, incomplete, difficult to implement, too complex, or lacking in graphics development tools. In short, we became frustrated.

So, we decided to write our own graphical script language.

RIPscrip stands for "Remote Imaging Protocol script" language. This graphical language is our answer to the graphics needs of the BBS community and has serious tools for implementation and practical use.

## Definition

RIPscrip is a text based Script language for displaying online graphics. The script language conforms to 7-bit ASCII, avoiding the use of Extended ASCII characters. This allows transmission over X.25 networks and other carriers that do not support full 8-bit binary transfers easily. RIPscrip allows RIPscrip graphical statements to be mixed with printable ASCII text and [de facto standard] ANSI/VT-100 directives. RIPscrip can dynamically determine what is graphics and what is text and display them appropriately in separate windows (a graphics window and a text window). And if you must have your own proprietary commands, RIPscrip has room for that too.

## How Does RIPscrip Work?

RIPscrip uses a flexible, and very efficient script language for its graphical statements. Its efficiency stems from its compactness and developmental planning. It is entirely Object Oriented instead of Raster Oriented for efficient transmission of data and powerful editing capabilities (using RIPaint or RIPdraw for example). The language is open ended enough so that literally billions of different graphics commands can be implemented as needed. RIPscrip is not a proprietary protocol standard, otherwise you wouldn't be reading this document. It is open to suggestion from the rest of the world.

Earlier Graphical Script Languages (Avatar and Skypix among others), utilize special command characters to indicate which graphics command is to be executed. This allowed for their use on systems that are limited to ASCII printable text. Traditional script languages use English words to accomplish things (eg, "BOX 0,0 100,50"). This kind of thing is incredibly bulky, especially when you consider that pictures are usually not simple things, but comprised of hundreds or thousands of individual graphical operations (eg, lines, circles, curves, text, etc.). With this in mind, a human-readable script language was completely inappropriate for the relatively limited bandwidth of conventional modems.

So, one of our main strategies for this language was to make it as efficient as possible without going completely binary. This allows the immediate installation of the protocol onto any ASCII text-based host system -- because the language consists entirely of ASCII printable characters. We justify the unreadability of the language by pointing out the limitations of today's modems and phone lines -- the language must be compact.

### Revision 2.A4

_Added in RIPscrip v2.A4._

- Changed some of the parameters for user defined [text variables](5.1-text-variables.md). Specifically, we removed "DATE" and "DECIMAL", renamed "NAME" to "TONAME", and added "TOLOWER" and "TOUPPER". In addition, we clearly defined that two parameters are allowed for this variable - a mode parameter and a conversion parameter.

- Removed justify values 2-3 from the RIP_REGION_TEXT command.

- Reformatted this document - giving it section numbers, a table of contents, and better diagrams. This should make printing out the specification and working with a printed copy much easier for everyone! This was done due to popular demand.

- Added two new commands for switching (they weren't in the previous specs):

  - RIP_SWITCH_BUTTON_STYLE
  - RIP_SWITCH_ENVIRONMENT

- Removed the `<slot>` parameter from the RIP_BUTTON_STYLE command. This command should redefine the current button style - allowing it to directly manipulate specific button style entries goes against the symmetry of the [data table](7.1-data-tables.md) system and the rest of RIPscrip's commands that work with them.

- Order of operation of resident query expressions has been clearly defined.

- Removed the `<slot>` parameter from the RIP_BUTTON command. This was changed to a reserved parameter. See the previous item for a description of why we did this.

- The parameters of the RIP_LOAD_BITMAP command have been altered. Specifically, the `<duplicate>`, `<palette>` and `<dither>` parameters were removed and moved into a single `<flags>` parameter. Additionally, a new flag was added at the same time for "transparency color". Also a new parameter was added called `<trans_color>` which specifies which color is to be transparent in a BMP file. The reserved parameter was increased to 4 bytes in size after all is said and done to give future grown potential.

- Re-documented color palette independence and situations relating to color palettes, and color palette mapping.

- Renamed VIEWX0, VIEWY0, VIEWX1, VIEWY1, VIEWX and VIEWY text variables to PORTX0, PORTY0, PORTX1, PORTY1, PORTW, and PORTH respectively.

- Added new text variables:

  - `$SGS$` ... Save graphics style
  - `$RGS$` ... Restore graphics style
  - `$SBS$` ... Save button style
  - `$RBS$` ... Restore button style
  - `$OFFSCREEN$` ... Determine offscreen pixel data
  - `$BACKSTAT$` ... Get status of backup area
  - `$ISEXTWIN$` ... Is a text window an extended text window?

- Renamed the `$SWITCH$` variable to `$CUR$` and enhanced its capabilities.

- Enhanced the `$RESET$` text variable definition.

- Removed the following text variables:

  - `$CLIP2CLIPOK$`
  - `$CLIPSAVEOK$`
  - `$STACKPOS$`
  - `$STACKCLEAR$`

- Added syntax diagrams for every text variable definition to make the possible parameters much easier to determine.

- Completely redesigned the `$INUSE$`, `$PROT$`, `$UNPROT$` and `$ISPROT$` text variables. The new variations are much simpler in nature and less cumbersome to work with.

- Removed all references to the "drawing coordinate frame"

- Documented the RIP_EXTENDED_TEXT_WINDOW command for resolution independent text windows.

- Revised the text variable system for the extended text window definition.

- Revised the RIP_KILL_ENCLOSED_MOUSE_FIELDS command to work a bit more efficiently.

- Removed the `$TEXTQUERY$` and `$VIEWQUERY$` text variables. They were redundant, and not sufficient to deal with resolution independent text windows, and viewports were simply redundant so the command wasn't necessary.

- Revised the definitions of the following text variables:

  - `$TWH$`, `$TWW$`, `$TWHOME$`, `$TWGOTO$`, `$TWERASEEOL$`, `$TWX0$`, `$TWY0$`, `$TWX1$`
  - `$TWY1$`, `$TWIN$`, `$CURX$`, `$CURY$`, `$CURSOR$`, `$CON$`, `$COFF$`, `$TWFONT$`

- Revised the keywords for some text variables that used the keyword "VIDEO" to indicate hardware device pixel coordinates instead of world coordinate pixels. These new keywords are now "DEVICE" instead for future extensibility with other display environments (eg, hardcopy, etc).

- Enhanced the documentation of "filled regions" to encompass filled polygons and curved surfaces - now these situations are clearly documented.

- Revised diagrams to be more understandable throughout the specification.

- Revised and enhanced the `$RESET$` text variable to accomodate more situations which were overlooked in its original definition.

- Documented exactly what gets saved in each [data backup area](7.2-data-backup-areas.md).

- Text windows and viewports that used to be referred to as "disabled" or "enable" are now using the new terminology of "deactivated" and "activated". This is to help distinguish between the concept of a text window or viewport that is "defined", as opposed to "active", as opposed to "current".

- Completely re-wrote the documentation on data tables and data backup areas to be clearer on the concepts involved and how "protection" works with data tables, and data backup areas. The data save stack and data save slot systems have been completley revised to be more "generic" and easier to implement on a target RIPscrip system. Base save areas can no longer be protected.

- Added a new graphical file format to the "image style" command. RIPscrip 2.0 now supports GIF (Graphics Interchange Format) files in addition to JPEG files. This was added due to popular demand because JPEG doesn't handle line art or fine-detail graphics anywhere near as well as GIF does both in terms of size, and quality. Also, GIF supports interleaved images which provide the user with nearly "immediate gratification" when an interleaved image is being displayed.

- Added another protocol to the list of protocols supported in the RIP_ENTER_BLOCK_MODE command. It is Super Kermit and it is assigned protocol #9 for block mode. The `$IFS$` protocol keyword for this protocol is "SUPERKERMIT".

- Removed the `$TERMNAME$`, `$TERMMFG$` and `$TERMVER$` text variables. Renamed the `$TERMDATA$` variable to `$TERMINFO$` and gave it parameters to cover the removal of the other three variables. This makes the vendor-specific text variables more generic and flexible in nature.

- Altered the multi-lingual support definitions in the spec. Before, we were identifying languages by the three character codes used to represent countries in the Olympics (USA, JAP, SPN, etc). Since many countries have many different languages, we are changing our strategy to a new coding scheme designed to explicitly identify the language, not the country that the user wants.

- The `$FEATURE$` text variable has been renamed to `$OPTION$` to more closely identify its purpose - to enable or disable specific system options.

- The `$IFS$` (is feature supported) text variable has been enhanced to work with the concept of "categories". This makes it so the host can query back pieces of information about specific topics (eg, "what protocols are supported", "what image formats are supported", etc).

_Added in RIPscrip v2.A3._

- Added the RIP_SWITCH_PALETTE command to switch from one palette slot entry to another.

- Added the RIP_FILE_DELETE command to remove unneeded JPEG or WAVE files off the user's hard disk so that they don't clutter things up when they're no longer needed.

- Added the RIP_ROUNDED_RECT and RIP_FILLED_ROUNDED_RECT commands to make rounded rectangles.

- Added the RIP_ROUNDED_RECT and RIP_FILLED_ROUNDED_RECT commands to make rectangles with rounded corners.

- Added the new port-based definitions for creating and working with on-screen and off-screen drawable areas. This technology upgrades the previous clipboard technology, and gives RIPscrip the ability to be able to draw to offscreen bitmaps. The new port-related commands are: [RIP_DEFINE_PORT](7.0-drawing-ports.md#rip_define_port), [RIP_SWITCH_PORT](7.0-drawing-ports.md#rip_switch_port), RIP_DELETE_PORT, [RIP_PORT_COPY](7.0-drawing-ports.md#rip_port_copy), and RIP_PORT_WRITE.

- RIP_SWITCH_TEXT_WINDOW had it's command character changed to be compatible with the new port commands.

- RIP_SWITCH_VIEWPORT had it's command character changed to be compatible with the new port commands.

- Added the RIP_PLAY_AUDIO command to playback a WAVE file.

- Removed the RIP_SCROLLER and the Form related text variables. This was necessary to get RIPscrip 2.0 out the door. These commands and a couple others (eg, RIP_ANIMATE, etc) will probably work their way into a future version of the specification.

### Revision 2.A2

_Added in RIPscrip v2.A2._

- Documented standard for setting and determining foreign language support.

- Added two new level 0 commands for creating groups of RIPscrip commands. These new commands are RIP_GROUP_BEGIN and RIP_GROUP_END. These are designed for a paint program to be able to group a number of RIPscrip commands and have them be treated as one object for the purpose of editing and moving. The terminal program just ignores these commands.

- Added a new `<no_border>` parameter to the RIP_FILL_STYLE command. This new parm lets RIPscrip draw filled objects without a border. This was accomplished by splitting the two byte `<pattern>` parameter into two one-byte parameters. This makes the new version of the command backwards compatible.

- Added RIP_FILLED_RECTANGLE command to complement the new `<no_border>` parameter of the RIP_FILL_STYLE command. RIP_BAR could not be updated because by default it has no border, and for backwards compatibility, the border would have to be on by default. Therefore, the new filled rectangle command.

- RIP_EXTENDED_FONT has been renamed RIP_EXTENDED_FONT_STYLE, and also expended for furture use so that someday font rotation can be expressed in 1/10's of degrees, and four reserved bytes were added just in case!

- Added RIP_POLY_BEZIER_LINE so that you can create a poly-bezier that does not have it's endpoints connected.

- Added RIP_FILLED_POLY_BEZIER so that you can create a filled poly-bezier object.

- Added RIP_FILLED_CIRCLE for a two-byte shorter filled circle than you can get using RIP_FILLED_OVAL.

- RIP_FILL_POLYGON was renamed to RIP_FILLED_POLYGON for consistency with the naming of other filled objects.

- Changed all icon references to the new icon, hot icon, and icon mask extensions (.ICN is now .BMP, .HIC is now .BMH, and .MSK is now .BMM)

- Added `<scale>` parameter to the RIP_LOAD_ICON command

- Documented rename of RIP_COPY_REGION to RIP_SCROLL

- RIP_POLY_BEZIER added in v2.A1

- RIP_COPY_BLIT added in v2.A1

- LOAD_BITMAP added in v2.A1

- Made corrections to the spec so that all the commands using clipboard slots specify how the slots are being used in the command set.

### Revision 2.A1

_Added in RIPscrip v2.A1._

- Added the ability to embed raw UU-Encoded data blocks inside RIPscrip encoded files. This allows you to transmit bitmaps, sound files, and other raw generic binary data over 7-bit ASCII text connections (like Internet, CompuServe, etc).

- Added some extra text variables for the purpose of extended vendor determination. Variables for determining the name of the manufacturer, name of the terminal program, actual version number of the terminal, and arbitrary vendor specific data have been supplied for the most flexibility. This method of determining vendor information is more generic and easier to work with than the vendor-codes used in the `$RIPVER$` text variable and the Query RIPscrip version ANSI command. In effect, the old method of determining vendor codes is obsolete.

- Added a new command for the creation and manipulation of scroller-type user interface objects. The reason this was added was due to popular demand. The command for this new object is RIP_SCROLLER. Using this command really involves some custom programming on the host system to process the selections of a scroller. We added this so that there's a standardized way of performing scroller operations in RIPscrip.

- Added the ability to refresh (redraw) any buttons that exist in a particular button style slot number. This lets you draw a bunch of buttons, alter the button style, then refresh the buttons thus altering their appearance (possibly highlighting all buttons in a group by changing their colors, etc).

- Added a new command (RIP_SET_REFRESH) which allows the host to define a refresh sequence that, when transmitted, will instruct the host to refresh (redisplay) the current screen. This is defined as a host definable sequence because every host may be different in the ways it refreshes screens and menus, and even different sub-sections of a host may use different refresh methods. Also, text variables for disabling refresh expressions and to force a refresh operation have been added to round out the refresh feature.

- Added a RIP_HEADER command which is used to both identify the revision of RIPscrip code that follows and also to allow for widespread flexibility in performing reset operations at the beginning of scenes (above and beyond the RIP_RESET_WINDOWS) command.

- Extended the specification where simple graphical primitives are concerned. In 1.xx versions of RIPscrip, raster operations for simple graphics primitives were limited to COPY and XOR modes. XOR was only available for simple line based primitives, not for curves like circles, ovals, and various pie slices. In addition, filled-in areas were not qualified for XOR operations. In RIPscrip 2.0, these limitations are being lifted. XOR applies to all primitives. In addition, line patterns and thicknesses are also allowed for the various primitives. Thickness limitations are no longer constrained to 1 pixel or 3 pixel thicknesses either. Bitmap operations offered raster operations of COPY, XOR, NOT, OR and AND. In RIPscrip 2.0, these operations are available for all primitives now.

- Added an extended font system to the specification. This provides for the original font systems covering pre-defined font sizes for the default bit-mapped font and simple vector fonts. This new command provides the ability to draw text in high qualith outline fonts like TrueType (tm). See RIP_EXTENDED_FONT_STYLE for further details on this command.

- Added a "local audio playback" text variable command. This is a variant on the local RIPscrip file playback command. Since you cannot be certain solely from a filename or a file extension if the file is truly a sound file, we have introduced this command to perform sound playback from within host commands or query expressions.

  **NOTE:** Formal sound file and music file formats have not been established yet for RIPscrip 2.0. They will be shortly. This command was added into the spec because its format isn't limited to whatever format is finally chosen.

- Added a "local bitmap playback" text variable command so that you can place icons on the screen from within a host command.

- Added a "local image playback" text variable command so that you can add photo-quality compressed images onto the screen from within a host command (eg, JPEG files).

- Added rule #16 which defines exactly what should be done if a RIPscrip command has too much information or too little.

- Documented what should happen if multiple viewports overlap or if text windows overlap, or viewports and text windows overlap.

- Expanded the pop-up picklist feature to support up to 64 individual picklist entries instead of the previously defined maximum limit of 20.

- Added a RIP_SET_MOUSE_CURSOR command which allows you to alter the currently defined mouse cursor style. This lets you change the mouse cursor to something like an hourglass, a pointer, cross-hairs, etc.

- Added a new command, RIP_BACK_COLOR. This command affects the fill operations. When you set the fill style or custom user-defined fill pattern, you specify the foreground color for fill operations. Use this command to set a background color for the fills so you can do two-toned fill operations. This color may or may not be used for the drawing of dashed lines for the odd-dash spaces (see RIP_LINE_STYLE).

- The RIP_LINE_STYLE command has been altered to support the ability to turn on or off background color drawing for odd dash sequences. Also, the line thickness parameter of this command has been generalized so that it can support any arbitrary line thickness other than 1 or 3 pixel wide lines.

- Added a RIP_SET_COORDINATE_SIZE command which allows the alteration of X/Y parameter byte widths. By default, all X or Y coordinates are 2-byte MegaNums (or UltraNums in 2.0). For situations where a world coordinate system gets very large (greater than 4096 wide), then you will need to increase the size of the coordinates. This command allows you to make these parameters say, 3 bytes wide, or 4 bytes wide. In practice, this command probably won't be used much - not until we start seeing very high resolution video devices.

- Extensive enhancements have been added to text variables. Specifically, text variable "parameters" have been allowed to alter the functionality of text variables. This applies to built-in text variables and to user-defined text variables.

- Data Entry Form generation has been added to one of the types of host command data types. This is a special case of data text variables.

- All SAVE and RESTORE type text variables now adhere to three different mechanisms (up to 10 slots for saving, a slot-less save area and push/pop stack like operations). In prior releases each type of save/restore had different mechanisms. Now, a uniform methodology has been added which is fully backward compatible and totally identical in nature for all of the various save/restore data types (screen, mouse fields, text windows and clipboard slots).

- Added a new mechanism to the save/restore areas that allows slot-less and slot-based save regions to be protected. A protected slot cannot be erased, copied over or modified by anything other than an unprotect operation or a hard reset operation. Push and pop operations skip over protected slots. Also, the ability to move data from slot-less areas to particular slots, and vice versa have been added.

- Added protection facilities to viewport slots, text window slots, clipboard slots, graphical style slots and to button style slots. This allows you to protect an entry so that nothing can overwrite or delete it short of a hard reset operation or an unprotect command.

- Button styles now have button style slots - up to 36 separate button style slots can be defined simultaneously. This can reduce data transmission for heavy button applications.

- An enhanced load icon command has been added which supports scaling and dithering. This is intended to replace the older RIP_LOAD_ICON command because it does the same thing, and much more!

- Formally defined what a "clipboard slot" is under 2.0 _(v2.A2)_

- Officially defined the file format specification for 2.0 icon bitmap files. The official file format is BMP files (device independent bitmaps). See the [end of this document](6.1-content-file-roles.md) for a technical file format specification.

- Altered the default palette in 256 color modes. The new palette is a uniform distribution of Red, Green and Blue for purposes of image reproduction. A uniform distribution of RGB values provides colors in all parts of the spectrum for as accurate image display as possible without color palette changes.

- Added another syntax rule (#14) to the language definition. This new rule covers the inability in previous releases to use special command characters in text parameters in the language (eg, "$", "[", etc).

- Added the ability to embed comments inside a RIPscrip file. This is syntax rule #15.

- Cropping rectangles for the RIP_IMAGE_STYLE command have been eliminated. The complexity of cropping sub-area of the image hamper the open development of RIPscrip for v2.0. This may be changed in future versions.

- Dynamic image pan/zoom operations have been eliminated from this revision. Since cropping rectangles are no longer part of the specification, pan and zoom operations aren't really necessary.

- TIFF files have been removed from the 2.0 specification for image file displaying. We will be using JPEG and BMP files exclusively for all bitmap image reproductions.

## Differences from 1.54 and 2.00 Formats

_Added in RIPscrip v2.A1._

In previous versions of RIPscrip, we used a simple Icon file format for its disk based bitmap icons. In 2.00 we introduce a newer, more superior file format (the BMP/DIB file format). This is a device independent bitmap format that accomodates monochrome images, 16 color images, 256 color images and 24 bit images. There is no real form of compression internally but the capability for compression exists for future expandability. The reason for changing file formats was a very important one because the older format did not have the built-in facilities for resolution and color palette independence. This new format does. We chose the BMP file format because it is truly a device independent bitmap format. For details about the actual file format specification, see the [end of this document](6.1-content-file-roles.md).

Any place in the RIPscrip specification that used to refer to .ICN files now will use .BMP files. Any 2.0 RIPscrip software should be intelligent with this change. If it sees a .ICN file it should realize that it is the older format and translate the file to .BMP instead. How those packages deal with .ICN files may vary from vendor to vendor but the recommended solution would be to convert the older .ICN to a 16 color .BMP file "on the fly". Reallistically, when a 2.0 package is installed, some conversion utility should be run on the icon(s) at boot-up time to convert all the existing files to the new format. Files that are received via RIP_ENTER_BLOCK_MODE should do dynamic file format conversion to the new format. The older .ICN file format will no longer be supported in 2.0 and later revisions.

## Backward Compatibility Topics

With this release, XOR write modes now apply to all graphical primitives (also fill patterns). Overall this shouldn't pose any problems for 99% of all RIPscrip 1.54 files out there, but there might be a few that are affected - if in RIPaint, you enable XOR write mode and do a couple lines and rectangles, then do a circle or filled rectangle, the circle or filled rectangle will be drawn in COPY mode even though XOR mode is active. In a 2.0 terminal, this would cause the circles and filled in areas to be XOR'ed as well. In this regard, 2.0 is not 100.0% fully backward compatible. _(v2.A1)_

Also with this release, the world coordinate/resolution independent aspect of the language handles filled-in areas a bit differently (see the [world coordinate system section](1.2-math-and-coordinates.md) below). Filled-rectangles don't fill all the way to the right or bottom borders of the rectangle - they are inset by one pixel from the right and up one line from the bottom. The reasons for this are described in the world coordinate section of this document. This can cause one pixel gaps in 1.54 files that wouldn't happen in 2.0 related files. _(v2.A1)_

With v2.A3 of the specification, we have introduced a system of graphical ports, or [drawing ports](7.0-drawing-ports.md). These drawing ports are areas where actual drawing takes place. In 1.54 and prior versions, any graphics that are drawn (eg, lines, circles, etc) are drawn to the screen (the screen port). Under 2.0 you can define multiple drawing ports which may or may not be on the screen (eg, screen ports, or offscreen "clipboard" ports). Each drawing port can have one viewport associated with it, allowing you to modify the sub-region inside the port that drawn objects will be "clipped to" (a clipping rectangle). The screen is always port #0 and is formally known as the default screen port. Under 1.54 you were allowed to have an offscreen bitmap area known as the clipboard. Under 2.0, the clipboard is simply an offscreen "clipboard" port. You may switch to any defined port and subsequent drawing operations will apply to that port instead of the screen (unless the new port is a screen port). _(v2.A3)_

The older RIPscrip commands that deal with the clipboard are in essence, obsolete. When they are instructed to work with the clipboard, they work with the first offscreen "clipboard" port that they find. Some newer commands have been included, which are more powerful, that allow you to specifically designate a given port number to work with. You are allowed up to 36 separate graphical drawing ports, which port #0 is the screen and cannot be deleted. _(v2.A3)_

RIPscrip 1.x filled objects (filled ovals, filled polygons, etc) had a border around the object. These borders were drawn using the current drawing color, line thickness, and in some cases, line pattern. Under 2.0, these borders can be turned off (they are on by default). This allows you to draw filled circles in a particular fill pattern without any borders. We default to keeping borders on for backward compatibility reasons. If you don't want borders, you will have to shut them off. _(v2.A3)_
