# 6.1 Content File Roles

[◀ Prev: 6.0 Writing 2.x .RIP Files](6.0-writing-rip-files.md) · [Contents](README.md) · [Next: 6.2 Asset Delivery & Storage ▶](6.2-asset-delivery-and-storage.md)

The content files of the 2.x generation - what each host-deliverable file type is for, how commands reference them, and the shape of the new BMP icon format at the concept level.

_The 1.54 roles (`.ICN`/`.MSK`/`.HIC`) are in [6.1 of the v1.54 reference](../../1.54/ripscrip/6.1-content-file-roles.md)._

## File roles

| Extension | Role |
| --- | --- |
| `.RIP` | A stored RIPscrip command stream (a scene) - see [6.0 Writing 2.x .RIP Files](6.0-writing-rip-files.md); host-deliverable and locally replayable ([5.3](5.3-local-playback.md)) |
| `.BMP` | An [icon](../../glossary.md): a named Windows-format bitmap stamped by [RIP_LOAD_ICON](4.0-icons-and-bitmaps.md#rip_load_icon)/[RIP_LOAD_BITMAP](4.0-icons-and-bitmaps.md#rip_load_bitmap), written by [RIP_WRITE_ICON](4.0-icons-and-bitmaps.md#rip_write_icon)/[RIP_PORT_WRITE](7.0-drawing-ports.md#rip_port_write), or used as an icon-button face ([4.3 Buttons](4.3-buttons.md)) - [icon formats techspec](../techspecs/3.0-icon-formats.md) |
| `.BMH` | A [hot icon](../../glossary.md) ("hot bitmap"): the pressed/highlighted state image of an icon button - same base filename as the button's `.BMP`, loaded automatically when the Hot Icon flag is set ([4.3](4.3-buttons.md#rip_button_style)) |
| `.BMM` | An [icon mask](../../glossary.md): the AND-stamp companion raster for transparency ([4.0](4.0-icons-and-bitmaps.md#masks-and-transparency)) - defined by the spec's extension tables but no `.BMM` files are known to have shipped |
| `.JPG` | A photographic image, displayed scaled into the image area ([4.1 JPEG Images](4.1-jpeg-images.md)) - [JPEG techspec](../techspecs/3.1-jpeg-images.md) |
| `.GIF` | An image format added on paper in the ALPHA 4 draft _(v2.A4)_ for line art and interleaved display; no shipped 2.x-generation client decodes it - see the [JPEG techspec](../techspecs/3.1-jpeg-images.md) |
| `.WAV` | A digitized audio file, played in the background ([4.5 Audio Files](4.5-audio-files.md)) - [audio techspec](../techspecs/3.4-audio.md) |
| `.ICN` `.MSK` `.HIC` | The 1.54 icon family - still recognized by 2.x clients for backward compatibility; the spec recommends on-the-fly conversion of `.ICN` to 16-color `.BMP` ([1.0](1.0-introduction.md#differences-from-154-and-200-formats)) |

Commands reference these files by bare name - no path or sub-directory information is allowed. Default extensions are appended when omitted (`.BMP` for icon commands, `.RIP` for playback variables); an explicitly provided extension is used verbatim.

Fonts are **not** content files in this sense: the stroked, outline (FastFont) and MicroANSI terminal fonts are global client resources, never host-delivered per connection - see the [FastFont](../techspecs/3.2-fastfont-fonts.md) and [MicroANSI](../techspecs/3.3-microansi-fonts.md) techspecs.

## The icon file format (concept level)

_Added in RIPscrip v2.A1._

The 2.x icon format is the **Device Independent Bitmap** - in practice the Microsoft Windows BMP file. The older 1.54 icon format (the Borland `getimage()` buffer dump) was completely inadequate for resolution- and color-independent environments: it carried no color palette and no notion of pixel format. The DIB format accommodates monochrome, 16-color, 256-color and 24-bit images, and stores palette information in the file so that color approximation or dithering can make the image appear correct no matter what color environment the terminal runs in. The spec formally declares the compression field unused (no RLE) and notes the format was chosen precisely because it is a true device-independent standard rather than an invented one.

Content creators normally never touch the bytes - icons are produced in a paint program, or captured on the terminal itself via [RIP_GET_IMAGE](4.0-icons-and-bitmaps.md#rip_get_image) + [RIP_WRITE_ICON](4.0-icons-and-bitmaps.md#rip_write_icon). Implementers decoding or generating icon files should work from the [icon formats techspec](../techspecs/3.0-icon-formats.md), which carries the header/color-table/pixel-data layout of the spec's DIB definition and reconciles it against the full-BMP files the 2.x clients actually shipped and wrote.
