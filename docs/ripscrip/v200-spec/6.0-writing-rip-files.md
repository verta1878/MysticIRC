# 6.0 Writing 2.x .RIP Files

[◀ Prev: 5.5 File Transfer & Queries](5.5-file-transfer-and-queries.md) · [Contents](README.md) · [Next: 6.1 Content File Roles ▶](6.1-content-file-roles.md)

Authoring-level conventions for 2.x `.RIP` files: encoding and line endings, line length and continuation, comments and grouping, and the prologue/epilogue conventions observed in TeleGrafix's own shipped 2.x-generation scenes.

_The 1.54 authoring conventions this page extends are in [6.0 of the v1.54 reference](../../1.54/ripscrip/6.0-writing-rip-files.md)._

## What a .RIP file is

A `.RIP` file is not a distinct binary format: it is a captured RIPscrip command stream - exactly the bytes a host would transmit - stored as a DOS text file. Everything in [1.1 Protocol & Command Hierarchy](1.1-protocol-and-command-hierarchy.md) applies verbatim to file content. A file can be transmitted by a host, replayed locally via the `$>file$` playback variable ([5.3 Local File Playback](5.3-local-playback.md)), played back by [RIP_READ_SCENE](5.5-file-transfer-and-queries.md#rip_read_scene), or delivered and auto-played through [block mode](5.5-file-transfer-and-queries.md#rip_enter_block_mode).

## Encoding and line endings

- Line endings are CRLF (`0D 0A`), as in every DOS-era capture - all 37 surveyed shipped 2.x-generation scripts use CRLF exclusively. Line endings are **significant** to the parser, so `.RIP` files should be stored and transferred byte-exact - never re-wrapped or "normalized".
- Text content (RIP_TEXT strings, button labels, embedded raw text) is [CP437](../../glossary.md) - the code page of DOS-based BBS terminals and host software. There is no in-band encoding declaration. (The shipped demo footers even exploit this: byte `0xA8` renders as a © glyph through the Dixon outline font.)

## Line length and continuation

Syntax rule 5 allows any command or line to be split with a backslash (`\`) immediately before the line break. Authoring practice from TeleGrafix's own 2.x-generation files:

- Command lines keep an 80-column discipline - the longest command line in the shipped 2.x corpus is 78 bytes including its trailing `\`. Raw text lines do not honor that limit (a 104-byte flowed-text line ships in NEWS.RIP), and terminals accept arbitrarily long lines: wrap for tool compatibility, but don't rely on readers enforcing it.
- The split may land anywhere - mid-parameter, mid-number. Continuation is heavy production traffic, not an edge case: one shipped palette-fade file is 1,024 physical lines of which 960 are continuations. Continuation lines carry **no introducer** - they are bare argument bytes.
- Watch trailing backslashes: an **odd** count means continuation, an **even** count means escaped literal backslashes (syntax rule 13's `\\\` example). If you need a literal `\` at end-of-line, write `\\`; a continuation after a literal backslash needs `\\\`.
- Multi-command lines are the norm - the densest shipped lines carry 13 `|`-separated commands (`FRACTMTN.RIP` lines 42, 158 and 399), and a typical case is a scene load plus two delays: `!|*|1R00000000TUNNEL.RIP|3D008C|3D0060`.

## Escaping, comments and grouping

Inside text parameters, `\!` → literal `!`, `\|` → literal `|`, `\\` → literal `\`; host-command special characters (`$`, `[`, `]`, `(`) are quoted with a backslash where they could be misread as command sequences - syntax rules 11 and 14 in [1.1](1.1-protocol-and-command-hierarchy.md#ripscrip-protocol---syntax-and-general-structure). New at the file level in 2.x:

- **Comments** - `!|!comment text` embeds a comment anywhere in a file ([RIP_COMMENT](1.1-protocol-and-command-hierarchy.md#rip_comment), _(v2.A2)_); comments line-continue like any command.
- **Grouping** - `!|(` … `!|)` bundles commands into logical groups for paint programs ([RIP_GROUP_BEGIN](1.1-protocol-and-command-hierarchy.md#rip_group_begin)/[RIP_GROUP_END](1.1-protocol-and-command-hierarchy.md#rip_group_end), _(v2.A2)_); terminals ignore them, and groups are typically stripped before putting a file online.
- **UU-encoded data blocks** - a file (or stream) may embed raw binary content (bitmaps, sounds) behind a [RIP_BEGIN_UUENCODE_BLOCK](5.5-file-transfer-and-queries.md#rip_begin_uuencode_block) command _(v2.A1)_.

## Mixing ANSI and plain text

Lines that do not begin with an introducer pass through to the current [text window](1.4-terminal-ansi-view.md), so `.RIP` files freely intermix RIPscrip with ANSI sequences and plain text. 2.x adds a modal wrinkle observed in the shipped corpus: after a [RIP_BEGIN_TEXT](3.0-text-output-and-fonts.md#rip_begin_text) region definition, raw lines are flowed into the graphics-side text region until a command line ends the block (NEWS.RIP flows a whole newspaper article this way) - see the [stream conventions techspec](../techspecs/1.0-stream-conventions-delta.md#raw-text-and-modal-text-flow).

## The SOH reset opener

Syntax rule 12 allows Ctrl-A (SOH, byte `0x01`) or Ctrl-B (STX) to replace the `!` introducer. TeleGrafix's 2.2-era convention - visible in their own revision of SHADOW.RIP - is to open a standalone scene file with **`\x01|*`**: SOH plus [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) as the first bytes of the file. Half the shipped 2.x scripts open this way; SOH never appears anywhere else in them, and every subsequent line uses the classic `!|`. Files that are deliberately non-destructive (palette-cycle fragments, fades, full-screen repaints) omit the reset. _(Corpus observation - see the [techspec](../techspecs/1.0-stream-conventions-delta.md#the-soh-introducer---x01) for the byte-level survey.)_

## Scene prologue and epilogue conventions

TeleGrafix never specified how a 2.x `.RIP` file should begin or end, but their shipped scenes follow recognizable conventions:

- **Prologue** - two disjoint conventions are observed, and no shipped file uses both. (1) A reset opener (`\x01|*` or `!|*`): ten files pair it with `|1K` ([RIP_KILL_MOUSE_FIELDS](4.2-mouse-fields-and-pointer.md#rip_kill_mouse_fields)) so stale mouse fields cannot fire during the redraw - EAGLE, FOUND, FRACTMTN, HAWK, RACECAR, SAILBOAT, SHUTTLE, SPACSHUT, TUNNEL and WEATHER, usually as `|1K|*` but as `|*|1K` in EAGLE and HAWK - and five more open with the bare reset (DEMOFILE, N2_BUSI, N2_PHOTO, N2_TITLE, SHADOW). (2) Scenes needing a known numeric environment instead open with the setup block `J10|n2000|M08|fZKQO` as the literal first command and no reset at all - Base Math to MegaNums (shipped `J` opcode - see the [RIP_SET_BASE_MATH note](1.2-math-and-coordinates.md#rip_set_base_math)), 2-digit coordinates, color-mapping mode with 8-bit palette precision, and a 1280×960 [world frame](1.3-world-view-virtual-canvas.md#rip_set_world_frame) - used by EXAMPLE1-4 and NEWS. Alternatively a single [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) command declares the revision and performs any combination of resets - that is what it was designed for, though no shipped 2.x-generation script uses it.
- **State re-assertion** - authored 2.x-generation streams re-assert unchanged state constantly (background color, write mode, fonts); state is inherited from whatever ran before, so well-behaved scenes re-establish everything they depend on.
- **Epilogue** - 20 of the 36 shipped 2.3-era scenes end with `!|#|#|#` - three consecutive [RIP_NO_MORE](1.1-protocol-and-command-hierarchy.md#rip_no_more) commands, following the spec's advice to transmit three or more for noise immunity - with a final CRLF. The 16 exceptions are the fourteen `CYC*.RIP` icon-cycle frames and `FADEIN.RIP`/`FADEOUT.RIP`, which end without an explicit terminator.

## Naming and delivery

Files referenced from commands and playback variables use bare DOS-style names - no path or sub-directory information (commands that take filenames reject paths). Extensions may be omitted where a command documents a default (`.RIP` for playback variables, `.BMP` for icon commands). Where files live on the terminal and how a host delivers them is covered in [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md).
