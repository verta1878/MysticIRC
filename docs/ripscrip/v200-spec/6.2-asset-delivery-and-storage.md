# 6.2 Asset Delivery & Storage

[◀ Prev: 6.1 Content File Roles](6.1-content-file-roles.md) · [Contents](README.md) · [Next: 7.0 Drawing Ports ▶](7.0-drawing-ports.md)

How a host delivers content files to the terminal and where they land: the query-then-download workflow, the block-mode extension routing table, the per-host connection directory, and the file override lookup order.

_The 1.54 model this extends is [6.2 of the v1.54 reference](../../1.54/ripscrip/6.2-asset-delivery-and-storage.md)._

## The delivery workflow

A well-behaved host delivers assets in two steps:

1. **Staleness check** - [RIP_FILE_QUERY](5.5-file-transfer-and-queries.md#rip_file_query) asks whether a file already exists on the terminal's disk, and (modes 02-04) its size, date and time. The host compares the response against its own copy to decide whether a download is needed at all - avoiding re-sending files the terminal already has. Terminals that store audio in a translated local format must answer as if the WAVE original were on disk ([4.5](4.5-audio-files.md)).
2. **Download** - [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) auto-initiates a file transfer (Xmodem variants, Kermit, Super Kermit, Ymodem, Ymodem-G, or Zmodem with or without crash recovery) with a file-type code telling the terminal what it is receiving - `.RIP` scenes to display or store, generic files, icons, or images to display on arrival. Over 7-bit-only links, [RIP_BEGIN_UUENCODE_BLOCK](5.5-file-transfer-and-queries.md#rip_begin_uuencode_block) embeds the same content as UU-encoded text _(v2.A1)_.

Once delivered, the host uses the assets by name - stamping icons, displaying images, playing audio, replaying scenes - with no further transmission cost, from the command stream (chapter 4) or from host commands via the playback prefixes ([5.3](5.3-local-playback.md)).

Uploads work through the same block-mode command with mode 1; the user can be prompted to authorize them (Data Security), and an unauthorized upload is refused with ten CAN (Ctrl-X) characters.

Housekeeping: the [`$FILEDEL$`](5.1-text-variables.md#filedel) text variable lets the host delete files it created and no longer needs. The specification constrains it twice over: the target "must be a filename that the host created, or downloaded to the terminal via RIP_ENTER_BLOCK_MODE or by some other means", and "no form of wildcard information is processed, nor is path information - if present, it will be ignored". A host therefore names a bare file; the terminal resolves it. _(The v2.A3 revision notes also announce a `RIP_FILE_DELETE` command for this, but no entry for it exists in the ALPHA 4 draft and the capability shipped in variable form - see [Errata](errata.md#rip_file_delete-was-announced-never-specified).)_

> **Editor's note - implementation guidance, not specification.** The draft never states which directory `$FILEDEL$` resolves against. Two of its own rules settle it in practice: deletion is limited to files _the host created_, and the host cannot supply a path. Since host deliveries land in the connection directory when one is configured, the safe reading is that `$FILEDEL$` should delete from the **connection directory only** and leave the shared default `ICONS\` alone - files there may predate the session or belong to another host, and no host created them. This mirrors the lookup order in reverse: reads fall back from the connection directory to the shared default, but deletes should not. This is inference from the spec's constraints and the storage model above, not documented behavior; no shipping client has been examined to confirm it.

## Block-mode routing - the extension table

In the batch DYNAMIC file types, the terminal routes each received file by extension _(v2.A0)_:

| Extension | COMPOSITE DYNAMIC (type 4) | ACTIVE DYNAMIC (type 5) |
| --- | --- | --- |
| `RIP` | Store in proper directory | Store **and play back** locally |
| `BMP` | Place icon in proper directory | Place icon in proper directory |
| `BMH` | Place hot icon in proper directory | Place hot icon in proper directory |
| `BMM` | Place mask icon in proper directory | Place mask icon in proper directory |
| `JPG` | Store in proper directory | Store **and display** per image settings |
| `GIF` _(v2.A4)_ | Store in proper directory | Store **and display** per image settings |

Files with any other extension are placed in the appropriate host directory with no further processing - which is how `.WAV` audio arrives, since it is absent from the table. "Proper directory" always resolves through the connection-directory model below, never through the user's ordinary download directory.

## Where files land

Every 2.x media type flows through **one directory family** - there was never a separate audio, image, or scene directory:

- The **[default icon directory](../../glossary.md)** (`ICONS\` historically) houses the whole host-deliverable media family: both icon generations (`.BMP`/`.BMM`/`.BMH` and legacy `.ICN`/`.MSK`/`.HIC`), `.JPG` images, `.WAV` sounds, and `.RIP` scenes.
- Each dialing-directory entry can name a per-host sub-directory - the **System Dir**, the RIPterm 2.30 name for the [connection directory](../../glossary.md) (the 1.54 manual's DIR field) - auto-created on first use. When one is configured, any icon, RIPscrip, sound, or image files sent by the host are automatically placed there.
- **One-off manual dials get one too**: RIPterm 2.30's Manual Connect prompt asks for a phone number _and_ a System Directory for the session - an ad-hoc, discardable connection directory for hosts not in the dialing directory. Every session therefore has a connection-directory binding.
- **Fonts are the exception** - stroked, outline and terminal fonts are global client resources resolved only from the font store, never per connection.

## Lookup order ("file override")

When a command or playback variable references a file by name, the terminal searches the **connection directory first**, then falls back to the default `ICONS\` directory. The point of this two-level scheme is that same-named assets from different hosts do not collide: each host's `MENU.BMP` resolves to that host's own copy, while genuinely shared assets can live once in `ICONS\`. The RIPterm manuals call this behavior "[file override](../../glossary.md)".

Commands never carry path information - filenames are bare DOS-style names, and the terminal decides where they resolve. (Modern implementations should also treat lookups as case-insensitive, as the DOS originals inherently were - see the [connection directory model techspec](../techspecs/4.0-connection-directory-model-delta.md).)
