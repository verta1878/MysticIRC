# 9.0 Command Inventory Comparison

[◀ Prev: 2.0 Write Mode Numbering](2.0-write-modes.md) · [Contents](README.md) · [Next: Technical Specifications ▶](../techspecs/README.md)

_Opcode-by-opcode comparison of [RIPlib](https://github.com/BradHawthorne/riplib)'s command table (`docs/spec/10-appendices.md` §A.1, with `11-dll-deviations.md`) against the [3.0 command reference](../../3.0/ripscrip/9.0-command-reference.md) here. See the [tree README](../README.md) for how each side's evidence should be weighed._

The two inventories agree on the great majority of the language - the whole alphabetic Level 0 core, most of Level 1, and the port commands. The disagreements cluster tightly, and where this repository's side rests on TeleGrafix's own shipping scripts the evidence is unusually direct: the demo corpus is 116 files the RIPscrip 3.0 driver itself rendered, several of them carrying TeleGrafix's own inline comments naming the commands they demonstrate.

## First: three commands RIPlib already has and does not know it

RIPlib's §A.1 marks `|!`, `|(`, `|)` and `|1R` as _"RIPlib extensions beyond the published TeleGrafix tables"_ (`spec (11 §DEV.4)`). Three of the four are documented commands in the 3.x record:

| Opcode | RIPlib | This repository | Evidence here |
| --- | --- | --- | --- |
| `\|!` | COMMENT - consumed, no output | [RIP_COMMENT](../../3.0/ripscrip/9.0-command-reference.md) | Carried from 1.54 |
| `\|(` `\|)` | GROUP_BEGIN / GROUP_END - no-op markers | RIP_GROUP_BEGIN / RIP_GROUP_END | Carried from 1.54 |
| `\|1R` | READ_SCENE - queues a scene-file request | [RIP_READ_SCENE](../../3.0/ripscrip/5.5-file-transfer-and-queries.md#rip_read_scene) | 1.54 onward; "the subroutine call of the 3.x scene architecture" |

Behavior matches in every case - only the standing is wrong. These can simply be reclassified from extension to inherited, which is a small win: it removes four rows from RIPlib's deviation register at no cost. `|1V`, `|1X` and the backtick `` |` `` composite-icon command have no counterpart here and are genuine RIPlib additions.

## Conflicts

### Prologue-critical - `|J` and `|f`

**These two carry the highest impact of anything on this page.** Ninety of the 116 corpus files open with the same prologue:

```text
!|J10|n2000|M08|fZKQO
```

RIPlib assigns both `J` and `f` to other commands, so that line means something entirely different to it.

| Opcode | This repository | RIPlib | Disposition |
| --- | --- | --- | --- |
| `\|J` | [RIP_SET_BASE_MATH](../../3.0/ripscrip/1.2-math-and-coordinates.md#rip_set_base_math) - `base_math:2`, selects base 36 or 64 for every subsequent numeric field | `SAVE_ICON` - `!\|J<slot>`, 2 args | **Callable** |
| `\|f` | [RIP_SET_WORLD_FRAME](../../3.0/ripscrip/1.3-world-view-virtual-canvas.md#rip_set_world_frame) - `x_dim:XY y_dim:XY`, corpus standard `ZKQO` = 1280×960 | `FONT_ATTRIB` - `attrib:2 res:2` | **Callable** |

**On `|J`.** RIPlib's §11.2 Erratum 1 reports that the 2.00a4 draft assigns `b` to both RIP_SET_BASE_MATH and RIP_EXTENDED_TEXT_WINDOW, and that the DLL disambiguates by argument length (2 characters → base math, 15+ → extended text window). The collision in the draft is real and this repository records it too - but the shipping driver resolved it differently: base math moved to **`J`**, leaving `b` to the extended text window alone, which is also how SyncTERM's descriptor table has it. The corpus is unambiguous, and ONLINE.RIP annotates the opcode inline in TeleGrafix's own words - _"Set base math to MegaNums"_ next to `J10`. A terminal that reads `!|J10` as `SAVE_ICON` slot 1 skips the base-math declaration that governs how it parses the rest of every scene.

**On `|f`.** RIPlib's §11.1 lists RIP_WORLD_FRAME among commands _"defined in the v2.A4 specification but NOT present in the production v3.0 DLL"_, on the grounds that no implementation was found in the export table or function strings, and §11.4 adds that ports use plain viewport rectangles with no world-frame transformation. That may well be accurate about what the DLL _computes_ - but `|fZKQO` is on the wire in 90 of 116 shipping scenes, so the opcode is at minimum accepted and consumed. "Parsed but not acted on" is a category RIPlib documents extensively elsewhere (§DEAD.1 through §DEAD.8); world frame looks like another member of it rather than an absent command. Reassigning the letter to a different command is the part that does not follow, and it is what makes §A2G.3's font attributes ride on an opcode that shipping content already uses.

Both are resolvable against sources RIPlib holds: grep any RIPtel demo script for its first line, or check whether the DLL's dispatch table has entries at `'J'` and `'f'` at all.

### The 3.x punctuation block

This repository's 3.x reconstruction recovered a family of rotated-ellipse primitives and two other commands from the demo census. **Their names are not editorial guesses** - the six skewed-oval names come verbatim from TeleGrafix's comments in NEWCMDS.RIP, a demo script written to introduce them. RIPlib assigns the same eight letters to extended commands.

| Opcode | This repository | Corpus evidence | RIPlib |
| --- | --- | --- | --- |
| `\|&` | RIP_SKEWED_OVAL - rotated ellipse | 3.0 (corpus), name verbatim from NEWCMDS.RIP | `ICON_STYLE` |
| `\|-` | RIP_FILLED_SKEWED_OVAL | as above | `TEXT_XY_EXT` |
| `\|+` | RIP_SKEWED_OVAL_CHORD | as above | `SCROLL` |
| `\|[` | RIP_SKEWED_OVAL_PIE_SLICE | as above | `FILL_POLYGON_EXT` |
| `\|]` | RIP_SKEWED_OVAL_ARC | as above | `POLYLINE_EXT` |
| `\|_` | [RIP_FILLED_OVAL_CHORD](../../3.0/ripscrip/2.2-curves.md) - unrotated, angles before radii | 3.0 (corpus) | `DRAW_TO` |
| `\|;` | RIP_MARKER - stamp a scaled marker glyph | 3.0 (corpus), **361 uses** | `BUTTON_EXT` |
| `\|<` | RIP_POLY_POLYGON - multi-contour even-odd fill with holes | 3.0 (corpus) | `GET_IMAGE_EXT` |

**Disposition: callable for the six skewed-oval letters, strong for `;` and `<`.** A demo script whose author-written comments name the command it is invoking is about as direct as wire evidence gets, and these scripts shipped inside the same product as the DLL. RIPlib's names for this block are labeled "Extended Commands (v2.0+)" but do not appear in the 2.00 Alpha 4 draft as documented here, so their provenance is worth establishing - if they came from DLL string tables or dispatch analysis, both sides are describing something real and the question becomes which opcode each name actually sits at.

`RIP_MARKER` and `RIP_POLY_POLYGON` carry a (†) in the 3.x reference, meaning the _name_ is an editorial reconstruction; the opcode, arguments and rendered behavior are corpus-observed regardless.

### Palette versus pattern - `|D` and `|d`

| Opcode | This repository | RIPlib |
| --- | --- | --- |
| `\|D` | [RIP_SET_DRAWING_PALETTE](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_set_drawing_palette) - `num:2 start:2 bits:1 c1:4 … cn:4`, a block of 256-entry palette RGB values in UltraNums | `FILL_PATTERN_EXT` - 18 args, `!\|D<p0>..<p7><color>` |
| `\|d` | [RIP_ONE_DRAWING_PALETTE](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_one_drawing_palette) - `entry:2 bits:1 rgb_color:4` | `EXT_FONT_STYLE` - `fid attr size` |

Both are 2.A0 commands here, and `|D` is what the corpus uses to build its 256-color fade backgrounds - the dithered gradients that stand in for the gradient command neither the help inventory nor the corpus contains (see [3.2-riplib radial gradient](../../3.2-riplib/ripscrip/2.1-radial-gradient.md#relationship-to-the-telegrafix-record)). Note the shape of the mismatch: RIPlib has no drawing-palette command at all but does have `|20 SET_VGA_PALETTE`, which covers similar ground with different arguments. **Open** - worth checking which of the two forms the DLL's palette code actually parses.

For extended font style this repository has `|y`, with a 26-digit wire layout crib recovered from FONTS.RIP (`!|!sfFFFFZZOOSSCCBBCCWWRRRRRR`) that already predates 3.x - RIPterm Professional 2.0's SHADOW.RIP drives it the same way. RIPlib's `|d EXT_FONT_STYLE` takes three fields. These look like different commands rather than a naming dispute.

## Suggested resolution order

1. **`|W` write-mode numbering** - separate page, [2.0 Write Modes](2.0-write-modes.md). Highest impact, cheapest fix, evidence already agrees on both sides.
2. **`|J` and `|f`** - they govern how every corpus scene opens. One `grep` of any demo script settles the wire question.
3. **Reclassify `|!`, `|(`, `|)`, `|1R`** from RIPlib extensions to inherited commands. Zero behavioral change.
4. **Establish the provenance of RIPlib's punctuation block** (`&`, `-`, `+`, `[`, `]`, `_`, `;`, `<`). If those names came from DLL strings, both sides hold real evidence and the task is matching names to opcodes; if they were inferred, the corpus decides.
5. **`|K`** - filled rectangle versus kill-mouse-extended, on the same terms as item 4.
6. **The Level 1 and Level 2 letter swaps** - lower stakes, mostly resolvable by DLL dispatch-table inspection.

Items 2, 4 and 5 would likely all fall out of a single pass: dump the DLL's Level 0 dispatch table and compare it against the corpus opcode census. Either project can run one half of that.
