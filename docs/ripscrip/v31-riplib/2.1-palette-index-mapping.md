# 2.1 Palette Index Mapping (§A2G.6)

[◀ Prev: 2.0 Fill Patterns & FPU Rendering](2.0-fill-patterns-and-rendering.md) · [Contents](README.md)

_Delta against [Canvas, Clipping & Write Modes](../../1.54/techspecs/2.0-canvas-clipping-write-modes.md) and [Canvas, Palette & RGB](../../2.0/techspecs/2.0-canvas-palette-rgb.md). See the [tree README](../README.md) for standing and provenance._

A framebuffer-integration change, not a protocol one: where in an 8-bit indexed framebuffer the EGA 16-color palette physically lives. No command, argument or color number changes - `!|c0F` is still white.

## The problem it solves

RIPlib renders RIPscrip graphics and VT100/ANSI text into **one shared 256-entry indexed framebuffer**. The text side wants the xterm-256 palette, which occupies indices 0-239. The graphics side, writing EGA colors to hardware indices 0-15 as the era hardware did, lands on top of it - so [RIP_SET_PALETTE](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_set_palette) (`|Q`) or [RIP_ONE_PALETTE](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_one_palette) (`|a`) recolors the terminal text as a side effect. `A2G.6`

## The mapping

v3.1 relocates the EGA palette to the **top sixteen indices**:

```text
EGA color 0  → framebuffer value 240
EGA color 1  → framebuffer value 241
...
EGA color 15 → framebuffer value 255
```

Drawing commands go through `s->palette[color]` to convert an EGA index to a framebuffer value; the hardware palette at 240-255 holds the RGB565 values. `A2G.6` The resulting split:

| Indices | Owner                                    |
| ------- | ---------------------------------------- |
| 0-239   | xterm-256 colors - VT100/ANSI text       |
| 240-255 | EGA 16-color palette - RIPscrip graphics |

Palette save/restore (`rip_save_palette`, `rip_apply_palette`) snapshot and restore only 240-255, so switching between protocols does not disturb the text palette. `A2G.6`

## Why it is in this tree

The relocation is invisible on the wire - which is the point, and why it belongs in techspecs rather than the language pages. It is recorded here because §A2G.6 presents it as part of the v3.1 protocol revision, and because it shapes two things an implementer will notice.

**Sixteen colors, not 256.** RIPscrip 2.x/3.x defines a 256-entry drawing palette and direct-RGB modes ([2.0 canvas, palette & RGB](../../2.0/techspecs/2.0-canvas-palette-rgb.md); [RIP_SET_DRAWING_PALETTE](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_set_drawing_palette) writes 256-entry RGB blocks in UltraNums, and the 3.x corpus leans on it for the dithered 256-color fade backgrounds). A sixteen-slot window at the top of a shared framebuffer cannot hold that; RIPlib's own summary describes 256-color and direct-RGB support as approximated. This is a constraint of the embedded target rather than a claim about the language, but content written against the 256-color palette will not render as authored.

**It is a co-tenancy scheme, not a spec change.** The specification never says where EGA colors live physically - that was the video hardware's business, and [implementation.md](../../implementation.md) deliberately keeps this class of decision out of the language docs. Any implementation sharing one indexed surface between a terminal emulator and RIPscrip has to solve the same problem; a modern renderer with a separate graphics surface, or an RGBA canvas, does not have the problem at all and needs none of this.
