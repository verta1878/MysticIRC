# 2.0 Write Modes - AND and NOT (§A2G.1)

[◀ Prev: Contents](README.md) · [Contents](README.md) · [Next: 3.0 Text Direction & Font Attributes ▶](3.0-text-direction-and-font-attributes.md)

_Covers RIPlib §A2G.1. Delta against [RIP_WRITE_MODE in the 3.0 reference](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_write_mode); see the [tree README](../README.md) for standing and provenance._

RIPlib presents `AND` and `NOT` as write modes added to `|W` by v3.1, extending what it treats as a three-mode v1.54 baseline. `A2G.1`

**Neither is an addition against the record reconstructed in this repository.** Both have been documented `|W` modes since the 2.00 Alpha 1 revision, both appear in the RIPtel 3.1 help inventory, and AND is used in the shipping 3.x demo corpus for masking effects - the full `00`-`04` table is in the [3.0 entry](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_write_mode), evidenced by 2.00a4, the `RIP_WriteMode` help entry, 44 corpus uses across 35 files, and SyncTERM (`ripper.c:14062`).

So §A2G.1 documents no new capability. What v3.1 does carry is a **change to which numbers mean which operation**, and that is a baseline disagreement rather than an extension:

> **The mode-numbering conflict is documented in [3.0-riplib → 2.0 Write Mode Numbering](../../3.0-riplib/ripscrip/2.0-write-modes.md).** In short: RIPlib assigns `01` to OR and `03` to XOR, while the 1.54 specification, the 2.00a4 table, the corpus, SyncTERM and RIPlib's own DLL disassembly (`§DEAD.3`) all put XOR at `01` and OR at `02`. It is the highest-impact difference between the two projects, and it is not something §A2G.1 needs in order to work.

If the numbering is resolved in favor of the documented table, §A2G.1 reduces to nothing: modes `03` (AND) and `04` (NOT) already exist, and RIPlib's implementation of them - previously dead code in the DLL, per `§DEAD.3` - becomes a completeness fix rather than a protocol revision. That is a good outcome for both projects: one fewer extension to negotiate.

## The operations themselves

Where the two records agree on an operation's existence they agree on its meaning; the descriptions below are RIPlib's, and match the [3.0 entry](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_write_mode).

**AND** - `dst = dst & src`. A bitwise AND of the source color with the existing destination pixel, useful for masking: ANDing with a color that has only certain channel bits set preserves only those channels. RIPlib's worked example is in its native RGB332 framebuffer terms - white `0xFF` AND red `0xE0` = red `0xE0`. `A2G.1`

**NOT** - `dst = ~dst`. Bitwise inversion of the destination, ignoring the source color entirely; the draw color parameter is parsed but unused. Self-inverse - applying it twice restores the original. `A2G.1`

Both apply to every drawing operation - lines, rectangles, circles, fills, text, region copies. `A2G.1` That breadth is the substantive part of §A2G.1: `§DEAD.3` records that the DLL parsed and stored all five modes but implemented only three in its pixel-write paths, so AND and NOT were accepted and silently ignored. Making them render is worth doing under either numbering.

Wire format is unchanged: `!|W<mode:2>`.
