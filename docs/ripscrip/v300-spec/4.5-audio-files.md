# 4.5 Audio Files (WAV)

[◀ Prev: 4.4 Tone & Sound Generation](4.4-tone-and-sound-generation.md) · [Contents](README.md) · [Next: 5.0 Host Commands ▶](5.0-host-commands.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

Digitized audio files: Microsoft **WAVE** (`.WAV`) PCM audio, played in the background while graphics and command processing continue - triggered from the command stream with [RIP_PLAY_AUDIO](#rip_play_audio) or at the host-command layer with the `$)FILE.WAV$` playback prefix ([5.3 Local File Playback](5.3-local-playback.md#local-audio-playback---filewav)), and distinct from the terminal's own speaker-tone generation ([4.4 Tone & Sound Generation](4.4-tone-and-sound-generation.md)), which needs no files at all.

_The 2.0 record is [4.5 in the v2.0 reference](../../2.0/ripscrip/4.5-audio-files.md); the file-role view is [6.1 Content File Roles](6.1-content-file-roles.md#wav-audio); byte-level RIFF/PCM layout and playback semantics are in the [v2.0 audio techspec](../../2.0/techspecs/3.4-audio.md)._

> **Editor's note - provenance:** WAV audio is not a 3.x innovation. RIP_PLAY_AUDIO entered the 2.0 specification at ALPHA 3 ("Added the RIP_PLAY_AUDIO command to playback a WAVE file" - 2.00a4 changelog) and **shipped** in RIPterm Professional 2.0 (January 1995): its manual introduces "digitized sound, in the form of .WAV files" (RIPTERM.DOC §4.3) with an Audio Setup screen for 19 sound boards (Sound Blaster, Pro Audio Spectrum, Gravis, etc.) and a `-A` command-line switch to disable digitized audio (RIPTERM.DOC §2.3), and the install carries HMI "Sound Operating System" drivers and a `RIPTERM.WAV` - both preserved (see the [RIPterm 2.30 audio assets](../../2.0/assets/audio/README.md)). TeleGrafix's December 1995 "RIP-2 Internet Multimedia" press release advertised the same "digital WAV sound". Like several other "3.x" features, it belongs to the RIPterm 2.30 product era that 3.x inherits (see the [revision history](1.0-introduction.md#revision-history)).

## Audio (Sound & Music) Formats

_Added in RIPscrip v2.A4._

RIPscrip permits the support of digitized audio to be played in the background whild graphics and other operations are being performed. This includes playing sounds while graphical commands are being received from the host (without interruption).

The format of audio data used by RIPscrip is formally defined as straight audio data in the Microsoft WAVE file format. When dealing with host systems and downloading digitized audio data, or being told to play back audio data, RIPscrip will assume that you are working with WAVE files. For example, you might be told to playback a file named SOUND.WAV. If you are not internally supporting the actual WAVE format, but some other format, then you need to translate the name of the file to the correct name in your environment (if necessary) and perform the playback.

When dealing with the [RIP_FILE_QUERY](5.5-file-transfer-and-queries.md#rip_file_query) command, you need to be careful if you're not dealing with true WAVE files. The RIP_FILE_QUERY command is used to "detect" if a particular file is present on the target system and if so, if it is the right date/time and file size as the file on the host. The file on the host will be in WAVE format so if you're translating the files as they're received, you need to translate the RIP_FILE_QUERY information returned to the host so that it thinks that the file you have on your local hard disk is actually a WAVE file (ie, translate the file size to a WAVE equivalent). If the sizes and, or the time/date don't match, the host could download a new file to you (via the [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) command) thinking that your's is out of date.

If you receive a WAVE file via the RIP_ENTER_BLOCK_MODE command, or by some other meanss, and you're dealing with anther digitized audio file format, it is up to you to translate that WAVE file to your destination format. Consequently, if you are requested to send a WAVE file to the host system, and the host system is requesting a .WAV file, then you must translate your file to WAVE format before sending it.

A Microsoft WAVE file is actually a normal "Pulse Code Modulation" digitized audio file stored with a bit of header information to identify whether it is stereo, 16-bit, 8-bit, etc, and other pieces of critical information for the decoding of the data. See the "Microsoft Windows Programmer's Reference Guide" for more specific information on the internal format of WAVE files.

_Evidence: 2.00a4._

## RIP_PLAY_AUDIO

_Added in RIPscrip v2.A3._

_Play a local digitized audio file on the terminal_

|               |                  |
| ------------- | ---------------- |
| **Level**     | 1                |
| **Command**   | `w`              |
| **Arguments** | `res:4 filename` |

**Format:** `!|1w <res> <filename>` **Example:** `!|1w0000filename.wav`

**Attributes used:** none **Evidence:** 2.00a4 ([2.0 entry](../../2.0/ripscrip/4.5-audio-files.md#rip_play_audio)) · HLP (`RIP_PlayAudio`; the `$)FILE.WAV$` macro, `AUDIO=TRUE` in RIPscrip.ini, DLL export `RIP_AudioSupport`) - not observed in the RIPtel demo corpus, not in SyncTERM

This command will physically start a local .WAV file to play back on the user's remote terminal. The audio file must already exist in the user's hard disk in the same location as their bitmapped icons. If the file doesn't exist, then this command does nothing. If you specify the `<filename>` parameter as `$OFF$` then you will in effect be shutting off any currnetly running sound file. If a sound is already playing when this command is received, the older file that was playing will be terminated in place for the new file. You may use [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) to transfer audio files to the user's computer for subsequent playback.

NOTE: The `<res>` parameter is for future expansion. For compatibility with future relases of RIPscrip, it should be set to "0000".

The `$)FILE.WAV$` host-command prefix is not a separate audio system - it is the macro-layer way of invoking this same playback engine; the command-stream vs macro-layer comparison is in [5.3](5.3-local-playback.md#playback-prefixes-vs-dedicated-commands).

The 3.0 driver plainly supports the command - audio configuration, tone-command error strings, and the DLL entry points all appear in the HLP material - but the demo corpus ships no audio files and never issues it. Playback is effectively **single-channel**, fire-and-forget, last-command-wins: no evidence in any recovered source - spec, help strings, or corpus - shows mixing of simultaneous sounds or any way for the host to monitor playback status. _Evidence: 2.00a4; HLP - not observed in the RIPtel demo corpus._

## Stopping, resets, and capability negotiation

- **Stopping playback** - issue [RIP_PLAY_AUDIO](#rip_play_audio) with `$OFF$` as the filename, or the [`$RESET(SOUND)$`](5.1-text-variables.md#reset) text variable, which aborts any playing digitized sound immediately (the DLL string table names a dedicated `resetKeywordSOUND` handler). _Evidence: 2.00a4; HLP._
- **Reset interaction** - a [RIP_HEADER](1.1-protocol-and-command-hierarchy.md#rip_header) with flag 2048 ("clears and stops any playing sound/music") silences audio as part of a scene reset; the soft-reset flag combination includes it. A plain [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) does not mention audio - hosts that need silence on reset should use the header flags or `$RESET(SOUND)$`. During a [`$D(time)$`](5.1-text-variables.md#d) delay, sound-related activity continues while everything else pauses. The 3.0 engine additionally tracks audio as a headerable object class in its [scene header segments](7.1-data-tables.md#audio-new-in-3x). _Evidence: 2.00a4; HLP (header-segment error strings)._
- **Terminal-side switch** - the RIPtel installer creates the master toggle **`AUDIO=TRUE`** in the `[CONFIG]` section of `RIPscrip.ini`; the driver also exposes a `RIP_AudioSupport` client-API entry point. _Evidence: HLP._
- **Capability negotiation** - before relying on audio, query [`$IFS(WAV)$`](5.1-text-variables.md#ifs): the terminal answers `1` if it can play WAVE files, `0` if not. `$IFS(LIST, _AUDIO)$` lists every audio format the terminal supports. The `$IFS$` processor is present in the 3.0 DLL's variable table. _Evidence: 2.00a4; HLP._
- **Delivery and housekeeping** - hosts deliver `.WAV` files with [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) (or a UU-encoded block), check freshness with [RIP_FILE_QUERY](5.5-file-transfer-and-queries.md#rip_file_query), and clean up with [`$FILEDEL$`](5.1-text-variables.md#filedel); audio files live alongside the icon files in the [connection directory](../../glossary.md)/default-directory family - see [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md). _Evidence: 2.00a4; HLP._
