# 5.4 Pop-Up Lists

Pop-Up Pick Lists - host-defined selection lists that pop up on the terminal and splice the chosen entry's response into the [host command](5.0-host-commands.md) being built, legal anywhere a [text variable](5.1-text-variables.md) is. The mechanism carries into 3.x from 2.0 intact, with one 3.x extension: an optional pop-up position.

_Evidence: 2.00a4; HLP; SyncTERM (ripper.c:11356-11635, 11936-11948)._

_The 2.0 record is [5.4 of the v2.0 reference](../../2.0/ripscrip/5.4-popup-lists.md) (1.54 lineage in the [v1.54 page](../../1.54/ripscrip/5.4-popup-lists.md))._

## Pop-Up Pick Lists

_Evidence: 2.00a4; HLP._

Any place that you can use a text variable (Queries, Button and Mouse Field return strings, and Keystroke Macros), you can take advantage of a unique feature of RIPscrip - Pop-Up Pick Lists. A Pop-Up Pick List is simply a list that pops up allowing the user to choose from one of several available values. Whichever entry in the list is chosen will insert its associated response into the host command returned back to your host.

A list is created by putting the special list instructions inside two sets of parentheses, `((` and `))`. The list consists of an optional question followed by two colons (`::`), followed by one or more comma-separated list entries. For example, `((Send Email to?::Sysop,Cosysop,Joe))` says to pop up a list asking "Send Email to?", giving the choices of "Sysop", "Cosysop", and "Joe".

The full 3.x syntax, with every extension in place:

```text
((*x,y:Question::response@Description,response@Description,...))
```

| Element | Meaning |
| --- | --- |
| `((` … `))` | List delimiters |
| `*` | Response required - the user cannot ESC out of the list |
| `x,y:` | Pop-up position in [world coordinates](../../glossary.md); omit either value (keep the comma) to center on that axis _(new in 3.x - HLP)_ |
| `Question` | Prompt text; if omitted, the default is `Choose one of the following:` |
| `::` | Separates the question from the entries |
| `response` | The text spliced into the host command when chosen |
| `@Description` | Optional display text shown in the list instead of the response |
| `~h~` or `_h_` | Hotkey markup around a character of the description; the first marked character is the active hotkey |

By default, if the user presses ESC instead of picking an entry in the list, then nothing is inserted into the text of the command. You can indicate that the user must pick an entry by putting an asterisk (`*`) at the beginning of the question - for example, `((*Send Mail to?::Sysop,Joe))` forces a choice of either Sysop or Joe.

In the previous examples, Sysop and Joe are the text responses that are inserted into your host command. They are also what is displayed in the listing. If you want to display something else in the listing instead of the return text, add an `@description` to the end of the entry. For example:

```text
((Send Mail To?::Sysop@Head Honcho,Cosysop,Joe))
```

...would display a pop-up pick list of Head Honcho, Cosysop, and Joe.

One final feature allows you to specify a hotkey for each entry in the list. To highlight the first character of an entry (thus allowing that key to activate the entry), put a tilde (`~`) or an underline (`_`) before and after the keystroke: `_S_ysop` highlights the "S" in "Sysop". You can highlight more than one character, but only the first one will be the active hotkey. If you omit the second tilde or underline, then the remainder of the description will be highlighted.

> **NOTE:** If you use a tilde or an underline in the Text Response (not the description), those characters are inserted into your host command when it is transmitted to the host. You probably don't want to do this. Recommendation: only use hotkey features on list entries where you specify a description!

If you do not specify a question, then the list defaults to the question:

```text
Choose one of the following:
```

Rules carried forward from 2.0, all confirmed by RIPtel's help: _Evidence: 2.00a4; HLP._

- Up to **64 entries** per list _(v2.A1)_; in earlier revisions of RIPscrip, a maximum of 20 entries was allowed. If the total number of entries makes the picklist too tall to fit on the screen, it must handle some form of scrolling mechanism. _(v2.A1)_
- In RIPterm version 1.52 and earlier, the total length of a pick list was 256 bytes; in version 1.53 and later, this limit was increased to 1024 bytes. _(v1.53)_
- The characters `!`, `\` and `|` have special significance in the RIPscrip language; to use them in a _Text Response_ they must be escaped with a backslash (`!` becomes `\!`, `\` becomes `\\`, and `\|` for the vertical bar). The hotkey markers `~` and `_` **cannot** be escaped - if they exist in a Text Response they are returned to the host, but everything after them is underlined and the first character is treated as the hotkey. Put hotkeys in descriptions, not responses.
- If the user presses ESC on a non-required list, nothing is inserted.

Examples, from simplest to fullest:

```text
((Send E-Mail to?::Sysop,Joe,Mike))
((*Send E-Mail to?::Sysop@The Head Honcho,Joe,Mike@My Brother))
((::Sysop@_T_he Head Honcho,Joe,Mike@My _B_rother))
((*10,50:Order which fruit?::A@_A_pples,O@_O_ranges,C@_C_herries))
```

The last example uses the 3.x position extension - the list pops up at world coordinates (10, 50) rather than centered. _Evidence: HLP._

## Recursion into the HCL

_Evidence: SyncTERM (ripper.c:11936-11948, 11890-11896)._

The chosen response is not merely transmitted - it is **re-fed through the host-command interpreter**. A pick-list entry may therefore itself contain text variables, control characters, [playback directives](5.3-local-playback.md), or another pick list; SyncTERM implements exactly this (`do_popup`'s result recursing through `handle_command_str`), with recursion depth capped at 64. An entry prefixed `*` inside the option list forces that answer without user interaction - the mechanism SyncTERM uses to auto-answer forced choices. A menu that plays local scenes, a scene that pops another menu: pick lists plus `$>` playback form a small but genuinely programmable UI layer, years before such things were commonplace.

## Worked example: definition and response flow

_Evidence: 2.00a4 (mechanism; constructed example)._

Consider a [mouse field](4.2-mouse-fields-and-pointer.md) whose host command embeds a pick list:

```text
!|1M0000122912340100000E((*Read which area?::MAIL@_M_ail,NEWS@_N_ews,FILES@_F_iles))^m
```

The flow when the user clicks the field:

1. The terminal begins expanding the field's host command and encounters the `((…))` list definition.
2. A pop-up appears titled "Read which area?" listing **M**ail, **N**ews, **F**iles (hotkeys highlighted). The leading `*` means ESC is refused - the user must choose.
3. The user picks "News". The list expression is replaced by that entry's text response, `NEWS`.
4. Expansion continues - in 3.x, the response itself is re-fed through the interpreter (recursion above), so a response containing directives would execute them here. The trailing `^m` becomes a carriage return, and the terminal transmits `E NEWS` followed by CR to the host - which sees an ordinary command string and never knows a menu was involved.

Nothing about the list persists after expansion; clicking the field again pops the list again.
