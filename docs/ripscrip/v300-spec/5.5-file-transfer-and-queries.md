# 5.5 File Transfer & Queries

[◀ Prev: 5.4 Pop-Up Lists](5.4-popup-lists.md) · [Contents](README.md) · [Next: 6.0 Writing 3.x .RIP Files ▶](6.0-writing-rip-files.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

The wire commands that exchange data and files with the host: text-variable query and definition, local scene playback from the command stream, file queries, timing control for local playback, block-mode file transfer, UU-encoded data blocks, capability negotiation and the multi-lingual groundwork.

**None of the level-3/level-9 commands on this page appears anywhere in the RIPtel demo corpus**: the demos are local scene files whose resources (bitmaps, JPEGs, fonts) already sit on disk, so nothing ever needs transferring or rate-limiting. All are nonetheless attested for 3.x - each is named in the RIPSCRIP.HLP inventory (one under a new name, noted below), and SyncTERM implements the block-mode transfer with a full protocol table. The query commands, by contrast, are the most heavily used commands in the corpus. _Evidence: HLP; corpus; SyncTERM._

Capability negotiation in brief: query [`$IFS(keyword)$`](5.1-text-variables.md#ifs) (Is Feature Supported) for a `1`/`0` answer on any feature - protocols (`$IFS(ZMODEM)$`), image formats (`$IFS(JPEG)$`), audio (`$IFS(WAV)$`), emulations, languages - or use its `LIST` directive to enumerate whole categories; query [`$TERMINFO(keyword)$`](5.1-text-variables.md#terminfo) for the terminal's name, vendor and version. These supersede the vendor codes of the [auto-sense response](1.1-protocol-and-command-hierarchy.md#ansi-sequences-auto-sensing). Full variable inventory in the [Text Variable Reference](9.1-text-variable-reference.md). _(v2.A4)_ _Evidence: 2.00a4; HLP._

## RIP_QUERY

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_query)); HLP (`RIP_Query`; query OBJECT/OPTION keywords, resident queries); corpus (489 uses in 62 files); SyncTERM (ripper.c:14881, descriptor `1#3#++`)._

_Query the contents of a text variable_

|               |                                        |
| ------------- | -------------------------------------- |
| **Level**     | 1                                      |
| **Command**   | `Σ` (the Escape character, ASCII 27)   |
| **Arguments** | `mode:1 window_num:1 res:2 query_text` |

**Format:** `!|1<escape> <mode> <window_num> <res> <query_text>` **Example:** `!|1<escape>2Q00this is a query $COMMAND$^m`

**Attributes used:** [Base Math](../../glossary.md) (current setting)

> **NOTE:** Σ is used to indicate the Escape character (ASCII 27 or ESC).

The Query Text Variable command instructs the terminal to immediately respond with some piece of information, whether statically stored, stored internally in RAM (dynamic information), or pre-defined text variables.

This command is unique in RIPscrip in the fact that the command character that is used is NOT a printable character. The escape character (ASCII 27) introduces this command as a measure of security: since the query command can query the terminal for critical (potentially private) information, you would not want a user to be able to query another user's terminal for something like his address information. Since most hosts do not allow the user to enter an escape character, this character is ideal for this purpose - using escape allows only the host (under most circumstances) to be in control of any queries.

The query text can contain control characters, pick-list definitions and text variables - see [5.0 Host Commands](5.0-host-commands.md) for these features.

Whether the information is transmitted instantly or not is dependent on the `<mode>` parameter, which determines when data queries are processed:

| Mode | Description |
| --- | --- |
| 0 | Process the query command NOW (upon receipt) |
| 1 | Process when mouse clicked in the current Graphics Viewport _(v2.A0)_ |
| 2 | Process when mouse clicked in the current Text Window (any text variables that return X or Y mouse coordinates return TEXT coordinates, not graphics coordinates in this mode; these coordinates are two-digit values instead of the graphical four-digit values). _(v2.A0)_ |
| 3 | Process when mouse clicked in the Graphics Viewport specified in the `<window_num>` parameter. If that viewport doesn't exist (hasn't been defined yet), then this query command is ignored. _(v2.A0)_ |
| 4 | Process when mouse clicked in the Text Window specified in the `<window_num>` parameter. Any text variables that return X or Y mouse coordinates return TEXT coordinates based on that window's MicroANSI text font sizes, not graphics coordinates in this mode. _(v2.A0)_ |

Modes 1-4 do not return the results of the query instantly - the query commands are processed when the user clicks the mouse in the text window or graphics viewport respectively. If the `<mode>` is 1 or 2, the current window/viewport is the area acted upon; modes 3 and 4 take the window number from the `<window_num>` parameter. If the associated window or viewport is not defined, the query command is ignored. These "queries after mouse clicks" are only acted upon if the user is clicking on something other than a Button or a Mouse Field. To disable a deferred query mode, issue the same command with the query string of `$OFF$`; providing a `<text>` parameter of anything other than `$OFF$` produces a revised (active) query command. _(v2.A0)_

If more than one query command can be acted upon (ie, multiple viewport queries and/or text window queries are found that the mouse was clicked inside of), then processing happens in a very specific order - all affected queries are processed, none are skipped: _(v2.A4)_

1. The port/viewport table is scanned from 0-35. If a query is found for a port that isn't deactivated, and the mouse was clicked inside that region (for screen ports only), then the query is processed and the next port/viewport is checked.
2. The text window table is scanned from 0-35. If a query is found for a text window that isn't deactivated, and the mouse was clicked inside that window's display area, then the query is processed and the next text window is checked.
3. If a "current viewport" query, otherwise known as a floating viewport query, is found and the mouse was clicked inside the current viewport, then the floating viewport query is processed.
4. If a "current text window" query, otherwise known as a floating text window query, is found and the mouse was clicked inside the text window's display area, then the floating text window query is processed.

When the user clicks the mouse down, all queries are checked against the point where the mouse was originally clicked. After all queries are processed, the mouse click is ignored until the user releases the mouse button. _(v2.A4)_

It should be mentioned that text window queries are performed before any viewport queries where resident queries are concerned. _(v2.A1)_

Some examples of query statements:

```text
                      ^m     Send a carriage return to the BBS now!
My name is $FULL_NAME$^m     Send text "My name is <insert-name-
                             here>" followed by a  carriage return
                             to the BBS.  The <insert-name-here>
                             will be replaced with whatever the
                             variable $FULL_NAME$ contains.
```

> **NOTE:** The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc. It should be set to 00 for compatibility with future releases.

**The 3.x record.** The corpus is saturated with the immediate form (mode 0) used as a _command executor_ rather than a data query: `$COMPAT$` (set 1.54-compatible environment), `$COFF$$DTW$` (cursor off + deactivate text window), `$D(1)$` (delay - 197 uses driving the wipe animations), `$MCURSOR(n)$`, `$SBAROFF$`, and conditional dispatch such as `!|1<ESC>0000<<IF $TGMENU_WIPES$="1">>$>WIPE01.FN$<<else>>$NULL$<<ENDIF>>` (see [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md)). Deferred modes 5/6 appear in the corpus wired to mouse-field _entry/exit_ status-line updates (`.MSE` overlays), a 3.x extension of the documented click modes - see [Query Deferral Modes](5.0-host-commands.md#query-deferral-modes). One authoring typo (CURVES.RIP's `|1<ESC>…` with no `!`) shows the shipping driver's tolerant introducer handling. _Evidence: corpus; HLP._

## RIP_DEFINE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_define) - flagged obsolete there already); HLP (`RIP_Define`; the DLL also exports `RIP_DefineTextVariable`); SyncTERM (ripper.c:15899) - not observed in the RIPtel demo corpus._

_Define a text variable_

|               |                      |
| ------------- | -------------------- |
| **Level**     | 1                    |
| **Command**   | `D`                  |
| **Arguments** | `flags:3 res:2 text` |

**Format:** `!|1D <flags> <res> <text>` **Example:** `!|1D00700text_var,60:?question?default data`

**Attributes used:** Base Math (current setting)

This command is used to create a text variable on the Client (terminal) system. Simply put, a text variable is a piece of information assigned to an identifier that can either be saved to the terminal's [persistent variable store](../../glossary.md) (static variables) or kept in memory only (dynamic variables). Per the 2.00a4 draft, identifiers are 1-12 characters - any alphanumeric character and underscores (`_`), where neither an underscore nor a number can be the first character; RIPtel 3.1's help raises the name limit to 20 characters for the in-line variable syntax (see [5.0](5.0-host-commands.md#setting--reading-user-variables-from-host-commands)), while SyncTERM's reconstruction keeps 12. Values run to 255 characters; where and how persistent variables are stored is implementation-defined.

The `<flags>` parameter combines three separate values into one MegaNum flag that determines how the variable definition will operate:

| Value | Description of Flag                   |
| ----- | ------------------------------------- |
| 001   | Save variable to the persistent store |
| 002   | Cannot specify a blank response       |
| 004   | Non-interactive query                 |

When a variable is flagged as persistent, it becomes a part of the Client system's actual configuration: the value is saved indefinitely until either changed or manually erased. You may choose not to allow the user to enter a blank response, requiring them to enter some piece of information for the variable.

The last flag determines whether the definition is interactive or not. An interactive definition will attempt to define the variable: if it already exists, the value pops up on the screen asking the user to confirm it is correct; if it does not exist, a similar pop-up box appears asking the user to enter data for the given variable. In a non-interactive situation, the Client system checks whether the variable exists. If it does, nothing happens (unless a default response is specified in this command, whereby the Client's variable is updated with the new information). If the value is not defined, the definition becomes interactive by default, since the user actually has to enter something anyway.

The `<text>` parameter is segmented in nature, much like the [RIP_BUTTON](4.3-buttons.md#rip_button) command's. Its syntax:

```text
variable-identifier[,field-width]:[?question-text?][default-value]
```

An example:

```text
FULL_NAME,30:?What is your full name?John Doe
```

The first section is the variable-identifier, immediately followed by an optional field-width (default 60; limit the values to 1-60). The colon (`:`) indicates that the identifier field is completed and that the remainder contains the question and/or the default response (if any) - with neither, the parameter reads `TEXT_VAR,width:` with no additional data. The question-text is specified between question marks (`?this is a question?`). The remainder is a default-value for the variable's contents; it may be omitted so that the user must enter his/her own value instead of some "canned response".

> **NOTE:** The `<res>` parameter is reserved for future use by TeleGrafix Communications, Inc. It should be set to 00 for compatibility with future releases.

THIS COMMAND IS NOW OBSOLETE. USE THE SPECIALLY ENHANCED TEXT VARIABLE SYSTEM WITHIN QUERIES OR HOST COMMANDS TO PRODUCE THE SAME RESULTS AS THIS COMMAND AND MUCH MORE! _(v2.A1)_

The corpus confirms the succession: the demos define hundreds of variables exclusively through the `$-=NAME=value$` [set form](5.0-host-commands.md#setting--reading-user-variables-from-host-commands) and the `$[directives]NAME[@question][=default]$` prompt syntax, never `1D`. The host may also delete variables; RIPtel confirms with the prompt _"The host wants to delete the variable %s. Proceed?"_, and protected variables trigger a "Data Security Activated" message. _Evidence: corpus; HLP._

## RIP_READ_SCENE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_read_scene)); HLP (`RIP_ReadScene`; "Can't locate local RIPscrip scene file %s"; DLL export `RIP_PlaybackLocalRIPFile`); corpus (92 uses in 34 files); SyncTERM (ripper.c:16534)._

_Playback local .RIP file_

|               |                     |
| ------------- | ------------------- |
| **Level**     | 1                   |
| **Command**   | `R`                 |
| **Arguments** | `res:8 filename...` |

**Format:** `!|1R <res> <filename>` **Example:** `!|1R00000000testfile.rip`

**Attributes used:** Draw Color, Back Color, Line Style, Fill Style, Write Mode, Font Style, Port (dependent on the contents of the source file), Base Math (current setting)

This command instructs the remote terminal to playback a local `.RIP` file. The current execution of RIPscrip commands will be temporarily suspended and the contents of the designated RIP file will begin executing. Regardless of whether or not the current RIPscrip code coming across the modem is in the middle of a line or not, the RIP playback file will be assumed to start at the beginning of a line. Therefore, if a RIP_READ_SCENE command is located in a `.RIP` file, it must be the very last command on the line, followed by a carriage return instead of a command delimiter (`|`). This ensures that the loaded `.RIP` file will begin executing properly with the correct delimiters found in the correct places.

The RIP playback file can alter colors, fonts, or whatever. Once the playback of the file is complete, the remaining RIPscrip code that was temporarily suspended will resume execution. Any changes that appeared in the loaded playback file will remain in effect when the resumed code is processed - if you change a color or a font in the playback file and leave them changed, they remain in effect during the resumed execution.

> **NOTE:** The `<res>` parameter is reserved for future development by TeleGrafix. It should be set to "00000000" for compatibility with future releases.

**The 3.x record.** In the corpus this is the _subroutine call_ of an entire scene architecture - `.FN` function scenes, `.DEF` variable definitions, `.MSE` overlays - and it gains three undocumented argument forms: _Evidence: corpus._

- **Plain `.TXT` files**: `!|1R00000000DRAGON.TXT` inside an open `1e` column region flows the file's text into the columns, word-wrapped - it is _not_ parsed as RIPscrip. See [Flowing Whole Files](3.1-column-text-system.md#flowing-whole-files---1r-on-plain-text).
- **Overflow pages**: `!|1R00000000$OVERFLOW(1,CUR)$` re-reads the current page of a column stream's overflow buffer ([pagination](3.1-column-text-system.md#pagination---overflow-and-resetoverflow)).
- **Computed filenames**: `!|1R00000000<<IF $COLORS$<"256">>BLUEBACK.FN<<ELSE>>BLUEFADE.FN<<ENDIF>>` - the corpus's ubiquitous color-depth dispatch - and `$&MAIN_STORY$` variable dereferences (NEWSPAPR.RIP). See [5.2 Templates & Conditionals](5.2-templates-and-conditionals.md#inline-conditionals---if--elseif--else--endif).

The host-command twin of this command is the `$>FILE.RIP$` playback prefix - same engine, click-triggered - compared in [5.3 Local File Playback](5.3-local-playback.md#playback-prefixes-vs-dedicated-commands).

## RIP_FILE_QUERY

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_file_query)); HLP (`RIP_FileQuery`); SyncTERM (ripper.c:16104) - not observed in the RIPtel demo corpus._

_Query existing information on a particular file_

|               |                            |
| ------------- | -------------------------- |
| **Level**     | 1                          |
| **Command**   | `F`                        |
| **Arguments** | `mode:2 res:4 filename...` |

**Format:** `!|1F <mode> <res> <filename>` **Example:** `!|1F010000testfile.icn`

**Attributes used:** Base Math (current setting)

This command queries the existence of a particular file, regardless of type. It is intended for host systems to determine if a particular icon or RIP file exists on the terminal's hard disk - the host side of the 3.x resource-caching story ([staleness check](6.2-asset-delivery-and-storage.md#the-delivery-workflow)). The `<mode>` parameter determines the command's response; the terminal sends the response to the host immediately upon execution.

| Mode | Description |
| --- | --- |
| 00 | Simply query the existence of the file. If it exists, a "1" is returned. Otherwise a "0" is returned to the Host (without a carriage return). |
| 01 | Same as 0, except a carriage return is added after the response. |
| 02 | Queries the existence of a file. If it does not exist, a "0" is returned to the Host followed by a carriage return. If it does exist, the returned text is a "1." followed by the file size (in decimal). The return sequence is terminated by a carriage return. An example of the returned text could be "1.20345". |
| 03 | Queries extended return information. If the file does not exist, a "0" is returned followed by a carriage return. If it does exist, the text returned to the Host is in the Format: `1.size.date.time <cr>`. An example of a return statement could be `1.20345.01/02/93.03:04:30<cr>` |
| 04 | Queries extended return information. If the file does not exist, a "0" is returned followed by a carriage return. If it does exist, the text returned to the Host is in the Format: `1.filename.size.date.time <cr>`. An example of a return statement could be `1.MYFILE.RIP.20345.01/02/93.03:04:30 <cr>`. Note that the file extension adds another period into the return text. |

The self-contained demo corpus has no host to answer, so the command never appears there; SyncTERM implements it against its per-BBS cache directory. Which directories are searched, and where downloaded files land, is the connection-directory model of [6.2](6.2-asset-delivery-and-storage.md). _Evidence: SyncTERM; HLP._

## RIP_DELAY

_Added in RIPscrip v2.A0._

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_delay)) - not in the RIPSCRIP.HLP name inventory, not observed in the RIPtel demo corpus, not in SyncTERM._

_Causes the Client Terminal to Pause_

|               |                  |
| ------------- | ---------------- |
| **Level**     | 3                |
| **Command**   | `D`              |
| **Arguments** | `delay_period:4` |

**Format:** `!|3D <delay_period>` **Example:** `!|3D002D`

**Attributes used:** Base Math (current setting)

This command will cause the remote terminal to pause for `<delay_period>` number of "timer ticks". A Timer Tick is defined as being 1/60th of a second, so a delay period of 60 would be equal to one full second of delay.

During the time period of the delay, the remote terminal should be queueing up any incoming RIPscrip code or raw text (if any) into some form of internal buffer to prevent character loss. After the delay period is complete, the data in that buffer (if any) should be processed immediately and the terminal should resume processing the incoming stream of data.

**The 3.x record** points to this command having been superseded by the text-variable form: the corpus performs all of its pacing - 197 occurrences - with `$D(1)$` inside [RIP_QUERY](#rip_query) commands (`!|1<ESC>0000$D(1)$`, the heartbeat of every wipe animation), and RIPSCRIP.HLP carries a `D` _variable_ processor (`tvarProc` list) but no `RIP_Delay` command name. See [5.1 Text Variables](5.1-text-variables.md). _Evidence: corpus; HLP._

## RIP_BAUD_EMULATION

_Added in RIPscrip v2.A0._

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_baud_emulation)); HLP (`RIP_BaudEmulation`; `$BAUDEMUL$` variable) - not observed in the RIPtel demo corpus, not in SyncTERM._

_Set Baud Rate Emulation for Local RIP Playback_

|               |              |
| ------------- | ------------ |
| **Level**     | 3            |
| **Command**   | `e`          |
| **Arguments** | `rate_val:4` |

**Format:** `!|3e <rate_val>` **Example:** `!|3e01UN`

**Attributes used:** Base Math (current setting)

This command sets the rate at which [local RIP file playback](5.3-local-playback.md) is performed. By default, local RIP playback is done at full speed, which is dependent on your CPU, hard disk speed and many other factors. With this command, you can set the speed at which the playback is performed so that it approximates a particular baud rate. The setting remains in effect even after a [RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) command, so that a Reset command inside a local RIP file will not alter the playback speed in mid-stride. The setting remains in effect until changed explicitly by the user (if possible under the terminal software), or by the host via another RIP_BAUD_EMULATION command.

Typical settings for `<rate_val>` might be 300, 2400, 4800, 19200, etc. A value of 0 indicates that local playback should be performed at maximum speed (no baud rate emulation). _(v2.A3)_

The 3.0 driver keeps the feature (its `$BAUDEMUL$` variable reads the setting back), but the demos run at full speed and pace their animations with `$D(n)$` delays instead. _Evidence: HLP; corpus._

## RIP_ENTER_BLOCK_MODE

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_enter_block_mode)); HLP (`RIP_EnterBlockMode`; "Invalid file transfer protocol number", upload confirmation "Upload file(s) '%s'?", DLL exports `RIP_GetBlockModeFilename`/`RIP_GetBlockModeTransferType`; RIPtel itself uses Zmodem for actual transfers); SyncTERM (ripper.c:17069; manual parse from 17150) - not observed in the RIPtel demo corpus._

_Enter block transfer mode with host_

|               |                                                  |
| ------------- | ------------------------------------------------ |
| **Level**     | 9                                                |
| **Command**   | `Σ` (the Escape character, ASCII 27)             |
| **Arguments** | `mode:1 proto:1 file_type:2 res:4 [filename] <>` |

**Format:** `!|9<escape> <mode> <proto> <file_type> <res> [filename] <>` **Example:** `!|9<escape>00010000ICONFILE.BMP<>`

**Attributes used:** Port (in image or local-playback file types), Base Math (current setting)

This command is used to auto-initiate any desired File Transfer Protocol. The `<filename>` parameter is optional on downloads, required for uploads, and if omitted must be replaced with a `<>` parameter (end of string).

The `<mode>` parameter specifies upload or download: "1" for upload mode, "0" (zero) for download mode. A filename is required for uploads. If the user has Data Security enabled on the terminal, they are prompted to OK the upload before it proceeds (RIPtel asks "Upload file(s) '%s'?"). If the user does not authorize the upload, ten Ctrl-X's (ASCII 24 or CAN) are sent at one-tenth second intervals. The `<file_type>` parameter is ignored for uploads.

### Transfer Protocols

The `<proto>` parameter is the file transfer protocol specifier, merged here with SyncTERM's 3.0-era dispatch (ripper.c:17187-17300):

| Value | Protocol | Filename Required? | SyncTERM |
| --- | --- | --- | --- |
| 0 | Xmodem (checksum) | Yes | supported |
| 1 | Xmodem (CRC) | Yes | supported |
| 2 | Xmodem-1K | Yes | supported |
| 3 | Xmodem-1K (G) | Yes | supported |
| 4 | Kermit | Yes | **rejected** |
| 5 | Ymodem (batch) | No | supported |
| 6 | Ymodem-G | No | supported |
| 7 | Zmodem (crash recovery) | No | supported |
| 8 | Zmodem (no crash recovery) _(v2.A0)_ | No | - |
| 9 | Super Kermit _(v2.A4)_ | No | - |

### File Types

The `<file_type>` parameter determines what type of files are to be received during the block transfer:

| Value | Description of Block Transfer Contents                         |
| ----- | -------------------------------------------------------------- |
| 0     | RIP file sequence (display it)                                 |
| 1     | Generic file sequence (store files for future use) _(v2.A0)_   |
| 2     | BMP file sequence (store them in proper directories) _(v2.A1)_ |
| 3     | Image file sequence (display it) _(v2.A0)_                     |
| 4     | COMPOSITE DYNAMIC file sequence (batch protocols only)         |
| 5     | ACTIVE DYNAMIC file sequence (batch protocols only)            |

Whether the `<filename>` is specified or not, this command must have a `<>` sequence after the filename (even if there is none). With a filename, using Xmodem/CRC:

```text
!|9<escape>01020000filename.icn<>
```

Without a filename, using Zmodem:

```text
!|9<escape>07040000<>
```

In brief: type 0 plays the received RIP file back like any other local RIP file; type 1 stores generic files for future use with no processing; type 2 is identical to type 1 but designated for icon files (`.BMP`, `.BMH`, `.BMM`) - use type 1 instead, as type 2 might change in future revisions; type 3 displays received JPEG images through the current [RIP_IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style) settings (full current-viewport size if none recorded); types 4 and 5 (batch protocols only) route each received file by its extension, storing it - and for ACTIVE DYNAMIC, also playing/displaying `.RIP` and `.JPG`/`.GIF` files on arrival. _(v2.A0)_ The full per-extension routing table, and where "the proper directory" is for every file type - the connection-directory model - are in [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md#block-mode-routing---the-extension-table); files with unrecognized extensions are simply placed there with no further processing.

> **NOTE:** This command must be terminated with a carriage return. A vertical bar (`|`) command delimiter cannot be used to separate this command from a subsequent one on the same line. In other words, this command must be the last command on a line of text. The protocol must begin on the very next line.

SyncTERM also sandboxes the command: filenames containing `\` are rejected, and received files land in a per-BBS `RIP` cache subdirectory rather than RIPterm's global icon directory. _Evidence: SyncTERM._

## RIP_BEGIN_UUENCODE_BLOCK

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4 ([v2.0 entry](../../2.0/ripscrip/5.5-file-transfer-and-queries.md#rip_begin_uuencode_block)); HLP (as **`RIP_BeginEncodedStream`** - the 3.0 name; "encoded stream" file types in the error strings) - not observed in the RIPtel demo corpus, not in SyncTERM._

_Begin a generic UU-Encoded data block_

|               |                     |
| ------------- | ------------------- |
| **Level**     | 9                   |
| **Command**   | `U`                 |
| **Arguments** | `file_type:2 res:8` |

**Format:** `!|9U <file_type> <res>` **Example:** `!|9U0200000000`

**Attributes used:** Port (for displayable graphics sequences), Base Math (current setting)

This command must be the last RIPscrip command on the line of text. The very next line of text will be the beginning (header) information of a UU-Encoded data file block - a way to move binary resources (JPEGs, bitmaps, sounds) over text-only links. The header contains the filename associated with the binary UU-Encoded data; this information is decoded by the receiving terminal and the resulting file is stored on the terminal's hard disk to be processed depending on the `<file_type>` parameter, which is identical in nature and values to the parameter by the same name in the [RIP_ENTER_BLOCK_MODE](#rip_enter_block_mode) command. The file that results from the UU-Encoded data block might be a JPEG file, BMP file, sound file, or could be just about anything.

Immediately after the last line of UU-Encoded data, either raw text or RIPscrip code should begin. Some UU-Encoded data blocks have line-by-line CRC checking. If this mode is specified in the header of the UU-Encoded data block, then CRC checking on the lines should be performed as defined in the UU-Encoding specification. If a single CRC fails, the terminal should kill the partial file and ignore remaining UU-Encoded data until a RIPscrip or raw text block is encountered that it can then subsequently process.

The 3.0 driver renamed the mechanism: RIPSCRIP.HLP's inventory lists it as `RIP_BeginEncodedStream`, and its error strings reference encoded-stream file types, confirming the feature survived into 3.x under the new name even though no shipped demo exercises it. _Evidence: HLP._

## International Support in RIPscrip

_Evidence: 2.00a4._

The RIPscrip language itself is not tied to any particular language. However, there is a need to establish a means of determining and specifying what RIPscrip / text window fonts with special characters should be used, and what language should be used in the terminal software. It is up to the individual application to use whatever files it needs to support a particular language. RIPscrip provides a standardized way of specifying the language support to use: a character code for each of the languages supported. _(v2.A2)_

Currently, English is the only supported language in RIPscrip. For the purposes of multi-lingual extensibility, the convention was established in the 2.x draft: _(v2.A4)_

| Code | Description of Language |
| ---- | ----------------------- |
| ENG  | English                 |

The means of setting the language is for the user to specify in the terminal, preferably in the dialing directory. This allows the user to select a different language for different systems. There is no ability for the host to specify to the terminal what language to use. _(v2.A2)_

The means of finding out what languages the terminal supports is handled via the [`$IFS()$`](5.1-text-variables.md#ifs) text variable. For example, if the host were to query the terminal with a `$IFS(ENG)$`, the terminal would respond affirmatively. _(v2.A2)_
