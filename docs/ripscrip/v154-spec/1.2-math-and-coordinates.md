# 1.2 Math & Coordinates

The [MegaNum](../../glossary.md) base-36 number system every command parameter is written in, and the fixed 640×350 EGA coordinate space every drawing command addresses.

## MegaNums (base-36 numbers)

Numeric command parameters are represented in base-36. This compacts numbers down to roughly 3/5 of their decimal form. This numbering system, technically called "Hexa-Tri-Decimal", has affectionately been dubbed "MegaNums". Unlike Hexadecimal which uses 0-9, A-F, MegaNums take advantage of the entire alphabet, using characters 0-9 and A-Z.

- The digit alphabet is `0`-`9` (values 0-9) followed by `A`-`Z` (values 10-35). It is a plain positional numeral system in base 36 - the value of `1M` is 1×36 + 22 = 58, and `ZZ` is 35×36 + 35 = 1295.
- **Calculating multi-character values:** most-significant digit first, each position worth a power of 36 - value = d₀·36ⁿ⁻¹ + d₁·36ⁿ⁻² + … + dₙ₋₁. To _encode_ a decimal value, take `value ÷ 36^k mod 36` for each position (e.g. decimal 250 as two digits: 250 ÷ 36 = 6 remainder 34 → `6Y`; decimal 639 → 17 r 27 → `HR`). Writers emit uppercase by convention.
- Parameters are **fixed-width**: a `:2` width specifier means exactly two MegaNum digits (0-1295), zero-padded on the left (decimal 10 as a 2-digit MegaNum is `0A`). Numeric parameters have no delimiters between them - the fixed widths are what let the parser slice them apart.
- Ranges per width: 1 digit 0-35 · 2 digits 0-1,295 · 3 digits 0-46,655 · 4 digits 0-1,679,615 · 6 digits 0-2,176,782,335. Screen coordinates use width 2.
- A variable-width numeric parameter may be used only as the last parameter of a command (in practice: the coordinate lists of the polygon/polyline commands); a text string is likewise always last and never MegaNum-encoded.
- **Where to find each command's field widths:** every entry's Arguments row uses `name:width` notation, and the [9.0 Command Reference](9.0-command-reference.md) argument column summarizes the widths for all 53 commands in one place.
- Implementer-level encoding edge cases live in the [MegaNum encoding techspec](../techspecs/1.1-meganum-encoding.md).

Some handy reference points:

| MegaNum | Decimal | Notes                   |
| ------- | ------- | ----------------------- |
| `00`    | 0       |                         |
| `09`    | 9       |                         |
| `0A`    | 10      | letters begin           |
| `0Z`    | 35      | largest single digit    |
| `10`    | 36      |                         |
| `HR`    | 639     | maximum X coordinate    |
| `9P`    | 349     | maximum Y coordinate    |
| `A0`    | 360     | full circle, in degrees |
| `ZZ`    | 1295    | largest 2-digit MegaNum |

## The coordinate space

RIPscrip 1.54 draws in a fixed coordinate space based on the EGA high-resolution 640×350 pixel graphics mode:

- X ranges 0-639, left to right.
- Y ranges 0-349, top to bottom (0 is the top scan line).
- Coordinates in commands are 2-digit MegaNums, so the encodable range (0-1295) comfortably covers the screen; coordinates are pixel positions on this 640×350 grid.

All drawing takes place in the graphics window and is clipped to the current [viewport](../../glossary.md) - see [1.3 World View & Virtual Canvas](1.3-world-view-virtual-canvas.md). Text-window coordinates are separate: they are character-cell based, not pixel based (see [1.4 Terminal & ANSI View](1.4-terminal-ansi-view.md)).

There is no world-coordinate indirection in 1.54 - commands address the 640×350 space directly. (The world/viewport mapping model arrives in the 2.x generation.)

## Aspect ratio

The 640×350 EGA mode has non-square pixels: era displays were 4:3, so each pixel is slightly taller than wide. Two consequences for authors:

- [RIP_CIRCLE](2.2-curves.md#rip_circle) and [RIP_ARC](2.2-curves.md#rip_arc) understand the aspect ratio and draw truly circular circles instead of oblong ellipses like on other graphics systems. The aspect ratio is based on the EGA 640×350 resolution and is understood by both the GUI designer and the Terminal Program.
- Geometry you compute yourself (polygons, béziers) is drawn on the raw pixel grid - a "square" in pixel counts will display slightly tall.

Modern renderer guidance (how to scale 640×350 to a 4:3 display, pixel-aspect correction, filtering) is implementation policy, deliberately kept out of the language reference - see [implementation.md](../../implementation.md).
