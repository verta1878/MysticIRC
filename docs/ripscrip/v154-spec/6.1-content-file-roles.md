# 6.1 Content File Roles

[◀ Prev: 6.0 Writing .RIP Files](6.0-writing-rip-files.md) · [Contents](README.md) · [Next: 6.2 Asset Delivery & Storage ▶](6.2-asset-delivery-and-storage.md)

The content files of 1.5x - `.ICN`, `.MSK`, `.HIC` and `.HLP` - what each is for, how commands reference them by bare name, and the icon file format at the concept level.

## File roles

| Extension | Role |
| --- | --- |
| `.RIP` | A stored RIPscrip command stream (a scene) - see [6.0 Writing .RIP Files](6.0-writing-rip-files.md) |
| `.ICN` | An [icon](../../glossary.md): a named raster image stamped by [RIP_LOAD_ICON](4.0-images-and-icons.md#rip_load_icon), written by [RIP_WRITE_ICON](4.0-images-and-icons.md#rip_write_icon), or used as an icon-button face ([4.2 Buttons](4.2-buttons.md)) |
| `.MSK` | An [icon mask](../../glossary.md): the AND-stamp companion raster controlling transparency when stamping an icon (stamped in AND mode before the icon is stamped in OR mode; documented in the RIPterm/RIPaint manuals and shipped mask files, not in the 1.54 spec itself) |
| `.HIC` | A [hot icon](../../glossary.md): the pressed/highlighted state image of an icon button - same base filename as the button's `.ICN`, loaded automatically when the Hot Icon flag is set ([4.2 Buttons](4.2-buttons.md#flags-bit-descriptions)) |
| `.HLP` | A help file deliverable via [block mode](5.5-queries-and-advanced-commands.md#rip_enter_block_mode) (stored, and auto-loaded if needed) |

Commands reference these files by bare name - no path or sub-directory information is allowed. The `.ICN` extension does not need to be included; if omitted it is appended automatically, and if another extension is provided it is used verbatim (which is how `.MSK` files are loaded through the same RIP_LOAD_ICON command).

## The icon file format (concept level)

_Added in RIPscrip v1.54._

The RIPscrip Icon File format is identical in design to the Borland BGI graphics `putimage()`/`getimage()` buffer format - the same buffer format used by the [RIP_PUT_IMAGE](4.0-images-and-icons.md#rip_put_image) and [RIP_GET_IMAGE](4.0-images-and-icons.md#rip_get_image) commands. In outline:

- The file begins with a four-byte header: 16-bit width and height, each stored **minus 1**.
- After the header follows each scan-line of the bitmap, stored as planar monochrome chunks - four chunks per scan-line in 16-color mode (one per EGA bit plane, highest plane first), each padded to a whole byte.
- The file ends with trailing "trash" data whose value is undefined.

> **Editor's note:** the spec's "1-byte of trash" is incorrect - every shipped icon file carries **two** trailing trash bytes (file size = `4 + height × 4 × ⌈width/8⌉ + 2`, verified against all 219 `.ICN`/`.HIC`/`.MSK` files in the RIPterm 1.54 distribution (212 + 3 + 4), zero mismatches - the RIPterm 2.0 distribution ships none of these formats, its icons having been renamed to `.BMP`). The two bytes match Borland's `imagesize()` +6-byte overhead over the 4-byte header. See the [icon format techspec](../techspecs/3.0-icon-format.md) for the full analysis.

Content creators normally never touch these bytes - icons are produced by RIPaint, or captured on the terminal itself via [RIP_GET_IMAGE](4.0-images-and-icons.md#rip_get_image) + [RIP_WRITE_ICON](4.0-images-and-icons.md#rip_write_icon). Implementers decoding or generating icon files should work from the [icon format techspec](../techspecs/3.0-icon-format.md), which carries the full byte layout, plane-merging rules, and a worked decode.
