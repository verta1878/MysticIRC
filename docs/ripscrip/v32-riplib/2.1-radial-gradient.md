# 2.1 Radial Gradient (§A2G.13)

[◀ Prev: 2.0 Drawing State Stack](2.0-state-stack.md) · [Contents](README.md) · [Next: 5.0 `<<DEBUG>>` Directive ▶](5.0-debug-directive.md)

_Covers RIPlib §A2G.13. A new value for an existing parameter field. See the [tree README](../README.md) for standing and provenance._

RIPlib's gradient-fill command takes a mode field that was effectively boolean; v3.2 adds a third value.

| Mode | Meaning | Since |
| --- | --- | --- |
| `0` | Horizontal - color varies with X | RIPlib v3.0 |
| `1` | Vertical - color varies with Y | RIPlib v3.0 |
| `2` | **Radial** - `c1` at the box center, `c2` at the farthest corner | **v3.2** |

Radial interpolation is per-pixel and linear in **normalized squared distance** from the center, using the floating-point unit §A2G.5 already requires for trigonometry. `A2G.13`

**Format:** `!|28<x:2><y:2><w:2><h:2><c1:2><c2:2><mode:2>`

**Example:** `!|280A0A1414010202` - x=10, y=10, w=20, h=20, `c1` = palette[1], `c2` = palette[2], mode 2 (radial). `A2G.13`

**Backward compatibility within RIPlib** is clean: v3.0 stored the mode as a boolean, treating any non-zero value as vertical, so an existing scene sending `1` still gets vertical output and only `2` is new behavior. `A2G.13`

## Relationship to the TeleGrafix record

⚠ **The command itself is not in the record.** `RIP_GRADIENT_FILL` (`|28`) is part of RIPlib's _v3.0 baseline_, attributed to RIPSCRIP.DLL 3.0.7 `spec (05 §5.8)` - but no gradient command appears in the RIPscrip 1.54 specification, the 2.00 Alpha 4 draft, the RIPtel 3.1 help inventory, or the 116-file demo corpus surveyed for the [3.0 command reference](../../3.0/ripscrip/9.0-command-reference.md). Shipping 3.x content produces its gradients a different way: [RIP_FILL_PATTERN](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill_pattern) with alternating dither patterns blending adjacent bands of a 256-color fade - the BLUEFADE.FN idiom, described as _"the workhorse of the corpus's smooth 256-color gradients"_ ([3.0 shapes & fills](../../3.0/ripscrip/2.3-shapes-and-fills.md)).

So mode `2` extends a command this repository cannot corroborate. Two consequences worth stating:

- **The 3.1/3.2 delta is sound; the baseline is the open question.** Adding a mode value to an existing field is exactly the low-risk change §A2G.8-13 aims for. Whether `|28` should exist at all - and with those arguments - is a v3.0-baseline question for both projects, and a good candidate for joint verification against RIPSCRIP.DLL.
- **The opcode occupies a digit slot.** Level-2 commands in the reconstructed record use letters (`T`, `A`, `B`, `R`, `P`, `s`, `p`, `C`, `W`, `Y`, `E`); RIPlib additionally uses `|20` and `|28`. Nothing collides today, but the digit space is not something the published specifications reserve for this purpose.

Radial gradients themselves are a reasonable thing to want, and RIPlib's formulation - two colors, center to farthest corner, per-pixel interpolation - is the obvious one. On an indexed-color framebuffer the result depends entirely on palette contents between `c1` and `c2`, the same caveat that applies to the corpus's dithered fades.
