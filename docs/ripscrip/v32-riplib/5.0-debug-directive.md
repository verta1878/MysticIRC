# 5.0 `<<DEBUG>>` Directive (§A2G.12)

[◀ Prev: 2.1 Radial Gradient](2.1-radial-gradient.md) · [Contents](README.md) · [Next: 9.0 Additions Reference ▶](9.0-additions-reference.md)

_Covers RIPlib §A2G.12. A new preprocessor directive. See the [tree README](../README.md) for standing and provenance._

A development-instrumentation directive joining the `<<IF>>` / `<<ELSE>>` / `<<ENDIF>>` family:

|  |  |
| --- | --- |
| **Directive** | `<<DEBUG msg>>` |
| **Effect** | Pushes `>DEBUG: <msg>` + CR to the terminal's transmit queue |
| **Suppression** | Skipped inside a false `<<IF>>` branch, like any other content |

The `0x3E` (`>`) prefix marks the line as a host-side log, distinct from the `0x3D` (`=`) sound-command marker in RIPlib's host protocol and from ordinary text. `A2G.12`

```text
<<DEBUG entering menu render>>
!|@01010Menu|
<<IF $APP0$=>><<DEBUG no user name yet>><<ENDIF>>
```

sends

```text
>DEBUG: entering menu render
>DEBUG: no user name yet
```

RIPlib's stated position is that _"a host that does not recognize the prefix simply drops the line - making this safe to leave in production scene scripts."_ `A2G.12`

## Relationship to the TeleGrafix record

**The directive slots into a real 3.x mechanism.** The `<<…>>` macro and conditional layer is genuine, corpus-attested 3.x - `<<NAME>>` macro expansion and `<<IF>> … <<ELSEIF>> … <<ELSE>> … <<ENDIF>>` conditionals, evaluated before the containing command executes, keywords case-insensitive ([5.2 Templates & Conditionals](../../3.0/ripscrip/5.2-templates-and-conditionals.md)). No published TeleGrafix specification describes it; it was reconstructed from the RIPtel demo corpus. Adding a keyword to that family is a natural extension, and `DEBUG` is unused there.

⚠ **It can shadow a macro.** In the 3.x layer, `<<NAME>>` expands to the text variable `NAME`, anywhere in a command's argument text - including inside a `$…$` reference. `<<DEBUG>>` is therefore syntactically indistinguishable from a macro reference to a variable named `DEBUG`, and content defining one gets the directive instead. `<<ELSEIF>>` faces no such problem because it only appears between `<<IF>>` and `<<ENDIF>>`; a bare `<<DEBUG msg>>` appears anywhere. A directive namespace less likely to collide - a punctuation-led form, say - would sit more comfortably in that grammar.

⚠ **Unsolicited terminal-to-host traffic is the real risk.** In RIPscrip 2.x/3.x, everything the terminal sends back is a _response_: an auto-sense reply, a mouse-field or button host command, a `RIP_QUERY` result, a file-query answer ([9.3 Host Command & Control Character Reference](../../3.0/ripscrip/9.3-host-command-reference.md#host-bound-responses)). There is no facility for the terminal to volunteer a line, and a BBS at a prompt treats inbound bytes as the user's keystrokes. `>DEBUG: entering menu render` + CR arriving at a menu prompt is a menu selection, not a dropped log line - `>` is a valid keypress, and the CR commits it.

That makes the "safe to leave in production" advice safe only for hosts written to expect it. A `RIPSCRIP032001`-aware host can filter the `0x3E` prefix; a 1993-2026 BBS cannot, because nothing told it to. Strip `<<DEBUG>>` before shipping a scene to a host you do not control, or gate it behind an `<<IF>>` on a variable only your development host sets:

```text
<<IF $APP9$="DEV">><<DEBUG entering menu render>><<ENDIF>>
```

The suppression rule makes that work - a false `<<IF>>` branch swallows the directive entirely. `A2G.12`
