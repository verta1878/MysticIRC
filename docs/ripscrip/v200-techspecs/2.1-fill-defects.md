# Fill Defects in the Shipping Implementation

[◀ Prev: Canvas Tiers, Palette & RGB Rendering](2.0-canvas-palette-rgb.md) · [Contents](README.md) · [Next: Icons (.BMP / .BMM / .BMH) ▶](3.0-icon-formats.md)

TeleGrafix's fill code was defective in three independent ways, across every client they shipped. This page is the single detailed record: what each defect is, what it affects, and what to implement instead. The [2.0](../ripscrip/2.3-shapes-and-fills.md#rip_fill) and [3.0](../../3.0/ripscrip/2.3-shapes-and-fills.md#rip_fill) language pages carry only a pointer here; the [1.54 reference](../../1.54/ripscrip/2.3-shapes-and-fills.md#rip_fill) documents the command as the specification defines it, without this commentary.

Two of the three reach commands that were **never removed from the language**, so this is not purely a legacy concern.

## Which generation is affected

**The 1.x DOS clients are fine.** RIPterm 1.5x fills through Borland's BGI `floodfill()`, and [RIP_FILL](../../1.54/ripscrip/2.3-shapes-and-fills.md#rip_fill) behaves as the specification describes - artists used it 3,787 times across 78 of the 118 scripts in the RIPtermJS 1.5x corpus and those scenes render. Its one limitation is the finite seed stack described below, which can leave an unusually complex region partly unfilled; that is a bounded, visible shortfall, not the catastrophic failure the later engine has.

**The 2.x/3.x Windows engine is where it breaks.** The rewrite onto GDI `ExtFloodFill` introduced both `§BUG.6` and `§DEAD.7`, neither of which exists in the BGI implementation. So the fill got worse, not better, across the generation boundary - and TeleGrafix removed the command from the language in the same era.

## Why RIP_FILL is documented as deprecated

The reference pages mark [RIP_FILL](../ripscrip/2.3-shapes-and-fills.md#rip_fill) **deprecated** rather than removed. The distinction matters, and this is where it is explained.

**The 2.00 Alpha 4 draft declares the command removed from the language.** Its stated reason is portability - _"fills work differently under Windows, OS/2, Macintosh, Amiga, and DOS. With all of the complexities involved, having a reliable fill operation cannot be achieved under multiple resolutions and platforms"_ `(v2.A2)` - and the 3.x documentation follows suit: `RIPSCRIP.HLP` lists no `RIP_Fill`, and the RIPtel demo corpus never floods.

**Every implementation kept it anyway.** The declaration was never carried through to code:

| Implementation | Status |
| --- | --- |
| RIPterm 1.5x | Implements it; 3,787 `!\|F` uses across 78 of the 118 scripts in the RIPtermJS 1.5x corpus |
| RIPSCRIP.DLL 3.0.7 (RIPtel 3.1) | A live flood-fill command with a border-color codepath survives in the binary (`§DEAD.7`) - so a legacy `!\|F` still executes on the last TeleGrafix client |
| SyncTERM | Implements the 1.54 behavior deliberately for legacy scenes (`ripper.c:13593`) |
| RIPlib | Implements it, corrected - see the summary above |

The 3.0 finding corrects an inference this repository previously drew from the help and corpus silence, that the driver had dropped the command entirely; positive evidence from the binary supersedes an absent name in an inventory.

**So, practically:** the command exists everywhere, executes everywhere, and is defective almost everywhere - which is what "deprecated" is meant to convey. An author cannot rely on it; an implementer cannot ignore it. Neither "removed" nor "supported" describes that accurately.

**New implementations should fix all three, not reproduce them.** None of the defects is load-bearing for any shipping content - no scene can depend on the screen flooding, on a pattern being ignored, or on a region being partly unfilled - so there is no fidelity argument for carrying them forward. [RIPlib](https://github.com/BradHawthorne/riplib) has implemented corrections for all three (cited below); new libraries and clients should adopt equivalent behavior. The exception is a renderer whose explicit goal is period-accurate reproduction of legacy scenes, which is why SyncTERM deliberately keeps the historical seed-stack behavior in a function it names `broken_flood_fill`.

## Summary

| Defect | Generation | Symptom | Affects | Correct implementation |
| --- | --- | --- | --- | --- |
| **Pie/chord fill leak** (`§BUG.6`) | 2.x/3.x | Fill escapes the shape and floods the screen | [RIP_PIE_SLICE](../ripscrip/2.3-shapes-and-fills.md#rip_pie_slice), [RIP_OVAL_PIE_SLICE](../ripscrip/2.3-shapes-and-fills.md#rip_oval_pie_slice), and the 3.x chord/skewed-oval variants | Rasterize the sector directly - per-pixel or scanline angle-and-distance test - instead of flood-filling a boundary |
| **Patterned flood ignored** (`§DEAD.7`) | 2.x/3.x | Patterned flood fills come out solid | [RIP_FILL](../ripscrip/2.3-shapes-and-fills.md#rip_fill), which the driver still executes despite the language removal | Two passes: solid fill first for exact boundary tracking, then apply the pattern over the filled region |
| **Seed-stack drop** | 1.x _(BGI-inherited)_ | Complex regions come back partly unfilled | [RIP_FILL](../../1.54/ripscrip/2.3-shapes-and-fills.md#rip_fill) | Unbounded seed storage plus a per-pixel visited set, rather than a fixed-capacity stack |

**Corrections in practice.** [RIPlib](https://github.com/BradHawthorne/riplib) implements all three: an `atan2f`-based per-pixel sector test for pie fill (reported as zero leak potential by construction), the two-pass patterned flood, and a growable seed stack backed by a one-bit-per-pixel mark bitmap (`riplib:src/drawing.c`, `draw_flood_fill` / `ensure_flood_stack_capacity` / `ensure_flood_marks`). SyncTERM deliberately reproduces the historical seed-stack behavior instead, in a function it names `broken_flood_fill`, so legacy scenes render as they did in period.

**Evidence scope.** `§BUG.6` and `§DEAD.7` were found by systematic disassembly of the **3.0 driver** (`RIPSCRIP.DLL` v3.0.7, October 1997; `riplib:docs/spec/11-dll-deviations.md`). The 3.x engine is the renamed 2.x engine - its font and resource containers still carry "RIPterm v2.0" magic strings - so the defects almost certainly predate 3.0, but no disassembly of a 2.x-era `RIPTERM.EXE` has been done to confirm it. They are documented at 2.0 because that is where the affected primitives and this engine lineage begin; the [3.0 delta](../../3.0/techspecs/2.0-fill-defects-delta.md) records what is directly evidenced, including the 3.x primitives that inherit the pie-fill leak. Treat the 2.x attribution as strongly indicated, not proven.

## §BUG.6 - pie and chord fills leak

`draw_pie` filled a pie slice by flood-filling the region enclosed by the arc and its two radial lines. Sub-pixel gaps between the arc's rasterized endpoints and the radii's endpoints leave that boundary open, and the fill escapes:

> _"Sub-pixel gaps between the arc and radial line endpoints caused the fill to leak out and flood the entire screen."_ (`§BUG.6`)

This is not a rare edge case. Any boundary assembled from two independently rasterized primitives is liable to have a one-pixel gap at the junction, and whether a given slice leaks depends on its center, radius and angles - so a scene can render correctly at one size and catastrophically at another.

The fix is not to patch the boundary but to stop using one: for each pixel in the bounding box, compute its angle from the center and its distance, and fill it if the angle falls within `[start, end]` and the distance is within the radius (adjusting for the ellipse case). There is no fidelity argument for keeping the flood-fill construction - the leak is a defect, not an aesthetic, and no shipping content can have depended on the screen flooding.

## §DEAD.7 - the patterned flood brush was never applied

The implementation accepted a fill pattern for flood fill and created the GDI brush for it, but never passed the brush to the `ExtFloodFill` call in the border-color codepath, so patterned flood fills came out **solid**:

> _"The DLL's flood fill command accepted a fill pattern setting but the flood fill algorithm always filled with a solid color."_ (`§DEAD.7`)

This is the codepath that proves the command outlived its removal: `§DEAD.7` describes a live flood-fill command in the 3.0 DLL, with a border-color branch and a constructed (if unused) pattern brush. A legacy scene sending `!|F` to RIPtel 3.1 therefore fills - solid, ignoring the pattern - rather than being discarded. Patterned filling of the ordinary filled primitives is unaffected.

## The seed-stack drop

Documented in full at [1.54](../../1.54/techspecs/2.1-pattern-fill-rasterization.md#fill-styles-and-patterns), with corpus figures and source citations in the [2.0 errata](../ripscrip/errata.md#rip_fill-declared-removed-but-still-implemented): the underlying BGI flood fill queues its seeds on a fixed-capacity stack (492 entries as RIPterm builds it) and **silently drops** seeds once it fills, so a complex region can come back partly unfilled. Artists did not avoid the command despite this - 3,787 `!|F` uses across 78 of the 118 scripts in the RIPtermJS 1.5x corpus.

This one is BGI-inherited and is the only fill defect the 1.x clients carry. It is worth reading TeleGrafix's removal rationale against that: they cited resolution independence and cross-platform behavior ([2.0 RIP_FILL](../ripscrip/2.3-shapes-and-fills.md#rip_fill)) - and the Windows rewrite that prompted the removal is precisely what introduced the two worse defects above.

## Guidance

- **New libraries and clients: implement all three corrections.** Rasterize filled arc primitives directly; never seed a flood fill on a boundary you assembled from separate primitives; and if you accept legacy `F` at all, use the two-pass patterned fill with unbounded seed storage. RIPlib's implementations are a working reference for each. Reproduce the historical behavior only if period-accurate legacy rendering is an explicit goal - and say so where a reader will see it, as SyncTERM's `broken_flood_fill` naming does.
- **Authors:** avoid flood fill, and treat filled pie and chord primitives as risky unless your clients are newer than RIPtel 3.1. Prefer the deterministic filled objects, or bound the shape with a filled polygon you generate yourself.
