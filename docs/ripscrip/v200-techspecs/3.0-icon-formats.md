# Icons (.BMP / .BMM / .BMH)

[◀ Prev: Fill Defects](2.1-fill-defects.md) · [Contents](README.md) · [Next: JPEG Images ▶](3.1-jpeg-images.md)

RIPscrip 2.x replaced the 1.54 Borland `getimage()` icon formats with plain Windows bitmaps; what follows is the byte-level detail of the files a 2.x client actually reads and writes.

_Documented as a **delta** from the 1.54 formats - the full 1.54 layout is on the [1.54 icon format](../../1.54/techspecs/3.0-icon-format.md) page._

## The extension mapping

The RIPterm 2.30 manual tabulates the replacement directly (RIPTERM.DOC §2.1.5, identical in the 2.0 and 2.30 manuals):

| File description         | Icon   | Mask   | Hot    |
| ------------------------ | ------ | ------ | ------ |
| RIPscrip v1.x icon files | `.ICN` | `.MSK` | `.HOT` |
| RIPscrip v2.x icon files | `.BMP` | `.BMM` | `.BMH` |

The specification records the same rename: "Changed all icon references to the new icon, hot icon, and icon mask extensions (.ICN is now .BMP, .HIC is now .BMH, and .MSK is now .BMM)" (spec revision note v2.A2, [Introduction](../ripscrip/1.0-introduction.md)). Note the manual's `.HOT` vs the published 1.54 specification's `.HIC` for the 1.54 hot-icon extension - see the [icons asset README](../../2.0/assets/icons/README.md#the-2x-icon-taxonomy) for discussion.

All three 2.x extensions denote the **same underlying file format**: a Windows 3.x BMP. The extension encodes the file's _role_ (icon, mask, pressed-state), exactly as `.ICN`/`.MSK`/`.HIC` did in 1.54. The client's file dialogs filter on `*.bmp *.bmm *.bmh` (string in `RIPTERM.EXE`, `~/src/rip-tools/artifacts/ripterm-2.30/extracted/`).

Icon files of every kind live in the `ICONS\` sub-directory of the RIPterm directory, alongside host-supplied `.JPG` images, `.WAV` sounds, and `.RIP` scripts (RIPTERM.DOC §2.1.4 - see the [connection directory model](4.0-connection-directory-model-delta.md)). On the wire they are referenced by [RIP_BUTTON](../ripscrip/4.3-buttons.md#rip_button) (icon buttons), [RIP_LOAD_ICON / RIP_WRITE_ICON](../ripscrip/9.0-command-reference.md), the `$<FILE.BMP$` [local bitmap playback](../ripscrip/5.3-local-playback.md) prefix, and transferred via [RIP_ENTER_BLOCK_MODE](../ripscrip/5.5-file-transfer-and-queries.md) - either as file type 2, "designated for Icon Files only (.BMP, .BMH and .BMM)" (spec v2.A2), or through the batch DYNAMIC modes (file types 4 and 5), whose per-extension routing tables place `BMP`/`BMH`/`BMM` "in proper directory" alongside `RIP`, `JPG` and `GIF`.

## `.BMP` - the icon format as shipped

The specification's Icon/DIB File Format appendix (ALPHA 4 draft §6.1.1 "DIB FILE HEADER", `../text/RIPScrip-2.0-alpha-4.txt` lines 18916-18990; concept-level summary at [content file roles](../ripscrip/6.1-content-file-roles.md)) defines the icon as a Device-Independent Bitmap and walks the `BitmapInfoHeader`, color table, and pixel-block layouts; that page is accurate for everything from the info header onward and is not repeated here. Two corrections/clarifications against the shipped files:

- **Shipped icons are full BMP files, not bare DIBs.** The spec text says the info header is "at the beginning of the file (at offset 0)", but every icon distributed with RIPterm 2.0 and 2.30 begins with the standard 14-byte `BITMAPFILEHEADER` (`BM` magic, u32 file size, u32 reserved, u32 pixel-data offset), with the 40-byte `BITMAPINFOHEADER` at offset 14. Evidence: all 207 preserved 2.x-generation icons ([assets](../../2.0/assets/icons/README.md)) start `42 4D` and carry a valid file header.
- **`biCompression` erratum:** the spec's struct comment reads "1=no compression" while its own body text (correctly) mandates 0 = uncompressed. Every shipped icon has `biCompression = 0`.

Supported pixel depths are 1/4/8/24 bits per pixel, uncompressed only, bottom-up rows padded to 4-byte boundaries, BGR color order - per the spec appendix and unchanged into RIPscrip 3.0. The 2.30 distribution contains 4-bit, 8-bit, and 24-bit icons (e.g. the 36×36 8-bit `RWBTN*` set and the 18×18 24-bit `RWICON10/11` pairs - [inventory](../../2.0/assets/icons/README.md#ripterm-220230-additions-112-files)).

### Observed writer conventions

The icons authored by TeleGrafix's own tooling share a fixed header-field pattern, verified programmatically across all 95 files of the 2.0-era icon set (`~/src/rip-tools/RIPTerm2.0/extracted/ICONS/`, carried unchanged into 2.30):

- `biSizeImage = 0`, `biClrUsed = 0`, `biClrImportant = 0`
- `biXPelsPerMeter = biWidth` and `biYPelsPerMeter = biHeight` - the writer takes the spec's own suggestion that these fields "could easily be set to zero, or the width and height of the image" literally

Worked example - `BUTTON.BMP` (322 bytes, 22×17, 4-bit; `version/2.0/assets/icons/BUTTON.BMP`):

```text
offset  bytes                    field
0x00    42 4D                    "BM" magic
0x02    42 01 00 00              file size = 0x142 = 322
0x06    00 00 00 00              reserved
0x0A    76 00 00 00              pixel data offset = 0x76 (14 + 40 header + 16×4 palette)
0x0E    28 00 00 00              biSize = 40
0x12    16 00 00 00              biWidth = 22
0x16    11 00 00 00              biHeight = 17
0x1A    01 00                    biPlanes = 1
0x1C    04 00                    biBitCount = 4
0x1E    00 00 00 00              biCompression = 0 (uncompressed)
0x22    00 00 00 00              biSizeImage = 0
0x26    16 00 00 00 11 00 00 00  biXPelsPerMeter = 22, biYPelsPerMeter = 17 (= width, height)
0x2E    00 00 00 00 00 00 00 00  biClrUsed = 0, biClrImportant = 0
0x36    AA 00 00 00 …            16 RgbQuad palette entries (B,G,R,reserved)
0x76    …                        pixel rows, bottom-up, 2 px/byte, rows padded to 4 bytes
```

## `.BMH` - hot bitmaps

A `.BMH` is a **plain Windows BMP** whose extension marks it as the _pressed/highlighted_ state of a same-named `.BMP`. There is no format difference whatsoever. Byte evidence from the shipped pairs (`~/src/rip-tools/RIPTerm2.0/extracted/ICONS/`, also preserved in [assets](../../2.0/assets/icons/README.md#ui-controls-8-bmp--3-bmh)):

- `BUTTON.BMP` / `BUTTON.BMH` - identical size (322 B), identical headers and palette; `cmp -l` reports 141 differing bytes, the first at file offset 118, which is exactly the pixel-data offset (0x76) - every difference is in the pixel raster.
- `RADIO.BMP`/`.BMH` (206 B, 27 pixel bytes differ) and `RADIOBUT.BMP`/`.BMH` (322 B, 26 pixel bytes differ) show the same pattern.

Semantics (spec, [RIP_BUTTON](../ripscrip/4.3-buttons.md#rip_button) flag 4096 "Make icon button use hot icons", v2.A3): when an icon button with the hot-icon flag is depressed, the client displays the same-named `.BMH` image in COPY mode; if no `.BMH` exists, the normal `.BMP` is displayed inverted (NOT mode); if neither file exists, the RIP_BUTTON command is ignored. The 2.30 distribution ships 22 `.BMH` files (the three 2.0-era UI controls plus 17 `RWBTN*V` and 2 `RWICON*` hot states); RIPscrip 3.0 (RIPtel) uses the identical convention unchanged - see the [3.x file-formats page](../../3.0/ripscrip/6.1-content-file-roles.md#bmh---button-highlight-variants).

## `.BMM` - icon masks

`.BMM` is the 2.x rename of the 1.54 `.MSK` icon mask (see the [1.54 icon format](../../1.54/techspecs/3.0-icon-format.md)). Documented evidence of the extension:

- The RIPTERM.DOC glossary: "Icon files may end in .BMP, .BMM (mask files), or .BMH (hot icons - used with buttons)".
- The RIP_ENTER_BLOCK_MODE extension table: "BMM ... Place mask icon in proper directory" (spec v2.A2, [Level 3-9 commands](../ripscrip/5.5-file-transfer-and-queries.md)).
- `RIPTERM.EXE` contains the filter strings `*.BMM`/`*.bmm` and the extension string `.BMM` (both the 2.0 and 2.30 binaries), and the 1.54-to-2.x icon converter renames `.MSK` → `.BMM` (RIPTERM.DOC §2.1.5 conversion table).

**No `.BMM` file was ever distributed** - none exists in any recovered RIPterm 2.0/2.30 or RIPtel 3.1 install - so the exact raster convention (whether the mask is stored as a 1-bit BMP, or as a 4-bit BMP whose nonzero pixels form the mask) is **unverified**. Given that the auto-converter produces `.BMM` from 1.54 `.MSK` files and every other icon-family file is a plain BMP, a monochrome (1-bit) BMP carrying the 1.54 mask raster is the natural reading, but this is inference, not observation.

## Conversion from 1.54 icons

The 2.x client retains read support for 1.54 icons by conversion, not native rendering: at start-up it scans `ICONS\` and offers "Convert icon ... to 2.0 BMP format?" (disable with the `-I` command-line switch), and it converts on the fly when a script references a legacy icon. The original file is **deleted** after conversion, the extension is rewritten per the table above, and the file date/time is preserved so host icon-update queries ([RIP_FILE_QUERY](../ripscrip/5.5-file-transfer-and-queries.md#rip_file_query)) still match (RIPTERM.DOC §2.1.5). The RIPscrip 3.0 driver still carries the same converter (`RIP_ConvertIconToBmp` - [3.x notes](../../3.0/ripscrip/6.1-content-file-roles.md#legacy-icn-icons-ripscrip-154)).

Adjacent, but not an icon format: the `ICONS\` directory of the definitive distribution also carries `.JPG` photographic images (baseline JFIF, displayed via [RIP_IMAGE](../ripscrip/4.1-jpeg-images.md#rip_image) and the `$(file.JPG$` playback prefix) - see the [asset inventory](../../2.0/assets/icons/README.md#jpeg-images-7-jpg---the-first-shipped-jpeg-content) and the [JPEG page](3.1-jpeg-images.md).
