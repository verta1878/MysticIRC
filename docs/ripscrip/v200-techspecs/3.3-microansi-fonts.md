# MicroANSI Terminal Fonts (RIPTERM.FNT / .MAF)

[◀ Prev: FastFont Outline Fonts](3.2-fastfont-fonts.md) · [Contents](README.md) · [Next: Audio ▶](3.4-audio.md)

The "RIPterm v2.0 MicroANSI Font File" container holds the fixed-cell bitmap fonts that render the 2.x text side - the ASCII/ANSI terminal emulation and RIPscrip [text windows](../ripscrip/2.0-color-modes-and-palettes.md) - in every graphics resolution the client supports, one complete 256-glyph **CP437** set (the code page of DOS-era BBS terminals and hosts; character codes 0x00-0xFF) per resolution.

It ships as `RIPTERM.FNT` in the RIPterm program directory (263,585 bytes; RIPterm 2.0, 1995-02-01) and as **`RIPTERM.MAF`** in the definitive 2.30 distribution - the same 263,585-byte container, revised only in glyph artwork (see [the MAF revision](#the-maf-revision)) - and the same container format continues unchanged into RIPscrip 3.0 as `RIPscrip.maf`, see the [3.x delta](../../3.0/techspecs/3.3-microansi-maf-delta.md). It shares only a filename with the 1.54-era 18,596-byte `RIPTERM.FNT`, a different format ([1.54 bitmap fonts](../../1.54/techspecs/3.2-bitmap-fonts.md)).

All integers little-endian. All offsets verified programmatically against all three recovered copies (`~/src/rip-tools/RIPTerm2.0/extracted/RIPTERM.FNT`, `~/src/rip-tools/RIPTerm2.22/RIPTERM.MAF`, `~/src/rip-tools/artifacts/ripterm-2.30/extracted/RIPTERM.MAF`).

## Container layout

```text
0x00  byte[0x28]  magic: 04 20 "RIPterm v2.0 MicroANSI Font File " 04 0A 0D 00 1A
                  (\x04 SP … SP \x04 \n \r \0 \x1A - TeleGrafix's standard container
                  magic convention, used across the client's own container files)
0x28  u16         resolutionCount        ; = 5
0x2A  u32         directoryOffset        ; = 0x26917 - NOT necessarily 0x3C!
0x2E  byte[14]    zero
0x3C  …           data (see caveat below)
```

**Caveat - stale directory snapshots:** the file carries **four** copies of the directory, of which only the last is valid. The writer emitted a directory snapshot before the font data and again after most resolution blocks, each one record longer and with the not-yet-final records' width/height fields wrong: 3 records at 0x3C (a zero-offset "640x350 EGA" record, then two records with live offsets but partly wrong dimensions), 3 records at 0xAC3A (after the 640×480 fonts), 4 at 0x16431 (after 800×600), and the canonical **5 at 0x26917** (after the 1024×768 fonts) - the only copy with all five `width`/`height` fields correct, and the one `directoryOffset` points to. Parsers must follow the u32 at 0x2A and ignore everything else that parses like a directory. (In RIPtel's `RIPscrip.maf` the u32 happens to be 0x3C, which is why earlier analysis missed this field's significance; the [3.x container](../../3.0/techspecs/3.3-microansi-maf-delta.md) writes a single directory and no snapshots.)

## Resolution directory (60-byte records)

At `directoryOffset`, `resolutionCount` consecutive records:

```c
struct MafResolution {              /* 60 bytes */
    uint16_t width, height;         /* screen resolution */
    uint32_t fontOffset[5];         /* absolute offsets of 5 font subrecords */
    char     name[36];              /* NUL-terminated, zero-padded */
};
```

(Note: the [RIPtel triage](../../3.0/research/riptel-binary-formats.md) described these as 64-byte records with `name[40]`; the correct stride, verified by the directory ending exactly at the first following font subrecord in both this container and `RIPscrip.maf`, is **60** bytes with `name[36]`.)

The shipped directory:

| Record | Resolution | Name | Font offsets (order: 80×43, 91×43, 80×25, 91×25, 40×25 cells) |
| --- | --- | --- | --- |
| 0 | 640×350 | `640x350 EGA` | 0xF0 (8×8), 0x91A (7×8), 0x1144 (8×14), 0x1F68 (7×14), 0x2D8C (16×14) |
| 1 | 640×480 | `640x480 VGA` | 0x49A2 (8×11), 0x54C9 (7×11), 0x5FF0 (8×19), 0x730F (7×19), 0x862E (16×19) |
| 2 | 800×600 | `800x600 - VGA` | 0xACEE (10×13), 0xC706 (8×13), 0xD42B (10×24), 0x1042D (8×24), 0x11C47 (20×24) |
| 3 | 1024×768 | `1024x768 - VGA` | 0x16521 (12×17), 0x18731 (11×17), 0x1A941 (12×30), 0x1E537 (11×30), 0x2212D (20×24) |
| 4 | 1280×1024 | `1280x1024` | 0x26A43 (16×23), 0x29847 (14×23), 0x2C64B (16×40), 0x3162D (14×40), 0x3660F (32×40) |

The five fonts per resolution correspond to the five selectable System Fonts of the text mode - 80×25 (default), 80×43, 40×25, 91×43, 91×25 (RIPTERM.DOC §4.4 "System Font Setup", Ctrl-Alt-F): "Any subsequent text/ANSI displayed on the screen will appear in the chosen system font unless the host explicitly tells RIPterm to use another font for the text window."

The cell sizes are exactly the five text modes at each resolution: e.g. at 640×350, 8×14 → 80×25, 8×8 → 80×43 (350⁄8 = 43), 7×14 → 91×25 (640⁄7 = 91), 7×8 → 91×43, 16×14 → 40×25. The internal font names state the cell and, from 800×600 up, the mode ("`10x13 (80x43)`", "`80x43 font`", …). Note the fifth record: the container carries a complete **1280×1024** font set even though no shipped video-mode database entry reaches past 1024×768 - see [Canvas Tiers, Palette & RGB](2.0-canvas-palette-rgb.md#resolution-tiers-as-shipped).

## Font subrecords

```c
struct MafFont {                    /* 50-byte header + glyphs */
    uint16_t cellWidth, cellHeight; /* pixels */
    char     name[30];              /* NUL-terminated ("8x14", "10x13 (80x43)", …) */
    uint16_t lastChar;              /* 0x00FF in all 25 fonts */
    uint16_t bytesPerGlyph;         /* = ceil(cellWidth/8) * cellHeight */
    uint8_t  reserved[12];          /* observed zero */
    uint8_t  glyphs[255][bytesPerGlyph];  /* characters 0x01-0xFF; 0x00 not stored */
};
```

Glyph bitmaps are row-major, one row = `ceil(cellWidth/8)` bytes, MSB = leftmost pixel, characters **0x01-0xFF** of CP437 in order - character 0x00 has no stored bitmap and renders blank, so char c lives at `fontOffset + 50 + (c - 1) × bytesPerGlyph`. Verification: every font ends at exactly `offset + 50 + 255 × bytesPerGlyph`, which is the next font's offset (or a directory snapshot, or end-of-file - see the caveat above), across all 25 fonts in all three recovered copies; and the classic CP437 glyphs render directly - char 0x01 of the 8×8 font at 0xF0 + 50 = 0x122 is `7E 81 A5 81 BD 99 81 7E`, the smiley face. The file ends exactly where the last font's char 0xFF ends (0x3660F + 50 + 255 × 160 = 0x405A1) - there is **no truncation**.

(Framing note, corrected 2026-08-08: this section previously described a 42-byte header with 256 glyphs and a "truncation quirk" losing most of the final char 0xFF. That reading only fits fonts whose `bytesPerGlyph` is 8 - for the 8-byte-per-glyph fonts the two framings give byte-identical glyph positions, which is how it survived spot-checks. The 50/255 framing was established by locating full-block char 0xDB and the char 0x01 smiley in fonts of several cell sizes across this container, `RIPTERM.FNT`, and RIPtel's `RIPscrip.maf`; the [3.x page](../../3.0/techspecs/3.3-microansi-maf-delta.md) documents the same verification against the successor file.)

## The MAF revision

`RIPTERM.MAF` differs from `RIPTERM.FNT` in exactly 6,885 bytes (FNT md5 `a0f64c…`, MAF md5 `47c240…`; the `.MAF` byte-identical across the 2.20.01 and 2.30 trees), **all inside glyph bitmaps** - the magic, directory, and every subrecord header are byte-identical. The client binaries name their respective file (`RIPTERM.FNT` string in the 2.0 `RIPTERM.EXE`; `RIPTERM.MAF` in 2.30's), and both log "Shutting down MicroANSI font system". The revision redrew extended-CP437 artwork (accented letters 0x7F-0xA7, box/block drawing 0xB0-0xDA, a few Greek/symbol cells 0xE0-0xEE) in the fonts of the three lower resolutions, and touched nothing at 1024×768 or 1280×1024:

| Resolution | Fonts changed | Changed characters (per-font counts) |
| --- | --- | --- |
| 640×350 | all 5 | 54-82 chars each, in 0x7F-0xA7, 0xAF-0xDA, 0xEC-0xEE |
| 640×480 | all 5 | 60-74 chars each, same ranges (16×19 also touches 0x60-0x61) |
| 800×600 | all 5 | 10-36 chars each, mostly 0x7F-0xA7 |
| 1024×768 | none | - |
| 1280×1024 | none | - |

Worked example - char 0x83 (â) in the 640×350 8×8 font, before (`.FNT`) and after (`.MAF`):

```text
.FNT (2.0)      .MAF (2.30)
.######.        ..###...
##....##        .#...#..
..####..        .####...
.....##.        ....##..
..#####.        .#####..
.##..##.        ##..##..
..######        .######.
........        ........
```

(The redraw shifts the circumflex accent to sit over the letterform instead of rendering as a detached tilde-like row.)
