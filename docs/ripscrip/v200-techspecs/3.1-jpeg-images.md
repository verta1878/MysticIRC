# JPEG Images (.JPG)

[◀ Prev: Icons](3.0-icon-formats.md) · [Contents](README.md) · [Next: FastFont Outline Fonts ▶](3.2-fastfont-fonts.md)

RIPscrip 2.x introduced photographic image display: host-supplied JPEG files rendered into a scalable image area of the viewport.

## Wire surface (brief)

- [RIP_IMAGE](../ripscrip/4.1-jpeg-images.md#rip_image) - `!|1p <res:4> <filename>` (v2.A0): display a JPEG from the terminal's `ICONS\` directory in the current image area.
- [RIP_IMAGE_STYLE](../ripscrip/4.1-jpeg-images.md#rip_image_style) - `!|1i <x0> <y0> <x1> <y1> <flags:4> <res:12>` (v2.A0): define the image area and display flags for subsequent images (details under Rendering below).
- `$(FILE.JPG$` - the local image playback host-command prefix, the JPEG analogue of `$>file.rip$` ([Local File Playback](../ripscrip/5.3-local-playback.md)).
- Delivery: [RIP_ENTER_BLOCK_MODE](../ripscrip/5.5-file-transfer-and-queries.md) transfers `.JPG` files into `ICONS\` (routing details in the [connection directory model](4.0-connection-directory-model-delta.md)); [RIP_FILE_QUERY](../ripscrip/5.5-file-transfer-and-queries.md#rip_file_query) checks existence/size/date; RIP_FILE_DELETE (v2.A4) removes "unneeded JPEG or WAVE files".

## The format as shipped

Every JPEG distributed with the definitive 2.30 client (seven files in the 2.30 `ICONS\` directory, preserved in [assets](../../2.0/assets/icons/README.md#jpeg-images-7-jpg---the-first-shipped-jpeg-content)) has the same profile - **baseline sequential DCT, JFIF 1.00, 8-bit sample precision, 3 components (YCbCr)** (`file(1)` over `~/src/rip-tools/artifacts/ripterm-2.30/extracted/ICONS/*.JPG`):

| File | Dimensions | Profile |
| --- | --- | --- |
| `ASTRO.JPG`, `BEACH2.JPG`, `BRIDGE02.JPG`, `DUSK_SEA.JPG`, `FIRCLOUD.JPG`, `JUPITER.JPG` | 320×200 | JFIF 1.00, baseline, 8-bit, 3-component, 96×96 density |
| `GALAXY.JPG` | 320×240 | same |

For an implementation, baseline sequential 8-bit YCbCr decoding covers all known original content. The 320×200 authoring size is the classic quarter-VGA photo size of the era; images are scaled to the image area at display time (below), so the stored size is not a constraint of the format.

## Decoder envelope (what the client could and could not decode)

RIPterm's decoder is derived from the Independent JPEG Group's libjpeg - its characteristic error strings are embedded in `RIPTERM.EXE` (2.30 build; the same JPEG engine ships from 2.0). Those strings define the supported envelope, and they matter to implementers because any historical content had to fit inside it:

- `Unsupported JPEG data precision` - 8-bit samples only; 12-bit JPEG is rejected.
- `Empty JPEG image (DNL not supported)` - the image height must be in the SOF frame header, not a deferred DNL marker.
- `CCIR601 upsampling not implemented yet` / `Fractional upsampling not implemented yet` - component sampling factors limited to the common power-of-two ratios (1×1, 2×1, 2×2 chroma subsampling).
- `Bogus JPEG colorspace` / `Unsupported color conversion request` - YCbCr/grayscale JFIF-style color only.
- Whether the shipped build decodes **progressive** JPEG is unverified - no error string settles it and no progressive file appears in any distribution; all shipped content is baseline. Implementations targeting historical fidelity can treat baseline as the interchange profile.

The client's file-open dialog filters "JPEG images / BMP images / All files" with `.JPG` (strings in `RIPTERM.EXE`) - **no GIF support shipped**, even though RIP_IMAGE_STYLE flag 8 anticipates GIF palettes (below).

## Rendering to the canvas

From [RIP_IMAGE_STYLE](../ripscrip/4.1-jpeg-images.md#rip_image_style) (v2.A0-A4):

- **Image area** - `<x0> <y0> <x1> <y1>` in the current viewport; coordinates beyond the viewport are clamped. All-zero coordinates disable image viewing entirely. With no RIP_IMAGE_STYLE processed, the image area defaults to the full viewport, and it resets to full viewport on [RIP_RESET_WINDOWS](../ripscrip/1.3-world-view-virtual-canvas.md#rip_reset_windows)/[RIP_HEADER](../ripscrip/1.1-protocol-and-command-hierarchy.md#rip_header).
- **Scaling** - the image is scaled to fit the image area (v2.A1). Flag `1` preserves aspect ratio, letterboxing the unused margins in black - without it the image stretches to the area.
- **Flags** - `2` delete the image file after display (for block-mode/UU-encoded delivery); `4` skip clearing the image area to the background color first; `8` commit the image's palette to the hardware color lookup table - "typically only of use … with GIF files. This flag is ignored with JPEGs" (v2.A4).
- **Color reduction** - the spec does not define how a decoded 24-bit image maps onto a 16- or 256-color video mode; that quantization/dithering is necessarily the terminal's own (RIP_IMAGE lists Write Mode, Viewport, Port, and Base Math as the attributes used). A modern true-color canvas can simply render the decoded RGB; a mode-faithful renderer must quantize to the active palette (see [Canvas Tiers, Palette & RGB](2.0-canvas-palette-rgb.md)).

`RIPTERM.DOC`'s glossary frames JPEG for its users simply as "a compressed graphic file format" with lossy compression (2.30 manual, glossary entries "JPEG", "lossy"). The RIPterm Pro Test Drive 2.11 changelog notes JPEG decoding was made ~20% faster - an implementation note only; the format envelope did not change (see [history.md](../../history.md)).
