# Audio (.WAV)

[◀ Prev: MicroANSI Terminal Fonts](3.3-microansi-fonts.md) · [Contents](README.md) · [Next: UI Resources ▶](3.5-ui-resources.md)

Digitized audio is a RIPscrip 2.x headline feature: background `.WAV` playback while graphics commands continue streaming from the host.

## The WAVE (PCM) interchange format

The [Audio Formats section](../ripscrip/4.5-audio-files.md#audio-sound--music-formats) (spec v2.A4) fixes the interchange format: **Microsoft WAVE containing uncompressed PCM**. Clients on non-WAVE-native platforms must translate - including translating file sizes reported back to the host so [RIP_FILE_QUERY](../ripscrip/5.5-file-transfer-and-queries.md#rip_file_query) update checks still match. No narrower profile (rate, depth, channels) is documented anywhere, so a conforming player should accept the general PCM WAV family; RIPterm's own output path handles 8- or 16-bit, mono or stereo (RIPTERM.DOC §4.3).

A WAVE/PCM file is a RIFF container:

```text
0x00  "RIFF"  u32 riffSize  "WAVE"        ; riffSize = file size - 8
      "fmt "  u32 fmtSize (= 16 for PCM)  ; format chunk
        u16 wFormatTag        ; 1 = PCM (the only tag the spec's "WAVE (PCM)" admits)
        u16 nChannels         ; 1 = mono, 2 = stereo
        u32 nSamplesPerSec    ; sample rate in Hz
        u32 nAvgBytesPerSec   ; rate × block align
        u16 nBlockAlign       ; channels × bytesPerSample
        u16 wBitsPerSample    ; 8 (unsigned samples) or 16 (signed, little-endian)
      "data"  u32 dataSize    ; dataSize bytes of raw samples follow
```

Chunks are word-aligned and other chunk types may appear between `fmt ` and `data`; a robust parser walks chunks rather than assuming fixed offsets (the one shipped file happens to be the minimal fixed layout below).

### Worked example - `RIPTERM.WAV`

`RIPTERM.WAV` (75,034 bytes) ships in the program directory of every 2.x-generation release, byte-identical (md5) across the recovered 2.0, 2.20.01, and 2.30 installs; preserved at [`version/2.0/assets/audio/RIPTERM.WAV`](../../2.0/assets/audio/README.md). Decoded:

```text
0x00  "RIFF" 12 25 01 00 "WAVE"      ; RIFF size 0x12512 = 75,026
0x0C  "fmt " 10 00 00 00             ; fmt chunk, 16 bytes
0x14  01 00                          ; wFormatTag = 1 (PCM)
0x16  01 00                          ; nChannels = 1 (mono)
0x18  77 2B 00 00                    ; nSamplesPerSec = 0x2B77 = 11,127 Hz
0x1C  77 2B 00 00                    ; nAvgBytesPerSec = 11,127
0x20  01 00                          ; nBlockAlign = 1
0x22  08 00                          ; wBitsPerSample = 8
0x24  "data" EE 24 01 00             ; 74,990 sample bytes (~6.7 s), unsigned 8-bit
```

The odd 11,127 Hz rate (nominal 11.025 kHz hardware clocking) is characteristic of period sampling tools. This is the client's own sound effect, not BBS content - but it is a useful conformance fixture: 8-bit mono PCM at ~11 kHz is exactly what a 2.x-era host would have assumed any terminal could play.

## Playback semantics

- [RIP_PLAY_AUDIO](../ripscrip/4.5-audio-files.md#rip_play_audio) - `!|1w <res:4> <filename>` (added v2.A3). Starts **background** playback of a local `.WAV` (graphics continue streaming); the file must live with the bitmapped icons in `ICONS\` (RIPTERM.DOC §2.1.4 routes "Sound Files - .WAV" there; there was never a dedicated audio directory - see the [connection directory model](4.0-connection-directory-model-delta.md)). A missing file is silently ignored; a new command **replaces** any sound already playing; the literal filename `$OFF$` stops playback. The 4-character `<res>` field is reserved ("0000").
- `$)FILE.WAV$` - the local audio playback host-command prefix ([Local File Playback](../ripscrip/5.3-local-playback.md)), the audio analogue of `$>file.rip$`, introduced because "you cannot be certain solely from a filename or a file extension if the file is truly a sound file" (v2.A4 revision notes).
- **Reset** - `$RESET(SOUND)$` ([terminal reset options](../ripscrip/5.1-text-variables.md#reset)) aborts any playing digitized sound immediately.
- **Delivery/management** - [RIP_ENTER_BLOCK_MODE](../ripscrip/5.5-file-transfer-and-queries.md) transfers `.WAV` files via the generic file type - `WAV` has no row in the DYNAMIC-mode extension tables, so audio falls to the catch-all and is placed in the proper directory unprocessed (see [block-mode routing](4.0-connection-directory-model-delta.md#block-mode-routing---the-extension-table)); RIP_FILE_QUERY checks existence/size/date so hosts can push updates; RIP_FILE_DELETE (v2.A4) removes "unneeded JPEG or WAVE files".
- **Capability negotiation** - the `$IFS$` [text variable](../ripscrip/9.1-text-variable-reference.md) exposes an `_AUDIO` category whose sole listed member is `WAV`.
- **No sequenced music** - the spec's preamble promises "both digitized and sequenced music", but no sequenced-music (MIDI) format, command, or file ever appears in the specification or any recovered 2.x-generation distribution. The 1.54-era `$MUSIC$`/`$SOUND()$` tone variables remain in the language as the legacy PC-speaker path, distinct from digitized audio.

## Client implementation notes (passing reference)

RIPterm implements WAV playback exactly along those lines - "A new feature in RIPterm is the support for digitized sound, in the form of .WAV files" (RIPTERM.DOC §2.1.3, identical framing in the 2.0 and 2.30 manuals) - via HMI's "Sound Operating System" DOS drivers (`HMIDRV.386`/`HMIDET.386` in the program directory), with sound-card selection and output options in Audio Setup (§4.3) and a `-A` command-line switch to disable audio entirely (§2.3). None of that affects the interchange format above. Notably, **no shipped demo script exercises the audio commands** - a scan of every `.RIP` file in the recovered 2.0 and 2.30 `ICONS\` directories finds no `!|1w` command and no `$)…$` prefix - so `RIPTERM.WAV` is the only WAV in any 2.x-generation distribution.
