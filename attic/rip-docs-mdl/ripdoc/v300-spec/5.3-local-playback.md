# 5.3 Local File Playback

[◀ Prev: 5.2 Templates & Conditionals](5.2-templates-and-conditionals.md) · [Contents](README.md) · [Next: 5.4 Pop-Up Lists ▶](5.4-popup-lists.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

Local playback directives instruct the terminal to process a file _already on the user's disk_ instead of pulling content over the modem - the client/server heart of the [Host Command Language](5.0-host-commands.md), which the White Paper singles out as the way "to simulate menus on an online service locally, thus making it so that you don't have to transmit hardly anything over the modem." They are prefix [text variables](5.1-text-variables.md), usable from within any host command or query.

_Evidence: WP; 2.00a4; HLP._

All four playback forms share one shape: `$`, a one-character prefix, the filename, `$`. RIPtel searches for the named file in the current host's [connection directory](../../glossary.md) first, then in `ICONS\`, then along the user-configured Search Path (which allowed CD-ROM-resident resources for games) - the [file override](../../glossary.md) lookup order detailed in [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md#lookup-order-file-override). _Evidence: HLP._

| Directive     | Media                             | Example           |
| ------------- | --------------------------------- | ----------------- |
| `$>FILE.RIP$` | RIPscrip scene (or any text file) | `$>NEWSPAPR.RIP$` |
| `$)FILE.WAV$` | Digitized audio                   | `$)TRAIN.WAV$`    |
| `$<FILE.BMP$` | Bitmap image                      | `$<BRICK.BMP$`    |
| `$(FILE.JPG$` | JPEG photograph                   | `$(ASTRO.JPG$`    |

The bracket mnemonic is deliberate, and inherited from 2.0: angle brackets (`>`, `<`) mark the _low-level_ playback primitives (raw RIPscrip, raw bitmap), while the parentheses (`)`, `(`) mark the _higher-level_ media objects (audio, compressed photos). _Evidence: 2.00a4._

_The 2.0 record this carries forward is [5.3 of the v2.0 reference](../../2.0/ripscrip/5.3-local-playback.md); 1.54 had only `$>file$`, in the [v1.54 page](../../1.54/ripscrip/5.3-local-playback.md)._

## Local Scene Playback - `$>FILE.RIP$`

_Evidence: 2.00a4; HLP; SyncTERM (ripper.c:7967-7970); corpus (DEMO-01.COL, TELCMDS.FN)._

You can re-play a `.RIP` file that you have locally on your hard disk from any place that allows text variables. After the initial dollar sign (`$`), enter the greater-than symbol (`>`) followed by the filename (with or without the `.RIP` extension), then ending in another dollar sign (`$`). Several examples:

```text
$>MYFILE.RIP$
$>FILE1$
$>FILE1.RIP$$>FILE2.RIP$$>FILE3$
```

The file replays as if it had arrived from the host - with one critical difference: **the data is echoed locally only, never sent to the host**. If the file is a RIPscrip scene, its graphics draw and any mouse fields it defines are created, which is how pop-up dialogs and entire menu systems run without host traffic. The file need not be RIPscrip at all - any text file, ANSI screen, or (in 3.x) flowed article text is legal; see the [Column Text System](3.1-column-text-system.md) for the non-RIPscrip case.

SyncTERM implements the form as a special case checked _before_ text-variable lookup: a leading `>` routes the remainder to `rip_play_scene` (`ripper.c:7967-7970`).

The RIPtel corpus leans on this directive harder than on any other: 34 distinct `$>file$` forms chain the whole demo together - `$>WIPE00.FN$` transition "subroutines", `$>newspapr.rip$` navigation, and the `$<<RETURN>>$` computed-return idiom described under [Templates & Conditionals](5.2-templates-and-conditionals.md#the-3x-macro-layer---name). Filenames are case-insensitive in practice (`$>newspapr.rip$` and `$>NEWSPAPR.RIP$` both appear).

## Local Audio Playback - `$)FILE.WAV$`

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4; HLP._

`$)FILENAME$` plays a local digitized audio file - Microsoft WAVE format as far as the wire is concerned; a terminal using another native format must translate. The file extension itself is unimportant:

```text
$)AUDIOFILE.FIL$
$)TRAIN.WAV$
```

The macro form is the HCL twin of the `1w` ([RIP_PLAY_AUDIO](4.5-audio-files.md#rip_play_audio)) command, and the same playback model applies:

- Audio plays **in the background, asynchronously** - graphics keep drawing and host data keeps arriving while sound plays.
- There is a **single playback channel**: starting a new file terminates whatever is currently playing.
- The reserved filename `$OFF$` (i.e. `1w` with filename `$OFF$`) silences the current sound.
- If the file does not exist locally, the directive does nothing; hosts deliver audio files ahead of time via block transfer ([6.2](6.2-asset-delivery-and-storage.md)).

See [4.5 Audio Files](4.5-audio-files.md) for the audio format details. Note that RIPtel 3.1's install sets `AUDIO=TRUE` in `RIPSCRIP.INI` and its help advertises "background digitized audio," but the demo corpus itself ships no `.WAV` files and never issues an audio command - the demos are silent. _Evidence: corpus; HLP._

## Local Bitmap Playback - `$<FILE.BMP$`

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4; HLP._

`$<FILENAME.BMP$` places a local bitmap (`.BMP`) file onto the screen through the current **image style** (`1i`, [RIP_IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style)): the bitmap is displayed inside the current image settings and adheres to them. This mode of displaying a BMP file is the only method for showing a BMP via the image-style settings. If no image style definition has been recorded, the bitmap is shown at the maximum size of the current viewport - scaled to fill it entirely.

For the purposes of universality, the bitmap is shown using the current screen's color palette and "auto-dithering" mode. RIPTEL.HLP is explicit that the full flexibility of `RIP_LoadBitmap` (palette modes, clipping options - [RIP_LOAD_BITMAP](4.0-icons-and-bitmaps.md#rip_load_bitmap)) is _not_ available from the macro form; use the wire command when you need it. This directive is provided as a simple method of showing a bitmapped image from within a host command:

```text
$<FILENAME.BMP$
```

Note that this uses the less-than sign, unlike the greater-than sign used for local RIPscrip playback - the opposite angle-bracket marks it as a low-level primitive playback, per the bracket mnemonic above.

## Local JPEG Playback - `$(FILE.JPG$`

_Added in RIPscrip v2.A1._

_Evidence: 2.00a4; HLP; corpus (N2_PHOTO.RIP)._

`$(FILENAME.JPG$` displays a compressed photographic image the same way - through the current image style, or full-viewport when none is recorded. The JPEG file is considered a higher-level object than a raw bitmap, so it uses the parenthesis prefix instead of the angle bracket. JPEG is the only supported photo format in the 3.0 driver:

```text
$(MYFILE.JPG$
```

A companion action variable positions the _next_ image without redefining a style on the wire:

```text
$IMGSTYLE(cur,x0,y0,x1,y1)$
```

where `cur` selects the current screen port. The demo corpus displays its sixteen JPEGs through the wire commands (`1i` + `1p`) rather than the macro form, but the macro and `$IMGSTYLE$` are documented in RIPtel's help as the host-command route to the same machinery.

## Worked examples per prefix

**`$>file.rip$` - scene playback from a mouse field.** A mouse field whose host command is nothing but a playback variable displays a locally stored dialog scene when clicked - nothing is sent to the host:

```text
!|1M00051E1R2A1100000$>HELPBOX$
```

Clicking the region replays `HELPBOX.RIP` from the connection directory (or the default `ICONS\` directory, or the search path). If `HELPBOX.RIP` itself defines mouse fields - say an "OK" button whose host command is `$PCB$` to paste back the screen area saved earlier - the pop-up is fully interactive without any host round-trip. _Evidence: 2.00a4._

The shipping corpus does exactly this at production scale - a DEMO-01.COL mouse field records a return scene, then plays the weather page, all locally:

```text
!|1M000G7Y8ICC1000000ID=2:$-=RETURN=>NEWSPAPR.RIP$$>TWEATHER.RIP$
```

_Evidence: corpus (DEMO-01.COL)._

**`$(file.JPG$` - image display from a button.** A button that shows a locally cached photograph inside the current image area when clicked:

```text
!|1U0A0A00003200<>View photo<>$(SUNSET.JPG$
```

The image scales into the image area exactly as if the host had issued [RIP_IMAGE](4.1-jpeg-images.md#rip_image) - but with no transmission cost, because `SUNSET.JPG` was delivered earlier by block mode. _Evidence: 2.00a4; HLP._

**`$)FILE.WAV$` - audio playback from a host command.** A host command (or portion of one) that starts background audio:

```text
$)TRAIN.WAV$Now boarding^m
```

The terminal starts `TRAIN.WAV` playing in the background and transmits `Now boarding` plus a carriage return to the host. Stopping playback (`$OFF$` semantics) belongs to [RIP_PLAY_AUDIO](4.5-audio-files.md#rip_play_audio) - see [4.5 Audio Files](4.5-audio-files.md). _Evidence: 2.00a4._

**Chained playback.** Several files can be replayed back-to-back from one command, as in `$>FILE1.RIP$$>FILE2.RIP$$>FILE3$` - useful for assembling a scene from locally cached parts. The corpus's `.RET` return scripts chain a transition wipe and a destination scene the same way (`$>WIPE01.FN$` … `$>TELPORT.FN$`). _Evidence: 2.00a4; corpus (TELDEMOS.RET, MENU.RET)._

**Computed playback (3.x).** With the [macro layer](5.2-templates-and-conditionals.md#the-3x-macro-layer---name), the filename itself can be assembled at run time: `$<<CMD1>>$` expands `<<CMD1>>` to `>TELDEMOS.FN` first, yielding the playback directive `$>TELDEMOS.FN$` - the mechanism behind RIPtel's generic menu scenes. _Evidence: corpus (MENU.MSE)._

## Playback prefixes vs dedicated commands

Same media, different invocation path: the chapter-4 commands live in the RIPscrip **command stream** (the host draws _now_, mid-scene), while the playback prefixes live at the **host-command/macro layer** (the action fires later, when a button or mouse field is clicked, or when a query is processed). The prefix forms also deliberately trade flexibility for brevity - fixed display settings where the commands take parameters.

| Media | Command-stream command | Host-command prefix | Differences |
| --- | --- | --- | --- |
| RIPscrip scene | [RIP_READ_SCENE](5.5-file-transfer-and-queries.md#rip_read_scene) | `$>file.rip$` | Same playback engine; the prefix form is the only one usable from a click |
| BMP bitmap | [RIP_LOAD_BITMAP](4.0-icons-and-bitmaps.md#rip_load_bitmap) / [RIP_LOAD_ICON](4.0-icons-and-bitmaps.md#rip_load_icon) | `$<file.BMP$` | The prefix displays via the image-style area with auto-dithering and the current palette only; the commands offer position, scaling, put modes, palette and transparency flags |
| JPEG image | [RIP_IMAGE](4.1-jpeg-images.md#rip_image) | `$(file.JPG$` | Both display via the current [RIP_IMAGE_STYLE](4.1-jpeg-images.md#rip_image_style) settings |
| WAV audio | [RIP_PLAY_AUDIO](4.5-audio-files.md#rip_play_audio) | `$)FILE.WAV$` | Both start background playback; the command form also defines `$OFF$` to stop a running sound |

The corpus shows both paths in production use, split exactly along this line: scene navigation and subroutines fire from clicks via `$>` (34 distinct forms) while mid-scene subroutine calls use `1R` (92 uses in 34 files), and the sixteen demo JPEGs display via the wire commands (`1i` + `1p`) because they are drawn during scene playback, not on click. _Evidence: corpus._
