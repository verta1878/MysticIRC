# Connection Directory Model

[◀ Prev: Bitmap Fonts](3.2-bitmap-fonts.md) · [Contents](README.md)

RIPscrip's asset storage model is two-tier - a per-connection asset directory plus a shared default directory, with a defined lookup order - and governs every named asset an implementation loads or saves (icons, masks, hot icons, `.RIP` scenes), as defined by RIPterm 1.54 (`~/src/rip-tools/RIPterm154/DOS/RIPTERM/RIPTERM.DOC`, dialing-directory DIR field section and §7.4.2.4).

_Canonical terms: [connection directory](../../glossary.md#client-storage), [default icon directory](../../glossary.md#client-storage), [file override](../../glossary.md#client-storage)._

## The two directories

- **Connection directory** - a per-host (per-connection) asset directory associated with each dialing-directory entry (RIPterm's DIR field; a bookmark/profile field in a modern client). RIPTERM.DOC: "Each entry in the directory has the ability to have a separate sub-directory associated with it. This is used mainly when RIPscrip graphics are being viewed on the host. Any icon (.ICN, .MSK, .HIC) or RIPscrip (.RIP) files that are received by the host [sic - from the host] should be placed in the designated sub-directory. This in effect, helps keep your icons separated from each other."
- **Default icon directory** - the shared fallback directory, historically `ICONS\` under the client install. RIPTERM.DOC: "If you omit a directory name in this field, and you dial into a RIPscrip host that requires icons or RIPscrip files, RIPterm will look for them automatically in the ICONS\ sub-directory." It holds the stock assets every host may rely on (RIPterm shipped 184 stock `.ICN` icons there - preserved in [`version/1.54/assets/icons/`](../../1.54/assets/icons/README.md)).

A connection directory is optional per connection; when none is configured, the default directory serves both roles. RIPterm could only associate a directory with dialing-directory entries - "if you dial a host by issuing modem commands directly (not using the dialing directory), then the correct directory may not be used since RIPterm has no way of knowing which dialing directory entry you are calling" (RIPTERM.DOC, DIR field notes). A modern implementation should give every connection profile its own directory so the caveat disappears.

## Resolution order: connection directory first ("file override")

Asset lookups check the connection directory **before** the default directory. RIPTERM.DOC: "If the DIR field is non-blank, indicating a sub-directory should be used for that specific host, RIPterm will check in that directory first for any necessary icons or RIPscrip files. If the needed files are not found in that sub-directory, RIPterm will check the ICONS\ sub-directory afterward to see if it is there. This facilitates the concept of \"file overide\" [sic]."

The manual's motivating example is the reason the order matters: sysops independently pick obvious names - "Files like EMAIL.ICN or FILES.ICN would be used on nearly any host! If all these files were located in the same directory, only the very latest installed files would be used when you call a host! In other words, when you call host XYZ, you might see host ABC's EMAIL icon!" (RIPTERM.DOC, same section). Per-connection directories keep same-named assets from different hosts from colliding, and the fallback still lets a host use stock assets by simply not delivering its own copy: "the sysop has the ability to overide [sic] standard icons with his own without affecting the standard icons in any way."

The same order applies to [local `.RIP` playback](1.0-rip-stream-parsing.md#related-local-playback), not just in-session loads - RIPTERM.DOC §7.4.2.4: "Each \"local RIP playback\" variable you enter will search for the .RIP file in the current host's icon directory. If it cannot find the file in that directory, it will check the ICONS\ directory."

## Downloads land in the connection directory

Host-delivered files (block-protocol downloads) are written to the connection's directory when one is specified, else to the default directory - never to the user's general download directory. RIPTERM.DOC, DIR field note: "RIPterm supports a \"block protocol\" mode for hosts that can support it. This mode allows the host to send files to your computer for subsequent use. Any files received in this mode are automatically placed in the proper host DIR directory. If no host DIR field is specified, then the ICONS\ sub-directory is chosen as the destination sub-directory. The download directory as set in the General Settings dialog box is not used in this situation as the destination directory." The wire-level delivery flow (RIP_FILE_QUERY → RIP_ENTER_BLOCK_MODE) is the creator-side page [Asset Delivery & Storage](../ripscrip/6.2-asset-delivery-and-storage.md).

## Auto-creation on first use

The connection directory is created by the client, not the user: "You do not need to create the sub-directory yourself. The first time that you specify a directory in the DIR field, it will be created when you click on the OK button" (RIPTERM.DOC, DIR field). An implementation should likewise create a connection's directory automatically the first time it is configured or first receives a download - a missing directory is never a user-visible error.

## Case-insensitive asset access

**All asset access is case-insensitive.** The original clients ran on DOS (RIPterm) and Windows (RIPtel), whose filesystems are case-insensitive by nature; scripts and hosts freely mix case (`meowbody.ICN`, `CHROME.MSK`), and nothing in the protocol ever compares filenames case-sensitively. An implementation on a case-sensitive filesystem must therefore provide case-insensitive lookup by convention - any equivalent scheme works ([implementation.md - Case Insensitiviy](../../implementation.md#case-insensitiviy)):

- **Lowercase-normalize everything** - store every asset file lowercased and lowercase every requested name before lookup.
- **Self-monitor and index** - pre-load and track the asset directories (watching for changes), resolving requests through a case-folded index that maps to the on-disk names.
- Any other scheme yielding the same observable behavior: a request for `EMAIL.ICN` finds `email.icn`, `Email.Icn`, etc.

This composes with the [asset-substitution / hierarchical-lookup suggestion](../../implementation.md#future-directions-versionnext) in implementation.md: an implementation may satisfy a request from a modern-format equivalent of the same base name (e.g. `.PNG` for `.ICN`), searching supported extensions in a defined preference order - the case-folding and the connection-first directory order both apply at every step of that search.

## Filename sanitization

Asset filenames on the wire are **bare names**: no drive letters, no path components. The 1.54 spec forbids path information in [RIP_LOAD_ICON](../ripscrip/4.0-images-and-icons.md#rip_load_icon) filenames, and reference implementations enforce it - SyncTERM rejects any name containing `/`, `\`, or `..` before touching the filesystem (`sbbs:src/syncterm/ripper.c` `load_stamp_icon()`; see [Icon Format](3.0-icon-format.md#how-icons-are-referenced-and-stored)). The same rule must apply to every filename an implementation receives - icon loads, block-mode download names, playback requests: reject (do not sanitize-and-accept) anything with path separators, parent-directory references, or drive prefixes, so a hostile host cannot write or read outside the two asset directories. Extension defaulting still applies after validation (a name with no `.` gets `.ICN` appended on icon loads).
