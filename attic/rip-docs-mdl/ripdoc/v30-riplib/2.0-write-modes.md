# 2.0 Write Mode Numbering

[◀ Prev: Contents](README.md) · [Contents](README.md) · [Next: 9.0 Command Inventory Comparison ▶](9.0-command-inventory-comparison.md)

_Disposition: **callable.** Delta against [RIP_WRITE_MODE in the 3.0 reference](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_write_mode). See the [tree README](../README.md) for how the two records' evidence compares._

The two projects assign different bitwise operations to the same `|W` values. This is the highest-impact disagreement between them: it needs no new content to bite, produces no error on either side, and mis-renders in both directions.

## The tables

| `\|W` value | This repository  | RIPlib                      | Agrees? |
| ----------- | ---------------- | --------------------------- | ------- |
| `00`        | COPY (overwrite) | COPY - `dst = src`          | yes     |
| `01`        | **XOR**          | **OR** - `dst = dst \| src` | **no**  |
| `02`        | **OR**           | **AND** - `dst = dst & src` | **no**  |
| `03`        | **AND**          | **XOR** - `dst = dst ^ src` | **no**  |
| `04`        | NOT (inverse)    | NOT - `dst = ~dst`          | yes     |

RIPlib's assignment is in `include/drawing.h:81-84` (`DRAW_MODE_OR 1`, `DRAW_MODE_AND 2`, `DRAW_MODE_XOR 3`, `DRAW_MODE_NOT 4`) and in `docs/spec/02-level0-drawing.md` §2.3.

## The evidence

**Four independent sources put XOR at `01` and OR at `02`.**

1. **The 1.54 published specification** defines `|W` with two values - `00` normal, `01` XOR - and describes the effect unambiguously: _"the pixel is inverted (black changes to white, red to green, etc.). Drawing the same item a second time erases it completely."_ ([1.54 RIP_WRITE_MODE](../../1.54/ripscrip/2.0-colors-and-attributes.md#rip_write_mode))
2. **The 1.54 specification's put-mode table**, on a different command, spells out the same ordering across all its defined values: `00` COPY, `01` XOR, `02` OR ([RIP_PUT_IMAGE](../../1.54/ripscrip/4.0-images-and-icons.md#rip_put_image)).
3. **The 2.00 Alpha 4 draft** extends `|W` to the full five-value table - `00` COPY, `01` XOR, `02` OR, `03` AND, `04` NOT - and the [3.0 reference](../../3.0/ripscrip/2.0-color-modes-and-palettes.md#rip_write_mode) carries it forward, corroborated by the `RIP_WriteMode` entry in the RIPtel help inventory, **44 uses across 35 files** in the RIPtel demo corpus, and SyncTERM (`sbbs:src/syncterm/ripper.c:14062`). The corpus's `03` uses are masking effects, consistent with AND.
4. **RIPlib's own disassembly of `RIPSCRIP.DLL` 3.0.7 agrees.** `§DEAD.3` records that the DLL _"accepted mode values 0-4 on the wire but only implemented COPY (0), XOR (1), and OR (2) internally"_ - `1` = XOR, `2` = OR, matching every source above. `spec (11 §DEAD.3)`

**No source has been identified for `01` = OR / `03` = XOR.** It is not the 1.54 text, not the 2.00a4 table, not the Borland BGI convention the language borrows from (BGI's `putimage` operators are `COPY_PUT` 0, `XOR_PUT` 1, `OR_PUT` 2, `AND_PUT` 3, `NOT_PUT` 4 - again XOR at 1), and not the DLL.

## How the divergence arose

RIPlib records the renumbering as a bug fix, `§BUG.7`:

> _"The DLL internal constants were 0=COPY, 1=XOR, 2=OR. The protocol wire values are 0=COPY, 1=OR, 3=XOR. Implementations that used the DLL constants instead of wire values would swap XOR and OR for every BBS connection."_ `spec (11 §BUG.7)`

Read against the sources above, the two halves of that sentence are the same ordering: what `§BUG.7` calls the DLL's _internal_ constants are what the specifications document as the _wire_ values. The premise that a separate, differently-ordered wire numbering exists is the part that has no support - and `§DEAD.3`, elsewhere in the same document, describes the DLL's behavior in the specification's terms without remarking on any conflict.

The most likely explanation is a transcription slip early on that later got rationalized into a deviation register; nothing about it looks deliberate. Nothing else in RIPlib depends on the ordering, so it is cheap to correct.

## Why it matters

- **`|W01` is the historically common non-copy mode.** It is the one the 1.54 specification documents and the one legacy scenes use for rubber-band effects and draw-twice-to-erase animation. On a RIPlib terminal it becomes OR - and OR never erases, so those effects leave residue and animations smear.
- **`|W03` inverts the error.** The 3.x corpus uses `03` for AND masking; RIPlib renders it as XOR.
- **`00` and `04` agree**, and the corpus uses COPY almost exclusively - which is why the conflict may not surface in casual testing, and why it is worth fixing before content that depends on it exists.
- **Nothing detects it.** Both sides parse the value, both render something, neither errors.

## Resolution

The change is a four-line edit to `include/drawing.h` plus the `§BUG.7` entry and the `docs/spec/02-level0-drawing.md` §2.3 table. Two checks would confirm it independently of this repository's reading, using sources RIPlib already holds:

- **Re-read the `|W` handler in `RIPSCRIP.DLL`** and note which pixel operation each accepted wire value reaches. `§DEAD.3` implies the answer is `1` → XOR.
- **Grep a 1.5x-era corpus for `!|W01`** and check whether the surrounding scene draws the same object twice - the erase idiom only makes sense under XOR.

If those agree, the resolution is to adopt `01` XOR, `02` OR, `03` AND, `04` NOT and retire `§BUG.7`. This repository's [3.1-riplib write-modes page](../../3.1-riplib/ripscrip/2.0-write-modes.md) records the knock-on effect on §A2G.1, which presents AND and NOT as v3.1 additions although both have been documented since 2.00 Alpha 1.
