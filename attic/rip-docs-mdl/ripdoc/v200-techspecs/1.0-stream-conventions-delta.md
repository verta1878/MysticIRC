# 2.x Stream Conventions (delta from 1.54)

[Contents](README.md) · [Next: Canvas Tiers, Palette & RGB ▶](2.0-canvas-palette-rgb.md)

The byte-level line grammar of a `.RIP` stream - the `!|` introducer, `|` command delimiter, `\` line continuation and quoting, raw-text pass-through, CR/LF handling - carries over from 1.54 unchanged and is documented in the [1.54 stream & file parsing page](../../1.54/techspecs/1.0-rip-stream-parsing.md); the language-level syntax rules (parameter widths, shortening, escaping) are in the 2.x specification's [Protocol Definition](../ripscrip/1.1-protocol-and-command-hierarchy.md) and are not restated here. What follows is what is **new on the 2.x wire** and what the **shipped 2.x script corpus actually does** - the conventions of the only known authentic RIPscrip 2.x-generation content, which any implementation must play back correctly.

The corpus: the **36 `.RIP` scripts** in the RIPterm 2.30 distribution's `ICONS\` directory (`~/src/rip-tools/artifacts/ripterm-2.30/extracted/ICONS/*.RIP`, preserved byte-exact in [`version/2.0/assets/icons/`](../../2.0/assets/icons/README.md)), plus the RIPterm Professional 2.0 original of `SHADOW.RIP` (`~/src/rip-tools/RIPTerm2.0/extracted/ICONS/SHADOW.RIP`) - the sole script the 2.0 install shipped, and the only one TeleGrafix later revised, making the pair a unique before/after sample of their own authoring conventions. Every claim below was verified programmatically across all 37 files (byte scans, 2026-08-08); observations that could not be cross-checked against a specification or binary are marked.

## The SOH introducer - `\x01|`

The 2.x specification (rule 12, [Protocol Definition](../ripscrip/1.1-protocol-and-command-hierarchy.md#ripscrip-protocol---syntax-and-general-structure), v2.A3) adds two alternate introducers to the 1.54-only `!`: **Ctrl-A (SOH, byte `0x01`) and Ctrl-B (STX, byte `0x02`)** may replace the exclamation mark, and - unlike `!|` - may start a RIPscrip sequence **mid-line**, after raw text, because BBS hosts strip control characters from user input and so only the host can emit them. The spec's own example is `This is raw text<STX>|c01|@1010hello world`.

What the shipped corpus does with this license is narrower and very consistent:

- **Exactly 18 of the 36 scripts begin with byte `0x01` at file offset 0**, immediately followed by `|` - e.g. `SHADOW.RIP` opens `01 7C 2A 0D 0A` = `\x01|*` + CRLF (SOH, then [RIP_RESET_WINDOWS](../ripscrip/1.3-world-view-virtual-canvas.md#rip_reset_windows)).
- **SOH never appears anywhere except offset 0.** No file uses it mid-line or on a later line; every subsequent command line uses the classic `!|`.
- **STX (`0x02`) never appears at all** in any shipped 2.x-generation script.
- The 18 files without SOH (the 14 `CYC*` palette-cycle fragments and `EXAMPLE1`-`4`) open with plain `!|`.

So in practice TeleGrafix used SOH as a **start-of-scene marker on the first line of a standalone scene file** - the reading the RIPscrip 3.0 corpus later makes systematic (111 of 116 RIPtel demo files; see the [3.x protocol notes](../../3.0/ripscrip/1.1-protocol-and-command-hierarchy.md)). The revised `SHADOW.RIP` is the clearest evidence that this was a deliberate 2.2-era convention: the 2.0 original opens with the line `!|l7040B040`, and the 2.20/2.30 revision **replaces that line with `\x01|*`** (see [the revision](#the-shadowrip-revision---a-beforeafter-sample) below).

**What a parser must tolerate:**

- Accept `\x01|` and `\x02|` wherever `!|` is accepted - including as the very first bytes of a file - and additionally mid-line after raw text, per the spec rule. A 1.54-only parser that requires `!` will treat the whole first line as raw text and lose the scene's reset.
- Do not require SOH: half the shipped corpus lacks it, and `!|` remains fully valid on line 1.
- After the introducer, parsing is identical to `!|`: commands separated by `|`, terminated by CR/LF or continued with `\`.

## Prologue conventions

Openers across the corpus, by first bytes of the file:

| Opener (observed bytes) | Files | Meaning |
| --- | --- | --- |
| `\x01\|*` … | DEMOFILE, EAGLE, HAWK, N2_BUSI, N2_PHOTO, N2_TITLE, SHADOW | SOH + reset first |
| `\x01\|1K\|*` … | FOUND, FRACTMTN, RACECAR, SAILBOAT, SHUTTLE, SPACSHUT, TUNNEL | SOH + [RIP_KILL_MOUSE_FIELDS](../ripscrip/4.2-mouse-fields-and-pointer.md#rip_kill_mouse_fields), then reset |
| `\x01\|1K\|w0000000000\|*` … | WEATHER | kill fields, define text window, then reset |
| `\x01\|D…` | FADEIN, FADEOUT | SOH + bulk [RIP_SET_PALETTE](../ripscrip/2.0-color-modes-and-palettes.md#rip_set_palette) - **no reset**: palette-fade effects meant to run over an existing scene |
| `\x01\|J10\|n2000\|M08\|fZKQO…` | NEWS | SOH + full setup prologue - **no reset anywhere in the file** |
| `!\|d…` | CYC001DN … CYC111UP (14 files) | no SOH, no reset: palette-cycle animation fragments |
| `!\|J10\|n2000\|M08\|fZKQO\|1b…` | EXAMPLE1-EXAMPLE4 | no SOH, no reset: setup prologue directly |

Two prologue idioms recur:

- **The reset opener** - `|*` (RIP_RESET_WINDOWS), usually preceded by `|1K` so stale mouse fields from the previous scene cannot fire during the redraw. 15 of 36 files contain a reset - 14 exactly one, plus DEMOFILE's playlist, which issues 17 (one before each chained scene); the files without one are deliberately non-destructive (palette fragments, fades, and NEWS, which paints over the full screen).
- **The setup block `!|J10|n2000|M08|fZKQO`** - set Base Math to [MegaNums](../../glossary.md#protocol--syntax) (`J10` - note the shipping engines' level-0 `J` opcode vs the ALPHA 4 draft's colliding `b`; see the [RIP_SET_BASE_MATH editor's note](../ripscrip/1.2-math-and-coordinates.md#rip_set_base_math)), 2-digit coordinates ([RIP_SET_COORDINATE_SIZE](../ripscrip/1.2-math-and-coordinates.md#rip_set_coordinate_size)), color-mapping mode with 8-bit palette ([RIP_SET_COLOR_MODE](../ripscrip/2.0-color-modes-and-palettes.md#rip_set_color_mode)), and a 1280×960 world frame ([RIP_SET_WORLD_FRAME](../ripscrip/1.3-world-view-virtual-canvas.md#rip_set_world_frame), `ZK`=1280, `QO`=960). EXAMPLE1-4 and NEWS open with it; thirteen more files carry the identical block in their branding footer (below). It restates the post-reset defaults - the corpus treats explicit state setup as cheap insurance, and the exact same block opens 90 of 116 RIPtel scripts ([3.x notes](../../3.0/ripscrip/1.1-protocol-and-command-hierarchy.md)).
- **Client-chrome queries** - DEMOFILE and the three `N2_*` files follow the reset with `|1\x1b0000$SBAROFF$`: [RIP_QUERY](../ripscrip/5.5-file-transfer-and-queries.md#rip_query) (level 1, command character = the literal **ESC byte `0x1B`**) carrying the `$SBAROFF$` text variable to hide the client's status bar before the scene draws.

## Epilogue conventions

- **`!|#|#|#`** - a triple [RIP_NO_MORE](../ripscrip/1.1-protocol-and-command-hierarchy.md#rip_no_more) is the standard scene terminator: **20 of 36 files end with exactly the line `!|#|#|#`** (CRLF-terminated). NEWS.RIP ends with it twice on consecutive lines. The files without it are the 14 `CYC*` fragments and FADEIN/FADEOUT - the non-scene animation/palette fragments, which contain no `#` at all.
- **The demo-branding footer** - 14 files close with a shared block (EAGLE, EXAMPLE1-4, FOUND, FRACTMTN, HAWK, NEWS, SAILBOAT, SHADOW, SHUTTLE, SPACSHUT, TUNNEL): the `!|J10|n2000|M08|fZKQO` setup restated, an Atech font selection ([RIP_EXTENDED_FONT_STYLE](../ripscrip/3.0-text-output-and-fonts.md#rip_extended_font_style) `|y…Dixon`), a [RIP_BUTTON_STYLE](../ripscrip/4.3-buttons.md#rip_button_style) + [RIP_BUTTON](../ripscrip/4.3-buttons.md#rip_button) pair whose button carries an empty `<><>` icon/label/host-command triple (a decorative beveled plaque), and two [RIP_TEXT_XY](../ripscrip/3.0-text-output-and-fonts.md#rip_text_xy) lines - a copyright line (usually "Copyright ¿ 1995 TeleGrafix Communications, Inc.", the `¿` is byte `0xA8` read as CP437 and the Dixon outline font evidently maps it to a © glyph) and "For Demonstration Purposes Only" - then `!|#|#|#`. Example, the FRACTMTN.RIP tail:

```text
!|J10|n2000|M08|fZKQO|y00000W0M000000001a1a000000Dixon
!|1B0000020PVK040F000F080700000F07000000|1U05ODCDQI0000<><>|c00|W03
!|y00000W0L000000001a1a000000Dixon
!|@5YP5Copyright ¿ 1995 TeleGrafix Communications, Inc.
!|@68Q0For Demonstration Purposes Only|#|#|#
```

Three more files carry part of it: WEATHER.RIP has the font and both branding text lines but no button; N2_BUSI.RIP has the font and a copyright line with variant wording ("For Demonstration Purpose Only!"); N2_TITLE.RIP and N2_PHOTO.RIP close with a bare `!|J10|n2000|M08|fZKQO|#|#|#`. Eighteen files carry the setup block somewhere.

- **Trailing line ending** - every file's last line is CRLF-terminated; FADEOUT.RIP and the 2.0-era SHADOW.RIP additionally end with one blank line (a bare final CRLF). No file ends mid-line.

## Line structure, endings and lengths

- **CRLF exclusively.** All 37 surveyed files use `\r\n` on every line - zero lone `\n`, zero lone `\r` (significant: the RIPtel corpus does contain bare-CR files, but no 2.x-generation one does).
- **Command lines keep an 80-column discipline: the longest line beginning `!|` or `\x01|` in the corpus is 78 bytes** (EAGLE.RIP polygon lines, including their trailing `\`). Continuation payload lines reach 77 bytes.
- **Raw text lines do not honor that limit: NEWS.RIP contains a 104-byte flowed-text line** ("Pirating the software is the same as robbing us of the dream. Would you want someone to ruin your dr…"). A parser must not clamp or split lines at 80 bytes.
- **`\` continuation is heavy production traffic, not an edge case.** 7 files use it; FADEIN.RIP is 1,024 physical lines of which **960 are continuations** - 64 RIP_SET_PALETTE commands, each spanning ~16 physical lines (~1,070 argument characters). Continuation lines carry **no introducer** - they are bare argument bytes (e.g. EAGLE.RIP line 2 ends `…4D79\`, line 3 opens `4U6L52…`), so a parser mid-command must consume the next physical line as argument data, not restart line classification.
- **Command density** - multi-command lines are the norm: up to 13 `|`-separated commands per line (`FRACTMTN.RIP`, e.g. line 42: twelve RIP_PIXEL plus a RIP_COLOR), and DEMOFILE's playlist puts a scene load plus two delays on one line: `!|*|1R00000000TUNNEL.RIP|3D008C|3D0060`.

## Raw text and modal text flow

Rule 6 of the protocol (a line not beginning with an introducer is raw text for the [text window](../../glossary.md#display-model)) carries over from 1.54 - but the corpus shows a **second, modal meaning** of raw lines: NEWS.RIP defines four linked text-column regions with [RIP_BEGIN_TEXT](../ripscrip/3.0-text-output-and-fonts.md#rip_begin_text) (`|1T…01/11/21/31`) and then flows its multi-paragraph newspaper article as **dozens of raw text lines with no introducer at all**, which the client pours into the graphics-side columns - not the TTY text window. Blank raw lines separate paragraphs. Notably, NEWS.RIP never sends the spec's [RIP_END_TEXT](../ripscrip/3.0-text-output-and-fonts.md#rip_end_text) (`|1E`) or the spec's per-line [RIP_REGION_TEXT](../ripscrip/3.0-text-output-and-fonts.md#rip_region_text) wrapper: the flow simply ends when the next `!|` command line arrives. The full column/stream mechanism was only formalized in 3.0 - the reconstruction, which uses this same NEWS.RIP as evidence, is in the [3.x column-text-system page](../../3.0/ripscrip/3.1-column-text-system.md); a 2.x implementation needs at minimum the modal rule: after a `1T` region definition, raw lines are flowed article text until a command line ends the block.

## Multi-level command parsing notes

Observed level usage across all shipped 2.x-generation scripts:

- **Levels 0, 1 and 3 only.** No shipped script uses level 2, level 9, or any multi-digit sub-level (`|15L`-style, spec rule 8) - those paths ship untested by original content.
- **Level 3 interleaves freely with level 0** as animation pacing: each `CYC*` file is 64 repetitions of `!|d<entry><bits><rgb>|3D0001` - one [RIP_ONE_DRAWING_PALETTE](../ripscrip/2.0-color-modes-and-palettes.md#rip_one_drawing_palette) step (UltraNum RGB argument regardless of Base Math) followed by a one-tick [RIP_DELAY](../ripscrip/5.5-file-transfer-and-queries.md#rip_delay). DEMOFILE chains whole scenes with `|1R` ([RIP_READ_SCENE](../ripscrip/5.5-file-transfer-and-queries.md#rip_read_scene)) plus `|3D` delays.
- **The command-type character can be a control byte.** Five files (DEMOFILE, N2_BUSI, N2_PHOTO, N2_TITLE, TUNNEL) use `|1\x1b` - RIP_QUERY's command character is the literal ESC byte `0x1B`, the only non-printing command character in the corpus. Tokenizers that assume printable command characters will mis-parse these files.
- **Level parsing rule** (unchanged from the spec): after `|`, consume decimal digits `1`-`9` as the level/sub-level string (a leading `0` is not a level digit), then exactly one command-type character, which may be any character from the spec's set - plus, per the corpus, ESC.

## Repeated state-sets - the `|k00` pattern

`|k` is [RIP_BACK_COLOR](../ripscrip/2.0-color-modes-and-palettes.md#rip_back_color). The 2.0-era SHADOW.RIP emits `|k00` (background = color 0) **160 times** - once on nearly every one of its 170 text-drawing lines, alongside 5 `|k0A` and 5 `|k0C`; the 2.30 revision keeps the drawing identical but strips the redundant repeats down to 10 `|k00` (the `|k0A`/`|k0C` uses survive unchanged). Elsewhere the corpus still carries scattered redundant state-sets (`|k00` once in each `N2_*` file, twice in WEATHER). Implication for implementers: authored 2.x-generation streams re-assert unchanged state constantly; state commands must be cheap and idempotent, and stream-diffing tools should expect this noise.

## The SHADOW.RIP revision - a before/after sample

The only script shipped by RIPterm Professional 2.0, and the only one TeleGrafix ever revised (2.0 original 12,485 bytes, dated 1995-02; 2.20/2.30 revision 12,157 bytes, dated 1995-11-28 - see the [asset notes](../../2.0/assets/icons/README.md#shadowrip)). The full delta, byte-verified:

|  | 2.0 original | 2.20/2.30 revision |
| --- | --- | --- |
| Opening line | `!\|l7040B040` | `\x01\|*` |
| `\|k00` count | 160 | 10 |
| Branding footer + `!\|#\|#\|#` | absent (file ends on a text line + blank line) | present |
| Physical lines | 184 | 194 (commands re-wrapped) |
| Drawing content | identical drop-shadow text demo ("RIPterm Pro 2.0"), 170 `\|y`/`\|c`/`\|@` text draws | identical |

The discarded opener `!|l7040B040` deserves a parser note: in the ALPHA 4 specification, level-0 `l` is [RIP_POLYLINE](../ripscrip/2.1-lines.md#rip_polyline), but the arguments do not parse as one (`70` would declare 252 points with only 8 argument characters following). Whether it is a pre-release 2.0 command or simply malformed is **not established** - what matters is that the shipping 2.0 client visibly played the file anyway, i.e. it discarded the unparseable command per the spec's corruption rule (rule 15: a hopelessly corrupted command is dropped and the parser resynchronizes at the next `|` delimiter - here, end of line). An implementation should do the same: skip, don't abort.

## What carries over from 1.54 unchanged

Everything not listed above - verified present and unchanged across the corpus:

- The `!|` introducer at column 0, `|` as universal command delimiter, and multiple commands per line ([1.54 stream parsing](../../1.54/techspecs/1.0-rip-stream-parsing.md)).
- `\`-before-CRLF line continuation and `\`-quoting of literal `!`, `|`, `\` in text parameters (spec rules 5, 11, 13 - the quoting corner cases carry v1.54 tags in the 2.x spec).
- Raw-text pass-through to the text window for lines without an introducer (modal column-flow excepted, above).
- MegaNum base-36 parameters as the default numbering ([1.1 MegaNum encoding](../../1.54/techspecs/1.1-meganum-encoding.md)); the 2.x additions - Base Math switching and UltraNum parameters - are language-level and covered by the [glossary](../../glossary.md#protocol--syntax) and the 2.x spec pages.
- CRLF line termination as authored; the corpus contains no counterexample requiring bare-LF or bare-CR tolerance, though accepting them costs nothing and the 3.x corpus does require bare-CR handling.
