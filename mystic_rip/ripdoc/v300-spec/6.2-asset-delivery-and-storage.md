# 6.2 Asset Delivery & Storage

[◀ Prev: 6.1 Content File Roles](6.1-content-file-roles.md) · [Contents](README.md) · [Next: 7.0 Drawing Ports ▶](7.0-drawing-ports.md)

_Reconstructed edition - every claim carries an evidence tag; see [Contents](README.md) for the legend._

How a host gets content files onto the terminal and where they land: the query-then-download workflow, the block-mode extension routing table, RIPtel's per-bookmark host directory, the shared default icon directory, and the "file override" lookup order.

_The 2.0 model this carries forward is [6.2 of the v2.0 reference](../../2.0/ripscrip/6.2-asset-delivery-and-storage.md) (1.54 lineage in the [v1.54 page](../../1.54/ripscrip/6.2-asset-delivery-and-storage.md))._

## The delivery workflow

_Evidence: 2.00a4; HLP._

A well-behaved host delivers assets in two steps:

1. **Staleness check** - [RIP_FILE_QUERY](5.5-file-transfer-and-queries.md#rip_file_query) asks whether a file already exists on the terminal's disk, and (modes 02-04) its size, date and time. The host compares the response against its own copy to decide whether a download is needed at all - the host side of the 3.x resource-caching story. Terminals that store audio in a translated local format must answer as if the WAVE original were on disk ([4.5](4.5-audio-files.md)). _Evidence: 2.00a4; HLP (`RIP_FileQuery`); SyncTERM (ripper.c:16104) - not observed in the RIPtel demo corpus, whose scenes are local and have no host to answer._
2. **Download** - [RIP_ENTER_BLOCK_MODE](5.5-file-transfer-and-queries.md#rip_enter_block_mode) auto-initiates a file transfer (Xmodem variants, Kermit, Super Kermit, Ymodem, Ymodem-G, or Zmodem with or without crash recovery - protocol table in [5.5](5.5-file-transfer-and-queries.md#rip_enter_block_mode)) with a file-type code telling the terminal what it is receiving - `.RIP` scenes to display or store, generic files, icons, or images to display on arrival. RIPtel itself uses Zmodem for its actual transfers. Over 7-bit-only links, [RIP_BEGIN_UUENCODE_BLOCK](5.5-file-transfer-and-queries.md#rip_begin_uuencode_block) embeds the same content as UU-encoded text _(v2.A1)_ - renamed `RIP_BeginEncodedStream` in the 3.0 driver. _Evidence: 2.00a4; HLP (`RIP_EnterBlockMode`, `RIP_BeginEncodedStream`, DLL exports `RIP_GetBlockModeFilename`/`RIP_GetBlockModeTransferType`); SyncTERM (ripper.c:17069) - not observed in the RIPtel demo corpus._

Once delivered, the host uses the assets by name - stamping icons, displaying images, playing audio, replaying scenes - with no further transmission cost, from the command stream (chapter 4) or from [host commands](../../glossary.md) via the playback prefixes ([5.3](5.3-local-playback.md)).

Uploads work through the same block-mode command with mode 1; the user can be prompted to authorize them (RIPtel asks "Upload file(s) '%s'?"), and an unauthorized upload is refused with ten CAN (Ctrl-X) characters. _Evidence: 2.00a4; HLP._

Housekeeping: the [`$FILEDEL(file,…)$`](5.1-text-variables.md#filedel) [text variable](../../glossary.md) lets the host delete files it created and no longer needs - no wildcards, no paths. The target "must be a filename that the host created, or downloaded to the terminal via RIP*ENTER_BLOCK_MODE or by some other means", and path information "will be ignored", so a host names a bare file and the terminal resolves it. \_Evidence: 2.00a4; HLP.* _(The v2.A3 revision notes also announced a `RIP_FILE_DELETE` command, but no entry for it exists in the ALPHA 4 draft and no such command name appears in the RIPSCRIP.HLP inventory - the variable form is the 3.x mechanism, implemented as `tvarProcFILEDEL`.)_

> **Editor's note - implementation guidance, not specification.** No specification states which directory `$FILEDEL$` resolves against. Two of its own rules settle it in practice: deletion is limited to files _the host created_, and the host cannot supply a path. Since host deliveries land in the connection directory when one is configured, the safe reading is that `$FILEDEL$` should delete from the **connection directory only** and leave the shared default directory alone - files there may predate the session or belong to another host. This mirrors the lookup order in reverse: reads fall back from the connection directory to the shared default, but deletes should not. _(hypothesis)_ - inference from the spec's constraints and the storage model above; no shipping client has been examined to confirm it.

## Block-mode routing - the extension table

_Evidence: 2.00a4._

In the batch DYNAMIC file types, the terminal routes each received file by extension _(v2.A0)_:

| Extension | COMPOSITE DYNAMIC (type 4) | ACTIVE DYNAMIC (type 5) |
| --- | --- | --- |
| `RIP` | Store in proper directory | Store **and play back** locally |
| `BMP` | Place icon in proper directory | Place icon in proper directory |
| `BMH` | Place hot icon in proper directory | Place hot icon in proper directory |
| `BMM` | Place mask icon in proper directory | Place mask icon in proper directory |
| `JPG` | Store in proper directory | Store **and display** per image settings |
| `GIF` _(v2.A4)_ | Store in proper directory | Store **and display** per image settings |

Files with any other extension are placed in the appropriate host directory with no further processing - which is how `.WAV` audio arrives, since it is absent from the table. "Proper directory" always resolves through the connection-directory model below, never through the user's ordinary download directory. (The `GIF` row is paper-only in 3.x - no shipped client decodes it; see [6.1](6.1-content-file-roles.md).)

## Where files land

_Evidence: HLP (RIPTEL.HLP "Host Directory", "Icon Search Path", "Download Directory"/"Upload Directory" topics - survey in the [techspec](../techspecs/4.0-connection-directory-model-delta.md))._

The 3.x client carries the 2.0 storage model forward intact and renames its surface. Every host-deliverable media type still flows through **one directory family** - there is no separate audio, image, or scene directory:

- The **default icon directory** (`ICONS\`) houses the whole host-deliverable media family: `.BMP`/`.BMH` icons (and legacy `.ICN`), `.JPG` images, `.WAV` sounds, and the script containers. RIPtel's installer creates `ICONS`, `FONTS`, and `Files` under the install root.
- Each **bookmark** (RIPtel's name for a dialing-directory entry) can name a per-host sub-directory - the **host directory**, the 3.x name for the connection directory (RIPterm 2.30's "System Dir", the 1.54 manual's DIR field) - configured in the bookmark editor's Advanced options. When one is specified, any icon, RIPscrip, sound, or image files sent by the host are automatically placed there. New bookmarks import their defaults from RIPtel's setup configuration, and auto-creation carries over from the DOS clients: "Many online services create their own host directories for you, without your knowledge."
- **New constraint in 3.x** - the host directory can only exist under the directory where the client is installed: "For security reasons, the host directory cannot exist in any arbitrary location on your hard drive." Directories the _host_ can populate are jailed under the install root; directories only the _user_ configures (the search path, below) may live anywhere. Implementations should preserve this property - host-influenced writes stay inside a client-owned sandbox.
- **New third lookup tier in 3.x** - the setup-level, user-configurable **icon search path**: extra directories consulted only after the two classic tiers fail, aimed at CD-ROM-distributed resource sets. Multiple directories are separated by semicolons (`C:\Windows;D:\;Icons\MyIcons`). The search path is **lookup-only** - host deliveries never write there.
- **Fonts are the exception** - stroked, outline and terminal fonts are global client resources resolved only from the font store (`FONTS\`), never per connection ([6.1](6.1-content-file-roles.md)).
- **User file transfers stay outside the model** - ordinary Zmodem downloads land in a `Files` directory (with separate user-configurable download and upload directories), a different namespace from host-deliverable resources, exactly as in the 2.0 block-mode rule.

## Lookup order ("file override")

_Evidence: HLP (RIPTEL.HLP "Host Directory" topic)._

When a command or playback variable references a file by name, the terminal searches the **host directory first**, then the default `ICONS\` directory, then the icon search path entries in order; first hit wins, and an error is reported only after all tiers fail. RIPTEL.HLP states the order outright: the client "will look for these kinds of files in that directory first. If the file cannot be found, then it checks the ICONS\ directory. If the file still cannot be found, then [it] checks any additional search directories that you have defined." The macro layer documents the same resolution order for the local-playback prefixes (`$>FILE.RIP$`, `$)FILE.WAV$`, `$<FILE.BMP$`, `$(FILE.JPG$` - [5.3](5.3-local-playback.md)).

The point of the scheme is unchanged from 2.0: same-named assets from different hosts do not collide - each host's `MENU.BMP` resolves to that host's own copy, while genuinely shared assets can live once in `ICONS\`. The RIPterm manuals call this behavior "file override". Commands never carry path information - filenames are bare DOS-style names, and the terminal decides where they resolve. (Modern implementations should also treat lookups as case-insensitive, as the DOS originals inherently were - see the [connection directory model techspec](../techspecs/4.0-connection-directory-model-delta.md).)

## Programmatic surface

_Evidence: HLP ([help extraction §3, §5](../../3.0/research/riptel-help-extraction.md))._

The directory model is reachable programmatically in 3.x, not just via configuration: the RIPscrip 3.0 function-name table includes **`RIP_SwitchDirectory`** among the wire commands - presumably switching the terminal's host/resource directory context - the client API exports `RIP_SetHostDirectory`/`RIP_GetHostDirectory`, and the text-variable processor list includes a `HOSTDIR` handler _(hypothesis: host-directory control)_. Wire-level semantics of `RIP_SwitchDirectory` are otherwise unrecovered - its opcode is unknown and no demo script in the RIPtel corpus exercises it.
