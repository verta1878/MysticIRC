# 1.0 Stream Parsing & Escapes

[Contents](README.md) · [Next: 2.0 Fill Pattern Mapping ▶](2.0-fill-pattern-mapping.md)

_Delta against [`.RIP` Stream & File Parsing](../../1.54/techspecs/1.0-rip-stream-parsing.md) and the [3.x protocol chapter](../../3.0/ripscrip/1.1-protocol-and-command-hierarchy.md). See the [tree README](../README.md) for how each side's evidence should be weighed._

Both projects implement the same parsing model - stream rather than lines, `!|` introducer, `|`-separated commands, fixed-width MegaNum fields, odd/even trailing-backslash continuation. Two smaller items differ.

## The escape set and its attribution

RIPlib's `unescape_text` accepts `\\`, `\|`, `\^`, `\n` and `\!`, attributing the first four to _"spec §1.6 / §7.1"_ and recording `\!` as a deliberate RIPlib extension in `§DEV.1`: `riplib (src/ripscrip.c:737-756)` `spec (11 §DEV.1)`

> _"Spec §1.6 / §7.1 define escapes `\\ \| \^ \n`. RIPlib's `unescape_text` implements all four AND additionally accepts `\!` as a literal '!'. … This is a deliberate, backward-compatible extension."_

⚠ **The attribution is inverted for `\!`.** Syntax rule 11, unchanged from 1.54 through the 2.00 Alpha 4 draft and into the 3.x reconstruction, reads:

> _"An exclamation mark (`!`) or vertical bar (`|`) character can appear in a RIPscrip text parameter by preceding it with a backslash (`\`). … A literal backslash is represented with a double-backslash (`\\`)."_ ([1.54](../../1.54/ripscrip/1.1-protocol-and-command-hierarchy.md), [3.0](../../3.0/ripscrip/1.1-protocol-and-command-hierarchy.md))

Per-escape standing against the published record:

| Escape | Standing |
| --- | --- |
| `\!` | **Specification, since 1.54** - rule 11, alongside `\|`. Not an extension |
| `\|` | Specification, since 1.54 - rule 11 |
| `\\` | Specification, since 1.54 - rule 11 |
| `\^` | Not named by any syntax rule, but **defensible**: `^` is the control-character prefix in host-command text (`^M` = CR), so a literal caret there does need quoting ([9.3 host command reference](../../3.0/ripscrip/9.3-host-command-reference.md#control-character-notation-in-host-commands)) |
| `\n` | **Not in the record** - newlines in text parameters are not escape-encoded |

**Disposition: callable, and harmless in effect.** Nothing renders differently either way; SyncTERM's preprocessor collapses any unknown `\X` to `X`, so `\^` and `\n` already yield `^` and `n` there. The correction is bookkeeping: `\!` moves out of `§DEV.1` and the deviation register loses another entry.

### One escape class RIPlib does not cover

Since v2.A3 the specification also requires **host-command metacharacters** to be quoted inside text parameters that reach the host-command layer - `$`, `[`, `]`, `(` and `)`, written `\$Name\$` and so on ([3.0 syntax rule 11](../../3.0/ripscrip/1.1-protocol-and-command-hierarchy.md)). This is not a conflict, just a gap worth flagging: without it, a mouse-field or button host string containing a literal `$` is interpreted as a text-variable reference. It matters more in practice than `\^` does, because the corpus leans heavily on `$…$` inside host commands.

## Alternate command introducers

RIPlib's baseline recognizes `!` as a command introducer at four positions - first byte of the stream, or immediately after CR (`0x0D`), LF (`0x0A`) or FF (`0x0C`) - and passes a mid-line `!` through as literal text. `spec (01 §1.8)` That matches the specification.

**What is missing is the rest of the rule.** Syntax rule 12 allows `!` to be replaced by **SOH (`0x01`)** or **STX (`0x02`)**, and those two are accepted _anywhere_ in a line - deliberately a host-only capability, since BBS users could not readily type control characters. SyncTERM implements exactly this split (`cb_accept_introducer()` accepts `!` only at line start, SOH/STX anywhere), and it is not a curiosity: the shipped 2.x script corpus opens with the SOH form, `\x01|*` ([2.0 stream conventions](../../2.0/techspecs/1.0-stream-conventions-delta.md)).

**Disposition: callable.** A `RIPSCRIP03`-class terminal that does not honor SOH/STX will fail to start scenes that shipping content already uses. It also matters for the other direction: RIPlib's v3.1 relaxation - accepting `!` after an ANSI CSI terminator, documented in [3.1-riplib techspecs](../../3.1-riplib/techspecs/1.0-stream-parsing-delta.md) - exists to solve the mid-line introducer problem that SOH/STX already solves portably. Implementing rule 12 makes that extension unnecessary, and avoids its side effect of turning an exclamation mark after a color change into a command.
