# UI Resources (.FNT / .IMG)

[◀ Prev: Audio](3.4-audio.md) · [Contents](README.md) · [Next: Connection Directory Model ▶](4.0-connection-directory-model-delta.md)

RIPterm draws its own user interface - dialogs, menus, check-boxes, radio buttons - with a private set of per-resolution assets: four proportional UI fonts (`0640X350.FNT`, `0640X480.FNT`, `0800X600.FNT`, `1024X768.FNT`) and twenty-six planar widget images (`*.IMG`). These are client resources, not wire formats, but they are direct evidence of the 2.x engine's resolution-scaled UI and their formats are documented nowhere else. The RIPterm 2.0 install ships them as loose files in `FONTS\`; in the definitive 2.30 distribution the loose files are gone from `FONTS\` while `RIPTERM.EXE` still carries every one of the filenames as strings - the assets evidently moved into the client's own resource packaging, a detail of the original software that doesn't affect the formats documented here _(cf. the [resource-container research notes](../../3.0/research/riptel-resource-containers.md))_. The loose files are preserved byte-exact in [`version/2.0/assets/fonts/`](../../2.0/assets/fonts/README.md).

All integers little-endian. Source files: `~/src/rip-tools/RIPTerm2.0/extracted/FONTS/`.

## `.IMG` widget images - format (decoded)

Small 16-color images for the check-box and radio-button controls, pre-scaled for each display resolution (640×350, 640×480, 800×600, 1024×768, 1280×1024 - the numeric infix is the vertical resolution, `1024` meaning the 1280×1024 set) plus one TeleGrafix glyph. Layout, verified against all 26 files (the size formula `12 + 4 × height × bytesPerPlaneRow` matches every file exactly):

```c
struct ImgWidget {                   /* 12-byte header */
    uint16_t width;                  /* logical image width in pixels */
    uint16_t height;                 /* rows */
    uint16_t bitShift;               /* pre-shift of the raster, in pixels (see below) */
    uint16_t bytesPerPlaneRow;       /* row stride of one plane, in bytes */
    uint16_t always1;                /* observed 1 in all files; meaning unverified */
    uint16_t always4;                /* observed 4 in all files; plane count (unverified) */
    /* followed by 4 × height × bytesPerPlaneRow bytes of pixel data */
};
```

Pixel data is **plane-sequential**: all `height` rows of plane 0, then plane 1, plane 2, plane 3. Bit _p_ of a pixel's 4-bit color index comes from plane _p_ (EGA order: blue, green, red, intensity), MSB = leftmost pixel. The raster is stored **pre-shifted right by `bitShift` pixels** - the EGA-era optimization of baking the destination bit alignment into the image so it can be latched to the screen without run-time shifting. The logical image occupies pixel columns `[bitShift, bitShift + width)` of each `bytesPerPlaneRow × 8`-pixel row; columns outside that window are junk (background fill on the left, uninitialized buffer garbage on the right - several files leak fragments of other shifted copies).

Worked example - `CK350_1.IMG` (204 bytes: 16×12, shift 0, 4 bytes/plane-row), decoded with the rule above; digits are 4-bit color indices (7 = light gray, 8 = dark gray, F = white):

```text
7FFFFFFFFFFFFFF7
F788888888888878
F8777777777777F8
F8777777777777F8      the unchecked check-box face:
F8777777777777F8      white top/left bevel, dark bottom/right,
F8777777777777F8      light-gray fill
F8777777777777F8
F8777777777777F8
F8777777777777F8
F8777777777777F8
F7FFFFFFFFFFFF78
7888888888888887
```

`CK350_2.IMG` (same dimensions, `bitShift = 3`) renders the same box with an X mark inside, its content occupying columns 3-18 of the 32-pixel row - the checked state, pre-shifted. The `_1`/`_2` suffix pairs throughout are the unchecked/checked (radio: unselected/selected) states.

Inventory (dimensions confirmed by header decode; see also the [asset README](../../2.0/assets/fonts/README.md#ui-widget-images-img)):

| Files | Count | Content | width×height per resolution set |
| --- | --- | --- | --- |
| `CHK350/480/600/768/1024.IMG` | 5 | check-mark glyph | 7×8, 8×10, 9×12, 13×16, 15×24 |
| `CK{res}_1/_2.IMG` | 10 | check-box, two states | 16×12, 16×16, 20×20, 25×25, 32×34 |
| `RD{res}_1/_2.IMG` | 10 | radio button, two states | 15×11, 16×17, 20×21, 25×25, 32×35 |
| `TELEGRFX.IMG` | 1 | TeleGrafix glyph | 16×12 |

Note the widget sets extend to a 1280×1024 tier (`*1024*.IMG`), matching the fifth [MicroANSI resolution record](3.3-microansi-fonts.md#resolution-directory-60-byte-records).

## Per-resolution system `.FNT` fonts (partially decoded)

Four proportional bitmap fonts for RIPterm's own dialog/menu text, one per video resolution (the 1024×768 file doubles for 1280×1024 - there is no fifth file). These are **not** MicroANSI containers and not the wire-selectable fonts; RIPTERM.DOC's font-directory rule names the extension family ("All font files end in a .CHR, .FNT, or .FF1 file extension", §2.1.4).

| File           | Size (bytes) | Internal name (Pascal string)          |
| -------------- | ------------ | -------------------------------------- |
| `0640X350.FNT` | 3,211        | `sys08 8x8`                            |
| `0640X480.FNT` | 3,723        | `SYS16 8x13`                           |
| `0800X600.FNT` | 4,165        | `SYS 24 9x13`                          |
| `1024X768.FNT` | 5,573        | `SYS 24 9x13` (same name, larger data) |

Decoded header region (all four files):

```text
0x00  u16   0x1122                  ; magic
0x02  u8    nameLen                 ; Pascal-style length prefix (9, 10, 11, 11)
0x03  char[nameLen] name           ; "sys08 8x8", "SYS16 8x13", "SYS 24 9x13"
…     byte[…]                      ; fixed-size name/style buffer, padded with
                                    ; uninitialized memory (leaked "…ormal" fragments
                                    ; of the string "Normal" appear in 0640X350.FNT)
0x32  char[10] "METAFONTP\0"        ; container tag
0x3C  u32   fileSize                ; equals the file's own byte length in all four
                                    ; files (0x0C8B, 0x0E8B, 0x1045, 0x15C5)
```

Beyond the header the structure is **only partially decoded** and is documented here as observed: at ~0x52 a field group reading `20 FF 08 00 08 00 …` is consistent with firstChar = 0x20, lastChar = 0xFF and an 8×8 cell for `sys08` _(interpretation unverified)_; from 0x11C runs an ascending u16 table of 45 entries with a constant stride of 8 (0x240, 0x248, 0x250, … 0x3A0), consistent with per-glyph data offsets for an 8-byte 8×8 glyph; and the file tail contains what appear to be per-character width bytes for the proportional metrics. The internal pointer tables contain values that overlap the table region itself, so the exact base of the glyph-data pointers has not been established; a full decode needs the loader code in `RIPTERM.EXE` disassembled. Implementers do not need this format - it renders no host-visible content - but any future decode should live on this page.

Evidence that these are the UI fonts: the 2.0 `RIPTERM.EXE` embeds all four filenames (strings `0640X350.FNT` … `1024X768.FNT`) and the internal names match the "sys…" naming; the files are absent from the wire-selectable font systems (BGI `.CHR` by number, FastFont by style name, MicroANSI by text mode).
