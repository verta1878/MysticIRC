# Icon Format (`.ICN` / `.MSK` / `.HIC`)

[◀ Prev: Pattern & Fill Rasterization](2.1-pattern-fill-rasterization.md) · [Contents](README.md) · [Next: BGI Stroked Fonts ▶](3.1-bgi-stroked-fonts.md)

A RIPscrip icon is a device-dependent 16-color bitmap in Borland BGI `getimage()`/`putimage()` buffer format, written to disk verbatim; `.ICN` (icons), `.MSK` (masks) and `.HIC` (hot icons) are the identical format, distinguished only by role. The 1.54 specification documents it in its [appendix](../ripscrip/6.1-content-file-roles.md) (`RIPScrip-1.54.txt`, "APPENDIX A: RIPscrip ICON FILE FORMAT SPECIFICATION"), whose trailing-byte count does not match the files RIPterm and RIPaint actually shipped.

## Binary layout

There is no magic number. The file begins with a 4-byte header at offset 0:

```c
struct icn_header {
    uint16_t width_minus_1;   /* little-endian; pixel width  - 1 */
    uint16_t height_minus_1;  /* little-endian; pixel height - 1 */
};
```

The dimension words store width-1 and height-1 (spec appendix; confirmed by every shipped file, e.g. `../../1.54/assets/icons/BUTTON.ICN` begins `15 00 10 00` = 22x17 pixels, and by readers: `RIPtermJS:src/BGI.js` `fetchIcon()` does `getUint16(0, true) + 1`, `sbbs:src/syncterm/ripper.c` `load_stamp_icon()` does `tmp + 1`).

Pixel data follows immediately at offset 4, stored scan line by scan line, top to bottom. Each scan line is four consecutive **bit planes**, most significant plane first:

```text
offset 4:  scan line 0, plane 3   ⌈width/8⌉ bytes
           scan line 0, plane 2   ⌈width/8⌉ bytes
           scan line 0, plane 1   ⌈width/8⌉ bytes
           scan line 0, plane 0   ⌈width/8⌉ bytes
           scan line 1, plane 3
           ...
           scan line h-1, plane 0
           2 trailing bytes (uninitialized "trash")
```

- Each plane chunk is one monochrome row: ⌈width/8⌉ bytes, bit 7 of each byte = leftmost pixel, rows padded on the right with don't-care bits (spec appendix).
- A pixel's 4-bit color index is assembled as `(plane3_bit << 3) | (plane2_bit << 2) | (plane1_bit << 1) | plane0_bit` - i.e. the file stores plane 3 (bit 3) first (spec appendix worked example; `RIPtermJS:src/BGI.js` `fetchIcon()`; `sbbs:src/syncterm/ripper.c` `load_stamp_icon()` plane-unpacking loop).
- The color indices are standard EGA palette slots 0-15 as set by RIP_SET_PALETTE; icons carry no palette of their own.

### Worked example: `RADIO.ICN`

`../../1.54/assets/icons/RADIO.ICN` (94 bytes) begins `0e 00 0a 00` → 15x11 pixels, so each plane row is ⌈15/8⌉ = 2 bytes and each scan line occupies 8 bytes. The first scan line's bytes are `00 00 f8 3e f8 3e f8 3e` (offsets 4-11):

```text
plane 3:  00 00  =  000000000000000-
plane 2:  f8 3e  =  111110000011111-
plane 1:  f8 3e  =  111110000011111-
plane 0:  f8 3e  =  111110000011111-
pixels:             777770000077777   (- = pad bit, don't care)
```

Row 0 is therefore five pixels of color 7 (light gray), five of color 0, five of color 7 - the top edge of the radio-button widget. Total size: 4 + 11·4·2 + 2 = 94 bytes, matching the file.

## File size and the trailing bytes

Every icon-format file in the original 1.5x distributions obeys:

```text
file_size = 4 + height * 4 * ceil(width / 8) + 2
```

Verified byte-exactly against all 184 `.ICN` files in `../../1.54/assets/icons/`, plus the 3 `.HIC` and 4 `.MSK` files in the RIPterm 1.54 install (`~/src/rip-tools/RIPterm154/DOS/RIPTERM/ICONS/`) - zero mismatches.

**The spec appendix is wrong about the tail.** [The appendix](../ripscrip/6.1-content-file-roles.md) documents exactly **one** trailing "trash byte", and its worked example (6x2 image) totals 13 bytes; real files always carry **two** trailing bytes. The values are garbage - observed tails include `00 00` (`WORLD-1.ICN`), `01 00` (`BUBBLE.MSK`), `04 00` (`BUTTON.ICN`), `39 3a` (`MOUSE.ICN`) - consistent with RIPterm writing the full uninitialized `imagesize()` buffer that Borland's EGAVGA driver allocates, whose size is data + 6 bytes (4 header + 2 slack). SyncTERM encodes the same 6-byte overhead in its size-limit check: `imgsz = ((w + 7) / 8) * 4 * h + 6` (`sbbs:src/syncterm/ripper.c`, `bgi_imagesize_ok()`). Readers should simply ignore everything after the pixel data; writers wanting byte-exact fidelity with TeleGrafix tools should emit two zero bytes.

Because the BGI buffer size is a 16-bit quantity, an icon whose buffer would exceed 65,535 bytes cannot exist as a valid BGI image; RIPterm reacts to over-size images with an "Image too large" error popup that has observable side effects on the drawing state (see [Canvas, Clipping & Write Modes](2.0-canvas-clipping-write-modes.md#image-too-large-side-effects)).

## How icons are referenced and stored

- RIPTERM.DOC's glossary defines the three extensions together: "an icon is a bit map graphic of varying size. Icon files may end in .ICN, .MSK (mask files), or .HIC (hot icons - used with buttons)" (`~/src/rip-tools/RIPterm154/DOS/RIPTERM/RIPTERM.DOC`, §1.7 glossary).
- Icon files live in the `ICONS\` sub-directory of the RIPterm install, optionally in per-host sub-directories falling back to `ICONS\` (RIPTERM.DOC §1.5 and the host-directory notes around its "icons" configuration field) - the storage layout and lookup order are documented in [Connection Directory Model](4.0-connection-directory-model.md).
- [RIP_LOAD_ICON](../ripscrip/4.0-images-and-icons.md#rip_load_icon) filenames may not contain path information; if the filename has no extension, `.ICN` is appended, and an explicit extension (e.g. `.MSK`) is used verbatim (spec; `sbbs:src/syncterm/ripper.c` `load_stamp_icon()` rejects `/`, `\`, `..` and appends `.ICN` only when the name has no `.`).
- [RIP_WRITE_ICON](../ripscrip/4.0-images-and-icons.md#rip_write_icon) writes the clipboard to disk in this same format; [RIP_GET_IMAGE](../ripscrip/4.0-images-and-icons.md#rip_get_image)/[RIP_PUT_IMAGE](../ripscrip/4.0-images-and-icons.md#rip_put_image) use the identical buffer in memory.

## `.MSK` mask files

A `.MSK` file is structurally an ordinary icon whose four bit planes are **identical**, so every pixel is either color 0 (black) or color 15 (white). Verified programmatically for all four masks shipped with RIPterm 1.54 (`BUBBLE.MSK` 27x23, `CHROME.MSK` 47x34, `MOUSE.MSK` 97x36, `TANK.MSK` 129x56 in `~/src/rip-tools/RIPterm154/DOS/RIPTERM/ICONS/`): in each file, planes 0-2 of every scan line are byte-identical to plane 3.

Masks implement transparent (non-rectangular) icon stamping with the classic AND/OR sprite technique - RIPscrip has no dedicated mask command; the mask is simply loaded with RIP_LOAD_ICON in AND mode at the same position before the icon:

- RIPaint's help topic "Icon Mask Creation" describes authoring: the icon editor's Mask button converts the image to black and white (the chosen "invisible" color and any black pixels become the mask), saved with the icon's basename and an `.MSK` extension; "When you load this mask image first before you load the original icon in the same spot, the color you selected to be invisible will not show up" (`RIPAINT.HLP` in `~/src/rip-tools/artifacts/ripaint-1.52/RIPAINT.ZIP`).
- Observed in shipped scenes: RIPaint's `BOUNCY.RIP` animates a ball with repeated pairs `!|1I000003110CHROME.MSK` (mode 03 = AND) immediately followed by `!|1I000002110CHROME.ICN` (mode 02 = OR) at the same coordinates (`RIPAINT.ZIP:BOUNCY.RIP`).

Note the implied plane convention: white (15) mask pixels preserve the screen under AND, black (0) mask pixels clear it; the paired `.ICN` has color 0 wherever the mask is white, so the OR pass leaves the background visible there.

## `.HIC` hot icon files

A `.HIC` file is byte-for-byte an ordinary icon with a different extension - e.g. `BUTTON.HIC` and `BUTTON.ICN` are both 22x17, 210 bytes (`~/src/rip-tools/RIPterm154/DOS/RIPTERM/ICONS/BUTTON.HIC`, `../../1.54/assets/icons/BUTTON.ICN`).

Hot icons are the "pressed" images of icon buttons, selected purely by filename convention (spec, [RIP_BUTTON_STYLE flag 4096](../ripscrip/4.2-buttons.md#rip_button_style)):

- When a [RIP_BUTTON](../ripscrip/4.2-buttons.md#rip_button) is an Icon Button and the current button style has flag 4096 ("Make Icon Button use Hot Icons") set, the depressed image is loaded from the same basename as the button's icon with the extension replaced by `.HIC`, and stamped in COPY mode.
- If the `.HIC` file does not exist, the original `.ICN` image is stamped in NOT mode for the duration of the depression (spec, same section).
- Reference implementation of the name substitution: `RIPtermJS:src/ripterm.js` `hotIconFilename()` (replaces `.ICN` with `.HIC`), with the flag-4096 check in `parseIconNames()`.

RIPterm 1.54 shipped three hot icons - `BUTTON.HIC`, `RADIO.HIC`, `RADIOBUT.HIC` - pairing with `BUTTON.ICN`, `RADIO.ICN`, `RADIOBUT.ICN` (`~/src/rip-tools/RIPterm154/DOS/RIPTERM/ICONS/`; the `.ICN` halves are preserved in `../../1.54/assets/icons/`).
