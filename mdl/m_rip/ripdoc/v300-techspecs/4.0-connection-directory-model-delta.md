# Connection Directory Model (delta)

[◀ Prev: MicroANSI Delta](3.3-microansi-maf-delta.md) · [Contents](README.md)

The storage model is the [v2.0 connection directory model](../../2.0/techspecs/4.0-connection-directory-model-delta.md) - itself the unchanged [v1.54 model](../../1.54/techspecs/4.0-connection-directory-model.md) widened to the whole media family - carried into a Windows Telnet client. The substance survives intact: a per-host directory checked first, the shared `ICONS\` directory as fallback, [file override](../../glossary.md#client-storage) semantics, auto-creation without user involvement.

Evidence below is from the RIPtel 3.1 WinHelp text (`~/src/rip-tools/artifacts/RIPtel/RIPTEL.HLP`, topic text extracted via `strings`; bracketed words rejoin the product name and jump-text fragments the extraction splits) - see the [help extraction](../../3.0/research/riptel-help-extraction.md) for the full survey.

## "Host directory" - the per-bookmark connection directory

RIPtel renames the [connection directory](../../glossary.md#client-storage) the **host directory** and configures it per **bookmark** - RIPtel's name for a dialing-directory entry - in the bookmark editor's Advanced options.

RIPTEL.HLP's "Host Directory" topic restates the model in RIPtel terms, naming the lookup order outright:

> The host directory is used when an online service displays information with [RIPscrip] graphics. … the host system can instruct [RIPtel] to load an image resource from its local hard disc and display the data on the video screen. [RIPtel] automatically looks for those files in a specific directory on the hard drive. If you have specified a host directory in the bookmark editor, than _[sic]_ [RIPtel] will look for these kinds of files in that directory first. If the file cannot be found, then it checks the [ICONS\\] directory. If the file still cannot be found, then [RIPtel] checks any additional search directories that you have defined in the … setup screen. After checking all of these possible directories, [RIPtel] will only display an error if the file couldn't be found.

"Host Directory" appears in the enumerated **Advanced Bookmark Options** (alongside VT-102 emulation, local echo, backspace mode, and the macro file), and new bookmarks inherit defaults: "When you create a new bookmark, these settings are 'imported' from [RIPtel]'s setup configuration, so you have a basic starting point to work from." Auto-creation carries over from the DOS clients, now attributed to the services themselves:

> Normally you will not have to set this option. Many online services create their own host directories for you, without your knowledge. But in the event that a system doesn't do this, then you may create your own with the host directory option in the bookmark editor.

The macro/host-command language documents the same resolution order for local file playback (`$>FILE.RIP$`, `$)FILE.WAV$`, `$<FILE.BMP$`, `$(FILE.JPG$`): searched in the host directory first, then `ICONS\`, then the configured search path ([help extraction §6](../../3.0/research/riptel-help-extraction.md)).

## New third tier - the icon search path

The setup-level "Icon Search Path" is additive and read-only in role: extra directories consulted **after** the two classic tiers fail, aimed at CD-ROM-distributed resource sets ("This option is very useful if you use online services that provide a CD-ROM for accessing system resources"). Multiple directories are separated by semicolons - the help's example is `C:\Windows;D:\;Icons\MyIcons` - and relative entries resolve under the RIPtel install directory. The help is explicit that the first two tiers are implicit: "[RIPtel] always searches for files in the ICONS\ directory, so you never need to add this one. Also, if you have a host directory setup in your bookmarks editor, you don't need to add that one either." Nothing suggests host-delivered files are ever written to a search-path directory - delivery still targets the host directory/`ICONS\` pair; the search path only extends lookup.

## New constraint - host directories confined to the install tree

RIPtel adds an explicit placement rule the DOS manuals never stated:

> Like the [ICONS\\] directory, your host directory can only exist under the directory where [RIPtel] is installed. For security reasons, the host directory cannot exist in any arbitrary location on your hard drive. You may define search directories anywhere on your system, but not host directories.

The asymmetry is the point: directories the **host** can populate (host directory) are jailed under the install root; directories only the **user** configures (search path) may live anywhere, including other drives. A modern implementation should preserve the same property - host-influenced writes stay inside a client-owned sandbox.

## Programmatic surface

The model is reachable programmatically in 3.x, not just via configuration: the RIPscrip 3.0 function-name table (RIPSCRIP.HLP) includes **RIP_SwitchDirectory** among the wire commands, the RIPTEL.EXE ↔ RIPSCRIP.DLL client API exports **RIP_SetHostDirectory** / **RIP_GetHostDirectory**, and the text-variable processor list includes a **HOSTDIR** handler ([help extraction §3, §5](../../3.0/research/riptel-help-extraction.md)). Wire-level semantics of RIP_SwitchDirectory are otherwise unrecovered - no demo script in the RIPtel corpus exercises it.

## File transfers stay outside the model

As in 2.0, ordinary Zmodem transfers do not flow through the resource directories: RIPtel stores received files in a `Files` directory under the install root by default, with separate user-configurable download and upload directories (RIPTEL.HLP "Download Directory" / "Upload Directory" topics; `INSTALL.LOG` creates `Files`, `ICONS`, and `FONTS` at install time). Fonts likewise remain global - `FONTS\` - never per-host, matching the [v2.0 rule](../../2.0/techspecs/4.0-connection-directory-model-delta.md).

## Implementer summary

- Resolution order: **host directory → default `ICONS\` directory → icon search path entries in order**; first hit wins; error only after all tiers fail.
- The host directory is the connection directory under a new name - per-bookmark, auto-created, host-writable, and confined beneath the client's own root; treat that confinement as a required security property.
- The search path is lookup-only (semicolon-separated, user-configured, unrestricted location); host deliveries never write there.
- User file transfers (download/upload directories) remain a separate namespace from host-deliverable resources, exactly as in the [2.0 block-mode rule](../../2.0/techspecs/4.0-connection-directory-model-delta.md).
