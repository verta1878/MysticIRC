# 6.0 Writing .RIP Files

[◀ Prev: 5.5 Queries & Advanced Commands](5.5-queries-and-advanced-commands.md) · [Contents](README.md) · [Next: 6.1 Content File Roles ▶](6.1-content-file-roles.md)

Authoring-level conventions for `.RIP` files - how a captured command stream is stored, wrapped, escaped, and bracketed by the prologue and epilogue conventions of TeleGrafix's own shipped scenes.

_Parser-side edge cases - stream-based dispatch, wild-data field-layout variance - are implementer material in the [.RIP stream parsing techspec](../techspecs/1.0-rip-stream-parsing.md)._

## What a .RIP file is

A `.RIP` file is not a distinct binary format: it is a captured RIPscrip command stream - exactly the bytes a host would transmit - stored as a DOS text file. Everything in [1.1 Protocol & Command Hierarchy](1.1-protocol-and-command-hierarchy.md) therefore applies verbatim to file content. A file can be transmitted by a host, replayed locally (see [5.3 Local File Playback](5.3-local-playback.md)), or played back by [RIP_READ_SCENE](5.5-queries-and-advanced-commands.md#rip_read_scene).

## Encoding and line endings

- Line endings are CRLF (`0D 0A`), as in every DOS-era capture. Line endings are **significant** to the parser (a bare CR terminates a command - observed terminal behavior, see the [.RIP stream parsing techspec](../techspecs/1.0-rip-stream-parsing.md)), so `.RIP` files should be stored and transferred byte-exact - never re-wrapped or "normalized".
- Text content (RIP_TEXT strings, button labels, embedded raw text) is [CP437](../../glossary.md) - the code page of DOS-based BBS terminals and host software. There is no in-band encoding declaration.

## Line length and continuation

Syntax rule 5 allows any command or line to be split with a backslash (`\`) immediately before the line break, "to conform to right margins and escape word wrapping". Authoring practice from the era's own files:

- TeleGrafix-era tools wrap at 80 columns - every RIPaint/RIPterm-era capture keeps its maximum line length ≤ 80 including the `\`.
- The split may land **anywhere** - mid-parameter, mid-number, even mid-filename. Real shipped scenes split polygon coordinate lists and even words of text across the continuation.
- The 80-column limit is a writer convention, **not** a reader guarantee: later files in the wild run longer (up to ~130 columns observed), and terminals accept arbitrarily long lines. Wrap for tool compatibility, but don't rely on readers enforcing it.
- Watch trailing backslashes: an **odd** count means continuation, an **even** count means escaped literal backslashes (syntax rule 13's `\\\` example). If you need a literal `\` at end-of-line, write `\\`; a continuation after a literal backslash needs `\\\`.

## Escaping in text parameters

Inside text parameters (syntax rules 11 and 13):

- `\!` → literal `!`, `\|` → literal `|`, `\\` → literal `\`.
- Escaping `!` matters when a text string could otherwise put an exclamation mark where a new line begins - e.g. drawn text ending one command and starting the next: `!|@1O65FOR YOUR VIEWING PLEASURE\!|…` keeps the exclamation mark out of introducer position while the following `|` still separates commands.

## Mixing ANSI and plain text

Because lines that do not begin with `!|` pass through to the [text window](1.4-terminal-ansi-view.md), `.RIP` files freely intermix RIPscrip with ANSI sequences and plain text. Era files even embed ANSI music (`ESC[MF…` sequences) between RIP lines, using cursor-up (`ESC[A`) to keep the music lines from scrolling the display. [Auto-sensing](1.1-protocol-and-command-hierarchy.md#ansi-sequences-auto-sensing) sequences (`ESC[!`, `ESC[0!`, `ESC[1!`, `ESC[2!`) may also appear in captures.

## Scene prologue and epilogue conventions

TeleGrafix never specified how a `.RIP` file should begin or end, but the shipped scenes are consistent:

- **Prologue** - nearly every scene opens with some ordering of: `!|*` ([RIP_RESET_WINDOWS](1.3-world-view-virtual-canvas.md#rip_reset_windows) - full reset + clear), `!|1K` ([RIP_KILL_MOUSE_FIELDS](4.1-mouse-fields.md#rip_kill_mouse_fields) - the spec explicitly recommends it "at the beginning of each Scene"), and a [RIP_TEXT_WINDOW](1.4-terminal-ansi-view.md#rip_text_window) definition (`!|w…`, often `w0000000000` to hide the text window or a full definition like `w0013271410`). Common observed openings: `!|*|1K|w0013271410|…`, `!|1K|*|w0010271610|…`, `!|1K` alone, `!|*` alone.
- Scenes that need a known graphics state continue with `W0` (write mode copy), `=00000001` (solid line, width 1), a palette (`Q…`/`a…`), and a color (`c0F`) before drawing - state is inherited from whatever ran before, so well-behaved scenes re-establish it.
- **Epilogue** - files end with `|#|#|#` - three consecutive [RIP_NO_MORE](5.5-queries-and-advanced-commands.md#rip_no_more) commands, following the spec's own advice that "the Host should transmit three or more RIP_NO_MORE command[s] consecutively" for noise immunity, sometimes followed by one empty CRLF line.

## Naming and delivery

Files referenced from commands and playback variables use bare DOS-style names - no path or sub-directory information (commands that take filenames reject paths). The `.RIP` extension may be omitted in playback variables and is appended automatically. Where files live on the terminal and how a host delivers them is covered in [6.2 Asset Delivery & Storage](6.2-asset-delivery-and-storage.md).
